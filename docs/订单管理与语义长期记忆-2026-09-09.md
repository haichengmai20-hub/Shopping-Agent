# 我的订单与语义长期记忆

2026-09-09 后续交付。代码以当前安装的 AgentScope 2.0.6 为准；本轮补齐订单产品入口，将长期偏好从“原句存储 + 默认按时间选取”改为“模型提炼 + 持久向量 + 语义召回”。

## 我的订单

侧栏“我的订单”支持全部/已确认/已取消筛选、每页 10 条、订单详情、商品与规格/数量/金额、收货信息和取消原因。服务端 `GET /commerce/orders` 按认证后的买家过滤，在 SQL 层分页；不加载其它买家的订单再由前端筛选。

取消流程：填写原因 → 生成现有取消确认资源 → 用户明确批准 → 原有 SQLite 交易台账原子更新 → 订单列表刷新。准备确认不执行取消，刷新能恢复确认与订单终态。订单仍是本地购买意向，不伪造付款、退款或物流状态。

## 调研结论与接口版本

调研使用官方文档、源码和工作示例；已克隆 AgentScope 仓库并对照本机安装包。

| 方案 | 可借鉴/采用的机制 | 本项目取舍 |
| --- | --- | --- |
| AgentScope 原生接口 | 2.0.6 的 `MiddlewareBase.on_reply`，官方 Mem0/ReMe 中间件与示例 | 本轮实现 `BuyerMemoryMiddleware`，真正挂入 MainAgent 中间件链；保留现有业务记忆工具 |
| Mem0 OSS | LLM 提炼事实、定制领域提示、向量检索、过滤与记忆管理 | 可作为后端候选；当前不引入运行依赖，需另验用户隔离、原子更新/删除和并发部署 |
| ReMe | 对话来源与提炼记忆分层、可解释维护、向量/BM25 检索，支持个人/过程记忆 | 更适合未来扩展经验记忆和完整来源管理；当前只做买家偏好，不采集整个对话形成第二套原文库 |
| 本轮后端 | SQLite 规范化事实与向量同一事务、精确余弦检索 | 每位买家上限 200 条，数据小，优先一致性与可运维性；不是大规模 ANN 索引，亦不声称接入了 Mem0 |

[AgentScope 当前官方示例](https://github.com/agentscope-ai/agentscope/tree/main/examples/long_term_memory) 包含 mem0、reme 和 agentic_memory。旧教程的 `LongTermMemoryBase` 不能直接套在 2.0.6；本机实际接口是 `Mem0Middleware`、`ReMeMiddleware` 等 `MiddlewareBase` 实现。

[Mem0 官方自定义提炼说明](https://docs.mem0.ai/open-source/features/custom-instructions) 强调限定领域事实、输出结构化 facts、用正反例避免无关信息入库；当前文档将 `custom_fact_extraction_prompt` 改名为 `custom_instructions`。这也说明配置不能依靠旧文章猜测。

[Mem0 OSS 部署说明](https://docs.mem0.ai/open-source/overview) 支持库内或独立服务部署。库内默认本地 Qdrant 与独立历史库，服务器形态可用 Postgres/pgvector；项目接入时必须显式配置模型、目录和用户过滤，不能让默认临时目录承担持久记忆。

[AgentScope/Mem0 兼容问题](https://github.com/agentscope-ai/agentscope/issues/1511) 记录过 Mem0 2.x 将身份过滤从顶层参数移入 `filters` 的不兼容；当前 AgentScope 源码已经采用过滤字典。我们采用“按已安装版本读源码”的接口策略，不因旧 issue 推断当前所有版本都不可用。

[ReMe 官方仓库](https://github.com/agentscope-ai/ReMe) 将原始来源、工作记忆和长期提炼分层，提供记忆管理与检索。对本项目的启发是明确区分用户输入、提炼事实和本轮召回，而不是把整段输入直接作为长期记忆。

## 写入与持久化

```text
页面输入 / remember、update 工具
  → 可信买家身份
  → AgentScope ChatModel 提炼（只提取本人稳定购物偏好）
  → JSON、来源片段、类别、长度、稳定性/置信度校验
  → embedding
  → SQLite 事务：规范化事实 + 向量 + 来源哈希 + 模型标识
  → 页面重新读取实际保存的记忆
```

提炼去除寒暄、赘述、重复、临时预算和行程、第三人称/假设、地址电话与指令；保留否定和商品适用范围。单次最多 5 条、每条 120 字；编辑只接受一条独立事实。没有有效事实时拒绝保存。提炼/向量失败不降级为保存原文。

已有规范化陈述作为同义归一化参照，同类别/同陈述唯一键去重，同源输入重复提交也按来源哈希合并。语义归一化仍依赖模型，并非严格的任意同义/冲突推理器；改变既有偏好应走明确编辑/修改工具，不自动批量删除相似记忆。

新权威库为 `DATA_DIR/buyer_memory.db`，`memory_facts` 同行保存事实与向量，`memory_migrations` 记录买家迁移完成状态。新记忆库只保留提炼事实和原文哈希，不保存填写的整段原文；正常对话流水/审计事件仍遵守原系统的独立存储边界。

旧 PreferenceStore 在买家首次访问时提炼并迁移，事实和迁移标记一次提交；失败不标为完成、原数据仍在。旧库作为迁移来源保留但不再参与该买家的召回，删除不会触发重新导入。若要物理清除历史原文，应另按备份/流水保留策略处理，不能把“当前记忆已删除”解释成所有备份和历史会话均已抹除。

## 读取、修改和删除

- 主 Agent 使用 AgentScope 中间件 `on_reply` 在每轮回复前读取最新权威事实，正向偏好按 query 向量做精确余弦召回，默认最小分数 0.25、数量沿用 `PREFERENCE_TOP_K`。不依赖旧 `PREFERENCE_RELEVANCE_ENABLED` 开关。
- 负向约束全量带入，并继续映射到业务材质过滤；不能因与本轮 query 相似度低而丢掉“不要塑料”等约束。
- query 向量服务失败时只保留最新负向约束并记录降级，不伪装成向量命中。更换 embedding 模型/维度需明确重建已有索引，不混用不兼容向量。
- 修改按旧陈述原子替换；删除按买家+精确陈述执行。向量同记录更新或删除，返回结果前再次核验当前记录，避免已删除的旧候选复活。
- 只在用户通过页面或工具明确写入时沉淀，不自动把助手回答当成买家事实。当前轮显式需求优先于长期偏好。
- Agent 接口类是 `BuyerMemoryMiddleware(MiddlewareBase)`；底层存储复用 `PreferenceStore` 的领域写入端口并提供 `select` 召回。将来换 Mem0/ReMe 时应在基础设施层适配，不改变页面接口或扩大工具权限。

接入外部框架的后续验收清单：固定版本；可信 `user_id` 过滤；禁止模型自选买家；同义/冲突测试；清晰的结果到本地记录 ID 映射；幂等与失败恢复；删除即时失效；API/worker 并发；备份迁移；关闭自动全对话采集；无凭据回归和真实模型评测。当前没有这些框架的性能/效果对比结论。
