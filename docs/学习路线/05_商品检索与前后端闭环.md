# 第五阶段 商品检索与前后端闭环

本阶段完整追踪一次商品检索：用户的一句话怎样变成工具参数，商品从哪里查出来，哪些条件由代码过滤，页面上的价格从哪里来，刷新后怎样找回历史。

建议用约 60 分钟学习，另用约 25 分钟做作业。本文由已在页面审阅的第五阶段稿整理，2026-10-07 落盘；对应当前本地源码基线 8cbd4d6b94eb9713952d3bd8f050da176accdca1。教学路径和金额不是本次真实模型执行。

## 一、这一阶段正在学习项目的什么

| 要完成的事 | 对应的 Globex 能力 |
| --- | --- |
| 从输入框找到实际请求 | 前端提交与后端 API |
| 从自然语言找到结构化条件 | Agent 工具选择和参数生成 |
| 从工具入口追到商品结果 | 检索、过滤、计价和商品卡构造 |
| 从后端结果追到页面字段 | AG-UI 事件、前端状态和 React 渲染 |
| 从本轮结果追到刷新后的历史 | 运行日志、会话与商品证据 |
| 找到哪里开始不符合预期 | 按数据变化定位问题 |

前四阶段分别提供模块地图、AgentLoop、状态机制和评测方法；第五阶段将它们接起来，完整读懂代表性工具 product_search_tool。

主例：“找一个轻便背包，寄到中国，单件商品价不超过 300 元人民币，同时告诉我加上运费和关税后的到手价。”

对照变体：“总到手价不超过 300 元人民币。”两句话的要求不同，当前代码保障的范围也不同。已在前两阶段补充核验：price_max_major 过滤的是换算后的单件商品金额；税运在后续组装商品卡时才计算。

为便于学习，下图采用 MainAgent 直接调用商品工具的路径。实际模型也可能先澄清、查品类知识或按需派发子 Agent。

        |

        |

        |

        +-- 取得或恢复会话 Agent
        +-- 组织消息及相关上下文
        |

MainAgent 生成 product_search_tool 调用
        | normalized_query、ship_to、price_max_major……
        v

        +-- 参数处理
        +-- 构造 ProductSearchSpec
        |

        +-- 精确查询 / 普通召回 / Hybrid

                                             CommerceClient

## 三、商品数据怎样准备好

本节学习商品工具实际查询的数据来源。当前本机开发使用版本化 data/catalog-v3.jsonl；加载器还兼容打包目录位置，选择逻辑见 [seed_products.py](../../app/infrastructure/persistence/seed_products.py)。不是每次提问都实时访问多个电商平台抓取商品。

~~~text
版本化商品目录
      |
      v
加载为 Product / SKU 对象
      +-- 商品仓储：提供商品属性与规格
      +-- 持久库存：提供业务库存状态
      |
      v
商品 searchable_text()
      |
      v
embedding 服务生成向量
      |
      v
写入 Qdrant 商品索引
~~~

| 组件 | 人话解释 | 当前承接的数据 |
| --- | --- | --- |
| 商品仓储 | 查询商品业务数据的入口 | 标题、规格、配送、材质等 |
| Embedding 服务 | 把文本变成可比较的向量 | 查询和商品文本的向量表示 |
| Qdrant 索引 | 按向量相似度找候选 | 当前主要返回商品 ID 和相似度 |

Qdrant 找到 ID 后，用例仍回到商品仓储取得商品对象；相似度分数不能代替价格、库存和配送事实。

阅读 [index_bootstrap.py](../../app/infrastructure/vector/index_bootstrap.py)、[qdrant_product_index.py](../../app/infrastructure/vector/qdrant_product_index.py)和 [catalog_search.py 的 _vector_recall()](../../app/application/usecases/catalog_search.py)，分别回答“商品怎样入索引”“索引返回什么”“怎样取回业务对象”。

向量建库失败时，代码会记录警告并允许检索降级。因此启动成功或 /health 正常不能单独证明 embedding 与向量检索已经成功。

## 四、前端输入怎样变成工具参数

本节学习用户文本、HTTP 请求与工具参数的转换。[useCommerceAgent.ts](../../frontend/src/hooks/useCommerceAgent.ts)创建 CommerceClient，使用 /commerce/ag-ui/run；后端 [parse_intent()](../../app/presentation/ag_ui.py)把请求转为业务输入。

| 前端请求信息 | 后端含义 |
| --- | --- |
| messages 最后一条用户内容 | 本轮 raw_query |
| threadId | shopping_session_id |
| runId | 本次运行标识 |
| forwardedProps.buyerId | 买家信息，仍需后端校验归属 |
| locale、currency | 地区语言与币种信息 |

~~~text
locale=zh-CN          语言地区
ship_to=CN           商品配送目的地
target_currency=CNY  商品报价目标币种
source_language      商品原文语言
~~~

这几个字段不能互相替代。中文提问不意味着一定配送中国；前端写人民币，也不证明模型已把预算传进商品工具。

模型可能生成以下工具参数。这里只示意参数，不是完整 HTTP 报文或已执行的调用：

~~~json
{
  "normalized_query": "轻便 背包",
  "ship_to": "CN",
  "price_max_major": 300,
  "target_currency": "CNY",
  "top_k": 3
}
~~~

[product_search_tool.py](../../app/application/tools/product_search_tool.py)会处理数字字符串、品类和约束，检查目的地，再构造 [ProductSearchSpec](../../app/domain/catalog/product_search_spec.py)。规格对象检查查询词、top_k 类型与范围，以及金额是否有限、非负。

~~~text
模型参数
    +-- 数字字符串转数字
    +-- 品类与相关约束处理
    +-- 目的地检查
    |
    v
ProductSearchSpec 校验
    |
    v
CatalogSearchUseCase
~~~

相关性条件与明确过滤条件也要分开。“轻便”写入查询词，会影响检索和后续判断；工具当前没有独立 max_weight_kg 参数，不能仅凭出现“轻便”就声称代码保证某个重量上限。

## 五、完整读一次商品检索用例

本节学习候选怎样被找到、排序和排除。[execute()](../../app/application/usecases/catalog_search.py)先判断三个入口分支：

~~~text
execute(spec)
    |
查询中有明确商品 / SKU ID？
    +-- 有 → 精确查目录
    |          +-- 存在且符合条件 → 商品卡
    |          +-- 存在但不符合条件 → filtered_out
    |          +-- 没找到指定 ID → missing_identifiers
    |
    +-- 无
          +-- Hybrid 开启 → BM25 + 向量 → 融合 → 尝试精排
          +-- Hybrid 关闭 → 向量召回 → 尝试精排
                                   |
                                   +-- 向量不可用或无候选时关键词兜底
~~~

召回是从大集合找出可能相关的候选，精排是对这批候选做更细的排序。

~~~text
normalized_query → Embedding → 查询向量
    |
Qdrant → 商品 ID + 相似度
    |
商品仓储 → 商品对象
    |
专用 reranker 尝试重排
    |
业务条件检查 → 最多 top_k 个 → 商品卡
~~~

代码可以在一定范围扩大向量候选窗口来补足合格候选，但不等于穷尽全库。普通分支的实际策略可观察以下字段：

| recall_strategy | 含义 |
| --- | --- |
| embedding_rerank | 向量召回且完成精排 |
| embedding_only | 向量候选，未应用精排 |
| keyword_2gram | 关键词兜底 |
| exact_id_lookup | 明确商品或 SKU ID 查询 |

rerank_applied 说明实际有没有精排；配置模型名称不证明本轮已经使用。[精排器装配](../../app/infrastructure/rerank/factory.py)

Hybrid 使用应用层 BM25（词项相关性）与向量召回，再用 RRF 按排名融合。HYBRID_RECALL_ENABLED 配置缺省值关闭；代码存在不证明本次运行启用了它。

~~~text
同一查询
    +-- BM25 词项召回 --+
    +-- 向量召回 ------+
                       |
                       v
              业务资格检查与融合
                       |
                       v
                   尝试精排
                       |
                       v
                  去重与 Top-K
~~~

_reject_reason() 还检查库存、品类、材质、配送等条件。空结果可来自未召回、候选被过滤、指定 SKU 缺货或明确 ID 不存在。只有相应精确存在性查询才能支持“不存在”；普通语义检索未命中不够。

filtered_out 是有限拒绝摘要，不保证列全；total_candidates 是当次分支统计，不是商品目录总数。

## 六、商品金额 规格与到手价

本节学习页面金额的实际口径。[CatalogSearchUseCase._within_price_cap()](../../app/application/usecases/catalog_search.py)的逻辑是：

~~~text
选择用于判断的 SKU
    |
商品金额换算为 target_currency
    |
比较商品金额 <= price_max_major
~~~

之后 _to_card() 才另外计算税运：

~~~text
SKU 商品金额
    |
项目内税运规则
    |
商品小计 + 运费 + 关税
    |
landed_price.landed_total_major
~~~

主例“单件商品价不超过 300，同时展示到手价”与当前代码结构相符；“总到手价不超过 300”还需额外核对。当前过滤没有比较 landed_total_major 与上限。本次只澄清实现范围，没有修复这项业务缺口。

Product 表示商品，SKU 表示具体规格，例如颜色和容量，价格与库存可以不同。当前 [primary_available_sku()](../../app/domain/catalog/product.py)取列表中第一个有库存的规格，不能解释成全商品最便宜的规格；明确请求 SKU 时，精确查询按那个规格检查。

| 字段 | 含义 |
| --- | --- |
| price_major、currency | 当前默认或指定规格商品金额，已换为目标币种 |
| source_price_major、source_currency | 原始报价 |
| skus[].price_major、skus[].currency | 各 SKU 原币报价 |
| default_sku_id | 这张卡当前采用的规格 |
| landed_price.landed_total_major | 本次计算到手价 |

商品卡税运调用当前传 quantity=1。换规格、数量或目的地不能直接沿用旧报价。[TariffSchedule](../../app/domain/shipping/tariff_schedule.py)是仓库里的简化演示规则，不能当作实时海关或物流报价。

## 七、一个结果的三个出口与前端展示

本节学习同一批商品怎样分别服务模型、页面和证据回查。用例结果返回后，工具层补 query_conditions、observed_at，保存完整依据，并交给不同消费者：

~~~text
CatalogSearchUseCase 返回 result
                |
product_search_tool 补查询条件和观察时间
                |
       +--------+------------------+------------------+
       |                           |                  |
       v                           v                  v
完整证据存储                 模型决策视图           业务 tool.result
result_ref                   ToolChunk              hits、策略等
       |                           |                  |
       v                           v                  v
后续引用回查                 Agent 继续判断          AG-UI 适配器
~~~

完整证据用于保存依据；模型视图限制本次推理所需内容，过大结果可能分页；业务事件把结构化展示信息交给前端链路。[工具结果处理](../../app/application/tools/product_search_tool.py)

~~~text
业务 tool.result
    |
ProductCandidateProjection
    |
AGUIRunAdapter 更新 state.products
    |
持久日志 → SSE → AG-UI Client
    |
CommerceClient.onStateChanged()
    |
readProducts(state.products)
    |
React 更新 ProductCards
~~~

状态投影是把执行过程中的结果整理为“现在应该展示的候选列表”。当前 [ProductCandidateProjection](../../app/application/agents/product_candidate_projection.py)用新普通查询替换候选；合法 hits=[] 会清空；没有 hits 的错误不会伪装成空检索；明确多个商品 ID 的精确查询才有专门的跨结果合并。

用户换条件后，旧商品未必符合本轮，不能无限追加。[ProductCards.tsx](../../frontend/src/components/ProductCards.tsx)分别展示商品价和到手价，主要格式化后端字段，不从模型文字自行推算税运。事件适配与接收见 [ag_ui_adapter.py](../../app/application/agents/ag_ui_adapter.py)和 [commerceClient.ts](../../frontend/src/lib/commerceClient.ts)。

## 八、本轮结束后怎样保存历史

编排器收尾保存会话、对话及商品证据；运行日志保存已产生的消息与状态投影，后续追问和刷新恢复各取合适记录。[orchestrator.py](../../app/application/agents/orchestrator.py)

~~~text
本轮商品与回答
    +-- AgentState：会话工作状态
    +-- 对话流水：买家输入和最终回答
    +-- 商品证据 / display_batch：候选与顺序
    +-- AG-UI 日志：页面消息和事件
                  |
                  v
        刷新 / 比较第二个 / 历史回查
~~~

这些存储不是一个无边界的大事务。排查时要找到哪份记录未保存或未读取。“当时有商品卡，刷新后丢失”应先查持久日志、历史接口和前端恢复，通常不是先改 embedding 模型。

## 九、按第一处差异定位问题

| 现象 | 优先检查 |
| --- | --- |
| 页面打开但消息失败 | 请求有没有到后端、配置、运行错误 |
| 只有选购知识没有商品 | 是否调用 product_search_tool |
| 声称没有商品 | 未召回、过滤、错误还是精确 ID 不存在 |
| 候选多但排序差 | 实际 recall_strategy、rerank_applied，再查召回与精排 |
| 商品价合格而到手价超预算 | 预算口径与 _within_price_cap 的比较字段 |
| 后端结果正确但卡片错误 | 业务事件、投影、AG-UI 状态、readProducts、组件 |
| 新查询为空仍显示旧候选 | 合法空结果、投影替换、状态应用 |
| 刷新后商品或顺序变化 | 日志、历史接口、展示批次和恢复 |

~~~text
预期是什么？
    |
观察到什么？
    |
输入这个环节时是否正确？
    |
离开这个环节的输出是否正确？
    |
找到第一处不符合预期的数据变化
    |
判断补配置、修实现还是修评测
~~~

第一阶段帮助找模块，第二阶段帮助追调用，第三阶段帮助看状态，第四阶段帮助判断证据是否足够。最后阶段让这些方法服务同一条业务链路。

## 十一、作业

### 作业 A：完整请求图

从“寄中国、商品价不超过 300 元的轻便背包，同时展示到手价”出发，图中包含页面、HTTP 解析、Agent 传参、ProductSearchSpec、召回过滤和卡片构造，以及完整证据/模型视图/前端事件三出口、页面渲染与历史保存。至少五条箭头写出具体字段。

### 作业 B：过滤推演与价格图

假设每件只有一个 SKU，币种均人民币，召回排序 A、B、C、D，top_k=3，其他条件符合。数据人为构造：

| 候选 | 商品价 | 可寄中国 | 有库存 | 给定到手价 |
| --- | ---: | --- | --- | ---: |
| A | 280 | 是 | 是 | 305 |
