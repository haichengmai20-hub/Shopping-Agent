# 第五阶段 商品检索与前后端闭环

<a id="overview-5"></a>
## 总览：05 在整个项目里做什么

**在整个项目里的位置。** 前四篇各讲一层：地图、循环、状态、评测。05 把它们用在同一条业务链路上，完整追一次商品检索：用户的一句话怎样变成工具参数，商品从哪里查出来，哪些条件由代码过滤，页面上的价格从哪里来，刷新后怎样找回历史。商品检索是能力层里最核心的工具，Globex 大部分回答都建立在它返回的事实上。它对应[纵览](README.md#overview-all)七站里的 ⑤ 商品检索，以及 ⑥ 里商品卡怎样到达页面。

**要回答的问题。** **一句「找一件轻便背包，寄到中国，300 元以内」怎样变成页面上的商品卡？哪些条件由代码保证，哪些要另外核对？**

**答案。**

- 数据：版本化的商品目录加载成商品和规格对象，再建成向量索引。向量只提供候选线索，价格、库存、配送这些事实总是回到商品数据里取。
- 检索：模型给的参数先校验成检索规格，再按「明确 ID 精确查询」「混合召回」「向量召回、关键词兜底」几条路找候选，尝试精排，最后用库存、配送、材质、价格等业务条件过滤。空结果可能是没召回、被过滤或 ID 不存在，要分开说。
- 金额与展示：价格上限只比较单件商品价，到手价按 1 件另算。一个结果有三个出口：完整证据、给模型的决策视图、给页面的事件；刷新和追问靠各自保存的记录恢复。

**放到训练推演里看。** 检索是策略最常用的动作，它返回的结构化事实，包括命中的商品、被过滤的候选及原因、到手价，既是策略的观察，也是计算奖励的依据。正因为代码只按单件价过滤，奖励必须自己核对总到手价，否则「推荐了超预算的商品」会被当成成功。

**全篇结构。**

| 段 | 包含的小节 | 学完能回答什么 |

## 文字版导读：先把全篇顺一遍

第一次读，先把这一节读完，再按链接进细节；复习时只读这一节。

**第一节：这一篇在学什么。** 主例是「找一个轻便背包，寄到中国，单件商品价不超过 300 元人民币，同时告诉我加上运费和关税后的到手价」，对照的说法是「总到手价不超过 300 元」。两句话要求不同，代码保障的范围也不同，这是全篇的主线。本篇要完成六件事：从输入框找到实际请求，从自然语言找到结构化条件，从工具入口追到商品结果，从后端结果追到页面字段，从本轮结果追到刷新后的历史，以及找出哪里开始不符合预期。详见[一、这一阶段正在学习项目的什么](#scope-5)。

**第二节：一次检索的完整路线。** 页面经 CommerceClient 发出请求 → 接口解析并校验买家与会话 → 运行管理器登记运行 → 编排器恢复会话、组织输入 → MainAgent 生成商品检索调用 → 工具处理参数、构造检索规格 → 检索用例找候选、过滤、生成商品卡和到手价 → 结果三路出去：完整证据保存、决策视图交给 Agent、商品事件经运行日志和 SSE 到页面 → 本轮收尾保存，刷新或追问时按记录恢复。每条箭头都要能说出传的是什么。详见[二、一次请求的完整路线](#route-5)。

**第三节：商品数据从哪来。** 运行时读的是版本化的样例目录 `data/catalog-v3.jsonl`，加载成商品和规格对象；商品文本经 embedding 服务变成向量，写进 Qdrant 索引。不是每次提问都去电商平台实时抓取。Qdrant 只返回商品 ID 和相似度，用例还要回到商品数据里取商品对象，相似度不能代替价格、库存和配送。向量建库失败时系统会降级继续运行，所以服务能启动、健康检查正常，都不能证明向量检索在工作。详见[三、商品数据怎样准备好](#catalog-5)。

**第四节：一句话怎样变成参数。** 前端请求里，最后一条用户消息是本轮问题，threadId 是会话，buyerId 是买家（后端还要校验归属），locale 和 currency 是地区语言和币种。语言地区、配送目的地、目标币种、商品原文语言是四个不同的字段，不能互相替代：中文提问不代表寄到中国，前端写人民币也不代表模型把预算传进了工具。模型生成的参数经工具处理后构造成检索规格，规格对象会校验查询词、数量范围和金额。还要分清相关性条件和过滤条件：「轻便」写进查询词，影响检索排序，但工具没有重量上限参数，代码不保证任何重量。详见[四、前端输入怎样变成工具参数](#params-5)。

**第五节：候选怎样被找到和排除。** 检索用例先看三条路：查询里有明确的商品或规格 ID 就精确查目录；否则开启混合召回时走 BM25 加向量再融合，关闭时走向量召回；向量不可用或没有候选时用关键词兜底。之后尝试精排，再用库存、品类、材质、配送、价格等业务条件过滤，最多返回 top_k 个。本轮实际走了哪条路，看 `recall_strategy` 和 `rerank_applied` 两个字段，配置里写了模型名不代表这次真的用上了。空结果有四种可能：没召回、候选被过滤、指定规格缺货、明确的 ID 不存在；只有精确存在性查询才能说「不存在」。被过滤的候选会列在 filtered_out 里，但只是有限摘要，不保证列全。详见[五、完整读一次商品检索用例](#search-5)。

**第六节：页面上的钱是什么口径。** 价格上限检查只比较「选用的规格的商品金额，换算到目标币种后，是否不超过上限」；运费和关税在生成商品卡时才另算成到手价。所以「单件商品价不超过 300，同时展示到手价」和代码一致，「总到手价不超过 300」还需要额外核对，当前过滤没有比较到手价。商品和规格要分清：同一商品的不同规格价格和库存可以不同，卡片默认取第一个有库存的规格，不是最便宜的。到手价按 1 件计算，换规格、数量或目的地都不能沿用旧报价；运费和关税规则是仓库里的简化演示，不是实时报价。详见[六、商品金额、规格与到手价](#price-5)。

**第七节：一个结果，三个出口。** 检索结果返回后，工具补上查询条件和观察时间，再分给三个消费者：完整证据存起来，得到一个取件编号，供以后回查；模型决策视图只放本次推理需要的内容，过大时分页；业务事件把结构化商品交给页面，经状态投影成为「现在应该展示的候选列表」，再经运行日志、SSE 和 CommerceClient 渲染成商品卡。新的普通查询会替换旧候选；合法的空结果会清空；工具出错不会伪装成空结果。页面只格式化后端字段，不自己推算运费和关税。详见[七、一个结果的三个出口与前端展示](#outlets-5)。

**第八节：本轮结束后存了什么。** 会话工作状态、对话流水、商品证据和展示批次、页面的运行日志各存一份，刷新、追问「第二个」和历史回查各取需要的那份。它们不是一个大事务，排查「当时有卡片，刷新后没了」要先找哪份记录没存或没读，通常不是先去改 embedding 模型。详见[八、本轮结束后怎样保存历史](#history-5)。

**第九节：找第一处差异。** 出了问题，按「预期是什么 → 观察到什么 → 进入这个环节时对不对 → 离开时对不对」逐段比，找到第一处不符合预期的数据变化，再判断该补配置、修实现还是修评测。前四篇的方法在这里汇合：01 帮你找模块，02 帮你追调用，03 帮你看状态，04 帮你判断证据够不够。详见[九、按第一处差异定位问题](#debug-5)。

**作业与验收。** 作业 A，从「寄中国、商品价不超过 300 元的轻便背包，同时展示到手价」出发画完整请求图，至少五条箭头写出具体字段；作业 B，按给定的四个候选推演过滤结果，并说明按到手价要求时哪件不合格、该读什么字段；作业 C，八个问题。最终验收覆盖五个阶段：拿一张商品卡反向定位每个字段的来源，再从一句需求正向追到工具、业务过滤、页面和历史，指出哪一步、哪个字段、哪条证据不符合预期。详见[十一、作业](#assignments-5)和[十二、参考答案与最终验收](#answers-5)。

读完导读，按顺序读正文一到九节，再从[作业](#assignments-5)开始动手；最后用[60 秒口述与面试追问](#oral-5)自测。

## 一、这一阶段正在学习项目的什么

**这一节在项目里管什么。** 前四篇各讲一层：地图、循环、状态、评测。05 把四层接到同一条业务链路上，从输入框一直追到商品卡和刷新后的历史。商品检索是能力层最核心的工具，Globex 大部分回答的事实都从它来；这一节先立全篇的主例和主线。

| 要完成的事 | 对应的 Globex 能力 |
| --- | --- |
| 从输入框找到实际请求 | 前端提交与后端 API |
| 从自然语言找到结构化条件 | Agent 工具选择和参数生成 |
| 从工具入口追到商品结果 | 检索、过滤、计价和商品卡构造 |
| 从后端结果追到页面字段 | AG-UI 事件、前端状态和 React 渲染 |
| 从本轮结果追到刷新后的历史 | 运行日志、会话与商品证据 |
| 找到哪里开始不符合预期 | 按数据变化定位问题 |

前四阶段分别提供模块地图、AgentLoop、状态机制和评测方法；第五阶段将它们接起来，完整读懂代表性工具 product_search_tool。

主例：“找一个轻便背包，寄到中国，单件商品价不超过 300 元人民币，同时告诉我加上运费和关税后的到手价。”

对照变体：“总到手价不超过 300 元人民币。”两句话的要求不同，当前代码保障的范围也不同。已在前两阶段补充核验：price_max_major 过滤的是换算后的单件商品金额；税运在后续组装商品卡时才计算。

**放到训练里看。** 这两句话的差别就是 06 整个奖励设计的出发点：代码只保证前一句，买家常说的是后一句，中间的缝里藏着「单件价合格、到手价超预算」的陷阱商品。训练要学的检索决策和奖励要核对的口径，全在这条缝上。

## 三、商品数据怎样准备好

**这一节在项目里管什么。** 检索质量的上限由数据决定。这一节讲商品从哪来（版本化样例目录，不是实时抓取）、索引怎样建（增量、可降级），以及一条容易被忽略的边界：服务能启动，不等于向量检索在工作。

本节学习商品工具实际查询的数据来源。当前本机开发使用版本化 data/catalog-v3.jsonl；加载器还兼容打包目录位置，选择逻辑见 [seed_products.py](../../app/infrastructure/persistence/seed_products.py)。不是每次提问都实时访问多个电商平台抓取商品。

~~~text
版本化商品目录
      |
      v
加载为 Product / SKU 对象
      +-- 商品仓储：提供商品属性与规格
      +-- 持久库存：提供业务库存状态
      |
      v
商品 searchable_text()
      |
      v
embedding 服务生成向量
      |
      v
写入 Qdrant 商品索引
~~~

| 组件 | 人话解释 | 当前承接的数据 |
| --- | --- | --- |
| 商品仓储 | 查询商品业务数据的入口 | 标题、规格、配送、材质等 |
| Embedding 服务 | 把文本变成可比较的向量 | 查询和商品文本的向量表示 |
| Qdrant 索引 | 按向量相似度找候选 | 当前主要返回商品 ID 和相似度 |

Qdrant 找到 ID 后，用例仍回到商品仓储取得商品对象；相似度分数不能代替价格、库存和配送事实。

阅读 [index_bootstrap.py](../../app/infrastructure/vector/index_bootstrap.py)、[qdrant_product_index.py](../../app/infrastructure/vector/qdrant_product_index.py)和 [catalog_search.py 的 _vector_recall()](../../app/application/usecases/catalog_search.py)，分别回答“商品怎样入索引”“索引返回什么”“怎样取回业务对象”。

启动时的建库是增量的（2026-10-19 按当前代码核对）：只给缺失或内容有变化的商品生成向量，并按向量服务、模型和维度算出的身份判断，换了 embedding 模型不会混用旧向量；每 10 件写一批，重启时已写好的直接复用。建库失败不会阻止服务启动，已写入的批次保留，日志提示检索可能降级；只建了一部分时，普通检索仍走向量分支，只是覆盖不全。因此启动成功或 /health 正常，不能单独证明向量索引完整、检索可用。

**放到训练里看。** 06 的训练环境用的就是这一节的兜底路径：商品目录同一份，但没接 embedding 和 rerank，召回全部走 `keyword_2gram`，按 ID 核对仍走精确查找（免费、确定、不依赖外部服务）。所以训练里的候选集和线上不同，规则基线的成绩只在「关键词口径」下成立——换回线上召回后基线要重跑，这条差距写在 06 的边界里。

<a id="params-5"></a>
## 四、前端输入怎样变成工具参数

**这一节在项目里管什么。** 从买家的一句话到一次检索，中间有两道转换：模型把话变成工具参数（策略的事），工具把参数校验成检索规格（代码的事）。02 第二节那个习惯——「模型传对了吗」和「代码按参数执行了吗」要同时检查——在这条缝上看得最清楚。

本节学习用户文本、HTTP 请求与工具参数的转换。[useCommerceAgent.ts](../../frontend/src/hooks/useCommerceAgent.ts)创建 CommerceClient，使用 /commerce/ag-ui/run；后端 [parse_intent()](../../app/presentation/ag_ui.py)把请求转为业务输入。

| 前端请求信息 | 后端含义 |
| --- | --- |
| messages 最后一条用户内容 | 本轮 raw_query |
| threadId | shopping_session_id |
| runId | 本次运行标识 |
| forwardedProps.buyerId | 买家信息，仍需后端校验归属 |
| locale、currency | 地区语言与币种信息 |

~~~text
locale=zh-CN          语言地区
ship_to=CN           商品配送目的地
target_currency=CNY  商品报价目标币种
source_language      商品原文语言
~~~

这几个字段不能互相替代。中文提问不意味着一定配送中国；前端写人民币，也不证明模型已把预算传进商品工具。

模型可能生成以下工具参数。这里只示意参数，不是完整 HTTP 报文或已执行的调用：

~~~json
{
  "normalized_query": "轻便 背包",
  "ship_to": "CN",
  "price_max_major": 300,
  "target_currency": "CNY",
  "top_k": 3
}
~~~

[product_search_tool.py](../../app/application/tools/product_search_tool.py)会处理数字字符串、品类和约束，检查目的地，再构造 [ProductSearchSpec](../../app/domain/catalog/product_search_spec.py)。规格对象检查查询词、top_k 类型与范围，以及金额是否有限、非负。工具现在还有 product_id、sku_id 两个独立参数，用来精确核对某一件商品：传了 ID 时查询词可以为空，工具也不再从查询文字推断品类（普通检索仍会推断）；规格对象会检查 ID 格式，并要求两个 ID 属于同一商品。

~~~text
模型参数
    +-- 数字字符串转数字
    +-- 品类与相关约束处理
    +-- 目的地检查
    |
    v
ProductSearchSpec 校验
    |
    v
CatalogSearchUseCase
~~~

相关性条件与明确过滤条件也要分开。“轻便”写入查询词，会影响检索和后续判断；工具当前没有独立 max_weight_kg 参数，不能仅凭出现“轻便”就声称代码保证某个重量上限。

**放到训练里看。** 这一节的参数表就是动作空间的具体形状：normalized_query、ship_to、price_max_major、excluded_material_tags、product_id/sku_id，每个字段都能填对也能填错。06 的任务集故意让买家说法在收货地、预算、材质上多变，就是逼这组字段的正确取值在训练分布里出现，held-out 再换一套说法检验是理解还是记句式。

<a id="search-5"></a>
## 五、完整读一次商品检索用例

**这一节在项目里管什么。** 这是检索的心脏：候选从哪条路找来、怎样排序、被什么条件排除。空结果在这一节被拆成四种原因——「没找到」在工程上从来不是一句话能说清的。

本节学习候选怎样被找到、排序和排除。[execute()](../../app/application/usecases/catalog_search.py)先判断三个入口分支：

~~~text
execute(spec)
    |
有明确的商品 / SKU ID？（先看 sku_id、product_id 参数，都没传才在查询词里找）
    +-- 有 → 精确查目录
    |          +-- 存在且符合条件 → 商品卡
    |          +-- 存在但不符合条件 → filtered_out
    |          +-- 没找到指定 ID → missing_identifiers
    |
    +-- 无
          +-- Hybrid 开启 → BM25 + 向量 → 融合 → 尝试精排
          +-- Hybrid 关闭 → 向量召回 → 尝试精排
                                   |
                                   +-- 向量不可用或无候选时关键词兜底
~~~

两个 ID 参数同时传时以规格 ID 为准。显式传入的 ID 查不到，结果写进 missing_identifiers，不会退回模糊检索；这样买家说「核对这一件」时，不会被相似的商品顶替。

召回是从大集合找出可能相关的候选，精排是对这批候选做更细的排序。

~~~text
normalized_query → Embedding → 查询向量
    |
Qdrant → 商品 ID + 相似度
    |
商品仓储 → 商品对象
    |
专用 reranker 尝试重排
    |
业务条件检查 → 最多 top_k 个 → 商品卡
~~~

代码可以在一定范围扩大向量候选窗口来补足合格候选，但不等于穷尽全库。普通分支的实际策略可观察以下字段：

| recall_strategy | 含义 |
| --- | --- |
| embedding_rerank | 向量召回且完成精排 |
| embedding_only | 向量候选，未应用精排 |
| keyword_2gram | 关键词兜底 |
| exact_id_lookup | 明确商品或 SKU ID 查询 |

rerank_applied 说明实际有没有精排；配置模型名称不证明本轮已经使用。[精排器装配](../../app/infrastructure/rerank/factory.py)

Hybrid 使用应用层 BM25（词项相关性）与向量召回，再用 RRF 按排名融合。HYBRID_RECALL_ENABLED 配置缺省值关闭；代码存在不证明本次运行启用了它。离线检索评测还可以打开「检索阶段采集」，记录混合召回从 BM25、向量、合并、融合到精排各阶段的候选，用来区分「根本没召回」和「召回了但在排序中丢了」；它不改变排序，普通分支不采集。

~~~text
同一查询
    +-- BM25 词项召回 --+
    +-- 向量召回 ------+
                       |
                       v
              业务资格检查与融合
                       |
                       v
                   尝试精排
                       |
                       v
                  去重与 Top-K
~~~

_reject_reason() 还检查库存、品类、材质、配送等条件。空结果可来自未召回、候选被过滤、指定 SKU 缺货或明确 ID 不存在。只有相应精确存在性查询才能支持“不存在”；普通语义检索未命中不够。

filtered_out 是有限拒绝摘要，不保证列全；total_candidates 是当次分支统计，不是商品目录总数。

**放到训练里看。** 检索结果的结构化字段——hits、filtered_out、missing_identifiers、recall_strategy——都是策略收到的观察，要原样进轨迹。奖励核对只认 hits 里的商品事实，不认模型回答里的自述（06 补强版判「编造」用的就是「推荐的 ID 必须在本轮 hits 里出现过」）；被过滤掉的候选也是策略能利用的信息：知道什么被滤掉、为什么，才学得会换参数重查。

<a id="price-5"></a>
## 六、商品金额 规格与到手价

**这一节在项目里管什么。** 全项目最容易讲错的一个口径：价格上限比较什么、到手价怎样算、什么时候算。前面几篇反复提醒「单件价合格不等于到手价合格」，机制就出在这一节的两段代码之间。

本节学习页面金额的实际口径。[CatalogSearchUseCase._within_price_cap()](../../app/application/usecases/catalog_search.py)的逻辑是：

~~~text
选择用于判断的 SKU
    |
商品金额换算为 target_currency
    |
比较商品金额 <= price_max_major
~~~

之后 _to_card() 才另外计算税运：

~~~text
SKU 商品金额
    |
项目内税运规则
    |
商品小计 + 运费 + 关税
    |
landed_price.landed_total_major
~~~

主例“单件商品价不超过 300，同时展示到手价”与当前代码结构相符；“总到手价不超过 300”还需额外核对。当前过滤没有比较 landed_total_major 与上限。本次只澄清实现范围，没有修复这项业务缺口。

Product 表示商品，SKU 表示具体规格，例如颜色和容量，价格与库存可以不同。当前 [primary_available_sku()](../../app/domain/catalog/product.py)取列表中第一个有库存的规格，不能解释成全商品最便宜的规格；明确请求 SKU 时，精确查询按那个规格检查。

| 字段 | 含义 |
| --- | --- |
| price_major、currency | 当前默认或指定规格商品金额，已换为目标币种 |
| source_price_major、source_currency | 原始报价 |
| skus[].price_major、skus[].currency | 各 SKU 原币报价 |
| default_sku_id | 这张卡当前采用的规格 |
| landed_price.landed_total_major | 本次计算到手价 |

商品卡税运调用当前传 quantity=1。换规格、数量或目的地不能直接沿用旧报价。[TariffSchedule](../../app/domain/shipping/tariff_schedule.py)是仓库里的简化演示规则，不能当作实时海关或物流报价。

**放到训练里看。** 「过滤在先、计价在后」这两段代码的顺序，就是 06 陷阱商品的机制出处：单件价不超过预算的商品能通过过滤，到手价却可能超。06 的补强版奖励不复用这两段代码的判断，而是用独立判定按 landed_total_major 逐件重算——奖励的口径必须对齐买家的要求，而不是对齐工具的实现。

<a id="outlets-5"></a>
## 七、一个结果的三个出口与前端展示

**这一节在项目里管什么。** 同一次检索，三个消费者要的东西不同：证据要完整、模型要够用、页面要好看。一份结果拆成三份形态，是「不丢、不塞、不混」的解法——02 讲过页面不是事实来源，这一节从数据侧把三个出口彻底分开。

本节学习同一批商品怎样分别服务模型、页面和证据回查。用例结果返回后，工具层补 query_conditions、observed_at，保存完整依据，并交给不同消费者：

~~~text
CatalogSearchUseCase 返回 result
                |
product_search_tool 补查询条件和观察时间
                |
       +--------+------------------+------------------+
       |                           |                  |
       v                           v                  v
完整证据存储                 模型决策视图           业务 tool.result
result_ref                   ToolChunk              hits、策略等
       |                           |                  |
       v                           v                  v
后续引用回查                 Agent 继续判断          AG-UI 适配器
~~~

完整证据用于保存依据，下单时也用它核验：订单工具只接受本会话检索返回过的商品和规格，模型不能凭空编一个 ID 去下单。模型视图限制本次推理所需内容，过大结果可能分页；业务事件把结构化展示信息交给前端链路。[工具结果处理](../../app/application/tools/product_search_tool.py)

~~~text
业务 tool.result
    |
ProductCandidateProjection
    |
AGUIRunAdapter 更新 state.products
    |
持久日志 → SSE → AG-UI Client
    |
CommerceClient.onStateChanged()
    |
readProducts(state.products)
    |
React 更新 ProductCards
~~~

状态投影是把执行过程中的结果整理为“现在应该展示的候选列表”。当前 [ProductCandidateProjection](../../app/application/agents/product_candidate_projection.py)用新普通查询替换候选；合法 hits=[] 会清空；没有 hits 的错误不会伪装成空检索；明确多个商品 ID 的精确查询才有专门的跨结果合并。

用户换条件后，旧商品未必符合本轮，不能无限追加。[ProductCards.tsx](../../frontend/src/components/ProductCards.tsx)分别展示商品价和到手价，主要格式化后端字段，不从模型文字自行推算税运。事件适配与接收见 [ag_ui_adapter.py](../../app/application/agents/ag_ui_adapter.py)和 [commerceClient.ts](../../frontend/src/lib/commerceClient.ts)。

合并上游后，页面成了一个「选购工作台」，分「选购对话」和「执行记录」两个标签页，输入框旁可以选模型、看上下文用量。执行记录显示主 Agent 的工具调用和模型公开返回的思考内容，随运行日志保存，刷新后能恢复。检索这一步只显示商品或规格 ID、配送国、币种、预算上限和件数，不显示查询词和召回策略；子 Agent 内部的检索只显示为一行派发。所以执行记录里显示「已完成」，不能说明检索成功或需求已满足，判断仍要看商品卡和工具结果。

**放到训练里看。** 三个出口只有「模型决策视图」进轨迹——它是策略实际看到的观察，包括投影和截断（[02 第三节](02_AgentLoop与子Agent派发.md#call-id-2)）。奖励核对站在「完整证据」一边，但比它更进一步：06 的独立判定回到商品数据按到手价重算，而不是复用工具存下的结果；页面那一路与训练无关。

<a id="history-5"></a>
## 八、本轮结束后怎样保存历史

**这一节在项目里管什么。** 一轮结束不是什么都留、也不是什么都不留：会话、对话、证据、日志各存一份，各自的消费者不同。这一节讲清谁存什么、谁取什么——排障「刷新后没了」先查这里，而不是先怀疑模型。

编排器收尾保存会话、对话及商品证据；运行日志保存已产生的消息与状态投影，后续追问和刷新恢复各取合适记录。[orchestrator.py](../../app/application/agents/orchestrator.py)

~~~text
本轮商品与回答
    +-- AgentState：会话工作状态
    +-- 对话流水：买家输入和最终回答
    +-- 商品证据 / display_batch：候选与顺序
    +-- AG-UI 日志：页面消息和事件
                  |
                  v
        刷新 / 比较第二个 / 历史回查
~~~

这些存储不是一个无边界的大事务。排查时要找到哪份记录未保存或未读取。“当时有商品卡，刷新后丢失”应先查持久日志、历史接口和前端恢复，通常不是先改 embedding 模型。

**放到训练里看。** 06 的奖励核对「本轮检索到过什么」，用的口径和证据存储一致：从工具结果里取 hits 的商品 ID（`seen_ids`），推荐里出现没见过的 ID 就按编造记 -1。训练轨迹本身不靠这些落库记录拼装——消息序列是运行时直接写的（[03 第六节](03_Harness与状态管理.md#recovery-3)）。

<a id="debug-5"></a>
## 九、按第一处差异定位问题

**这一节在项目里管什么。** 前四篇的方法在这一节汇合成一个排障流程：不猜、不跳，逐段比「进入时对不对、离开时对不对」，找到第一处不符合预期的数据变化再动手。它也是 06 归因方法的前身——run-01 的三条原因，每条都是先找到第一处差异（奖励曲线和核验曲线分叉、clipfrac 恒零、held-out 追问率不降）才定下来的。

| 现象 | 优先检查 |
| --- | --- |
| 页面打开但消息失败 | 请求有没有到后端、配置、运行错误 |
| 只有选购知识没有商品 | 是否调用 product_search_tool |
| 声称没有商品 | 未召回、过滤、错误还是精确 ID 不存在 |
| 候选多但排序差 | 实际 recall_strategy、rerank_applied，再查召回与精排 |
| 商品价合格而到手价超预算 | 预算口径与 _within_price_cap 的比较字段 |
| 后端结果正确但卡片错误 | 业务事件、投影、AG-UI 状态、readProducts、组件 |
| 新查询为空仍显示旧候选 | 合法空结果、投影替换、状态应用 |
| 刷新后商品或顺序变化 | 日志、历史接口、展示批次和恢复 |

~~~text
预期是什么？
    |
观察到什么？
    |
输入这个环节时是否正确？
    |
离开这个环节的输出是否正确？
    |
找到第一处不符合预期的数据变化
    |
判断补配置、修实现还是修评测
~~~

第一阶段帮助找模块，第二阶段帮助追调用，第三阶段帮助看状态，第四阶段帮助判断证据是否足够。最后阶段让这些方法服务同一条业务链路。

## 60 秒口述与面试追问

**60 秒口述。** 商品检索是 Globex 最核心的工具。数据来自版本化的样例目录，加载成商品和规格，增量建成 Qdrant 向量索引；索引只给候选 ID，价格、库存、配送这些事实总是回到商品数据里取。模型生成的参数先校验成检索规格，检索用例按三条路找候选：有明确 ID 就精确查目录，否则走混合召回或向量召回，向量不可用时关键词兜底；之后尝试精排，再用库存、配送、材质、价格过滤，最多返回 top_k 个。最容易讲错的是金额口径：价格上限只比较单件商品价，到手价按 1 件另算，所以「总到手价不超过 300」需要额外核对。一个结果有三个出口：完整证据供回查和下单核验，决策视图交给模型，业务事件经状态投影和 SSE 变成商品卡；刷新靠各自保存的记录恢复。放到训练里看，检索返回的结构化事实既是策略的观察，也是奖励的依据，奖励必须自己核对总价。

**面试追问。**

| 追问 | 答题要点 |
| --- | --- |
| 向量检索已经命中，为什么还要查商品仓储？ | 相似度只是候选线索；价格、库存、配送、规格必须来自业务数据 |
| 检索返回空，能说「没有这个商品」吗？ | 不能，可能是没召回、被过滤或缺货；只有精确的存在性查询才能说不存在 |
| 怎么知道这次有没有用上精排？ | 看本轮结果里的召回策略和是否精排两个字段，配置里写的模型名不算数 |
| 传了价格上限 300，就能保证总价不超过 300 吗？ | 不能。只比较单件商品价，运费和关税在商品卡里另算，而且按 1 件计算 |
| 要训练检索相关的决策，奖励怎么算？ | 以结构化结果为准：推荐的商品是否满足全部硬约束，包括按数量算的到手价；有没有把被过滤的候选当推荐；不看模型文字的自述 |
