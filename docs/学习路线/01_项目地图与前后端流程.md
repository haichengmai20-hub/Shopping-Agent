# 第一阶段 项目地图与前后端流程

本阶段先回答一个问题：**沿着一条选购请求，Globex 的各部分为什么存在、谁调用谁、传递什么、结果怎样回到用户？**

本章遵循[时间紧张版教程导读](../../docxs/Globex_教程导读_时间紧张版.docx)的 Step 1：约 30 分钟阅读，另用 15～20 分钟完成纸笔作业。当前讲解对应本地源码提交 8cbd4d6b94eb9713952d3bd8f050da176accdca1；工作区另有未提交的本机环境准备改动。本阶段是源码学习，不要求启动模型服务。

学完后应能：用两三句话解释项目目标和现有业务边界；分开画出服务启动与一次请求处理；说清 Model、Agent、AgentLoop、Harness 的分工；遇到问题时知道先定位前端、接口、Agent、工具还是存储。商品检索算法、Agent 循环内部、上下文治理与订单事务留给后续阶段。

## 一、用一个选购请求建立项目问题

贯穿本阶段的例子是：

> 帮我找一件轻便背包，寄到中国，总到手价不超过 300 元人民币。

| 用户提供的信息 | 系统需要做什么 | 当前项目从哪里取得依据 |
| --- | --- | --- |
| 背包、轻便 | 理解目标，形成检索词或选购条件 | 模型决策与商品检索 |
| 寄到中国 | 检查候选是否可配送 | 商品数据与业务过滤 |
| 总到手价不超过 300 元人民币 | 按项目规则计算和过滤 | 报价、运费、关税与汇率规则 |
| 帮我找 | 组织候选并说明理由 | Agent 综合工具返回的信息 |
| 下一轮说“比较前两个” | 找回上一轮候选和会话信息 | 持久会话及商品证据 |

这里的 Model（模型）负责理解需求、生成下一步行动或回答；业务工具和用例提供可核查的商品事实与约束结果。当前项目使用版本化样例商品目录和本地订单账本，尚未接入真实电商供给、支付或物流。这里的“到手价”是根据项目现有数据和规则计算的结果。项目边界见[README](../../README.md)开头及“项目状态”。

**预算口径补充（2026-10-03 核验）：** 当前 [CatalogSearchUseCase._within_price_cap()](../../app/application/usecases/catalog_search.py)过滤的是目标币种下的单件商品金额；运费、关税在 _to_card() 中另行计算为 landed_price。因此本章场景中的“总到手价不超预算”是需要检查的任务要求，不能直接当作已经兑现的硬过滤保证。

试着先填一句：Globex 是一个______；买家输入______；系统通过______；最后返回______。把输入、查证过程和输出说完整即可。

## 二、Model、Agent、AgentLoop、Harness 各是什么

| 概念 | 在本项目中的职责 | 人话 |
| --- | --- | --- |
| Model，模型 | 根据当前输入生成文本或工具调用 | 做当前一步的判断 |
| Agent，智能体 | 组合模型、提示词、工具和状态；本项目的 MainAgent 是主角色 | 带着工具和工作记录执行任务 |
| AgentLoop，智能体循环 | 决策、执行、观察结果，再决定是否继续或收尾 | 查一次不够就继续查，信息足够就回答 |
| Harness，运行支撑机制 | 权限、状态、预算、超时、恢复、观测等工程能力 | 让循环可控、可追踪、能恢复 |

~~~text
Harness：权限、状态、超时、恢复、观测
    |
    +-- 支撑 Agent 运行
            |
            +-- Model：决定下一步或生成回答
            +-- Tools：执行检索、查询、准备订单等动作
            +-- State：保存当前工作的上下文与进度
                     |
                     +-- 多次决策与观察形成 AgentLoop
~~~

Think → Act → Observe → Reflect 是理解循环的教学拆分，不意味着代码中有四个独立服务，也不意味着每轮必须额外调用一次“反思模型”。需要补概念时，读[01 AgentLoop 核心概念](../../docxs/01_AgentLoop范式与电商搜索Agent核心概念.docx)第 2、5 节。

本项目还需要分清两个名字。MainAgent 负责一次选购中的模型与工具决策；MainAgentOrchestrator（业务编排器）负责让一次请求进入 Agent、组织会话和本轮输入、消费执行事件并处理收尾。编排器的职责是安排这一轮业务怎样运行，不是代替模型判断哪款背包合适。

## 三、前端与后端怎样合作

前端是浏览器里的 React 页面，负责接收买家输入和呈现文字、商品卡、进度、确认卡。后端是 Python 服务，负责校验请求、运行 Agent、访问商品与数据库、执行业务规则。浏览器看到一张商品卡，并不等于商品事实由浏览器计算；页面主要根据后端返回的结构化事件渲染。

把本机的两个端口想成两个窗口。5173 是 Vite 开发服务器：把前端页面和 JavaScript 交给浏览器；8000 是 Uvicorn 承载的 FastAPI 后端：接收业务请求并运行 Python 代码。开发时，[vite.config.ts](../../frontend/vite.config.ts) 会把浏览器发往 5173 的 /commerce 等请求转给 8000，这个转送叫代理。端口指本机服务的入口号，不能把 5173 和 8000 当作两个模型。

~~~text
浏览器中的 React 页面
    |
    | 买家点击发送；前端组织 HTTP 请求
    v
Vite 开发服务：127.0.0.1:5173
    |
    | 把 /commerce 请求代理到后端
    v
Uvicorn + FastAPI：127.0.0.1:8000
    |
    | 调用业务编排器、Agent、工具和存储
    v
模型服务、商品目录、数据库等后端依赖
    |
    | 本轮产生的事件经后端持久日志与 SSE 逐步送回
    v
浏览器更新文字、商品卡和进度
~~~

API（应用程序接口）是前后端约定的请求地址、输入和输出形式。例如当前页面使用 POST /commerce/ag-ui/run：POST 表示前端向后端提交本轮输入，接口代码先校验、解析，再把请求交给运行管理器。SSE 是在 HTTP 连接上连续把事件发回浏览器的方式。AG-UI 约定事件类型与字段；它们让页面逐步显示文本和工具进度。

前端可以携带本轮输入和显示状态；后端会重新核对买家、会话与业务事实。[parse_intent](../../app/presentation/ag_ui.py)只取最后一条用户文本作为本轮问题，不能直接把浏览器传来的旧回答当成可信历史。后端运行日志保存已产生的事件，刷新后可以按游标继续读取。第一阶段先理解“事件从哪里来、页面据此显示什么”，恢复细节留到第三阶段。

## 四、第一条线：服务启动时怎样接线

~~~text
启动后端进程
    |
    v
加载 app/presentation/server.py
    |
    +-- 创建 FastAPI 应用、注册接口
    |
    v
执行应用启动流程 lifespan
    |
    v
app/composition.py：build_container()
    |
    +-- 读取配置
    +-- 创建模型、检索、数据库相关对象
    +-- 创建 MainAgentFactory
    +-- 创建 SessionRegistry
    +-- 创建 MainAgentOrchestrator
    +-- 创建 AGUIRuntime

    |
    v
~~~

FastAPI 是项目声明 HTTP 接口的框架，Uvicorn 是运行该 Python Web 应用的服务器。Container 是项目保存已装配组件的 Python 对象；它与 Docker 容器不是一个概念。Factory（工厂）是创建对象的代码：MainAgentFactory 保存组装 MainAgent 所需的依赖，具体会话的 Agent 在请求处理阶段取得或创建。

先打开[server.py 的 lifespan](../../app/presentation/server.py)寻找 build_container() 和 c.startup()，再打开[composition.py 的 build_container](../../app/composition.py)。长函数第一遍只看右边创建了什么、左边变量传给了谁。当前源码能看到如下接线：

~~~text
SearchAgentFactory + TradeAgentFactory + 其他依赖
                         |
                         v
                 MainAgentFactory
                         |
                         v
                   SessionRegistry
                         |
                         v
                MainAgentOrchestrator
                         |
                         v
                    AGUIRuntime
~~~

这些箭头表示“作为依赖交给下一个对象”，不表示每个用户请求都会重新创建它们，也不表示每次选购都派发两个子 Agent。目录中有一种实现，只说明它的代码存在；看当前实际使用哪一种实现，要到 composition.py 查接线。

## 五、第二条线：一次买家请求怎样走完

下图是当前网页的主要运行路径。订单审批、故障恢复与具体检索算法将在后续阶段展开。

~~~text
买家在 React 页面输入背包需求
    |
    | 用户文本、买家信息、会话 ID、本次运行 ID
    v
POST /commerce/ag-ui/run
    |
    | 解析本轮输入、校验身份和会话
    v
AGUIRuntime
    |
    | 登记 run，启动这一轮执行
    v
MainAgentOrchestrator
    |
    +-- SessionRegistry：取得或恢复会话的 Agent
    +-- 组织本轮输入和相关信息
    +-- 消费 agent.reply_stream(...) 的事件
                    |
                    v
                MainAgent
                    |
                    | 选工具并给出参数
                    v
          product_search_tool
                    |
                    | 结构化商品检索条件
                    v
          CatalogSearchUseCase
                    |
                    | 查询商品与检索能力，执行业务过滤
                    v
                检索结果
                    |
           +--------+--------------------------+
           |                                   |
           | 工具返回的观察结果                | 商品等结构化事件
           v                                   v
       回到 Agent                         事件适配与持久日志
           |                                   |
           | 继续判断或生成回答                | SSE
           v                                   v
       最终回答及相关事件 ----------------> 前端展示

业务回合收尾：按各自职责保存 AgentState、对话及有关证据。
~~~

这张图的关键是两条返回路径：工具结果返回 Agent，成为后续判断的依据；结构化事件返回页面，让用户看到商品卡与执行进度。一次搜索也可能没有符合条件的商品；图只表示执行路径，不预设命中数或成功回答。

MainAgent 也可以按需调用 task_dispatch，把子任务交给 SearchAgent 或 TradeAgent。简单商品检索时，它可以直接调用 product_search_tool。下一阶段再分析什么时候派发、子 Agent 看得见什么，以及同轮多派怎样并行。

此处还可先认识三个标识：buyer_id 表示服务哪位买家；shopping_session_id 表示哪段对话；run_id 表示这段对话中的哪一次运行。一个买家可以有多个会话，一个会话可以包含多轮运行。浏览器刷新时，这些标识帮助它找回自己的已保存内容。

### 作业二参考答案

**Q1。** Globex 是对话式购物 Agent：买家描述需求后，它可组织商品检索、比较和交易确认。当前商品来自版本化样例目录，订单记录和库存操作在本地账本中；真实电商供给、支付与物流尚未接入。因此演示流程中的“下单”不等于真实平台付款。

**Q2。** Model 根据输入生成工具调用或回答；MainAgent 持有模型、提示词和业务工具，在当前任务中决定下一步；MainAgentOrchestrator 取得会话、组织本轮消息、调用 Agent 并处理事件和持久化。Harness 的一个例子是工具超时：即使模型选择了某个工具，工程代码也要限制等待时间，避免整轮任务无限挂起。

**Q3。** 同一个已启动的后端进程先装配组件，再接收多次请求，所以第二条消息不要求重跑整个 build_container。第二轮进入编排器后，由 SessionRegistry 根据 shopping_session_id 取得或恢复会话 Agent；必要时还会读回候选证据。进程重启则会重新装配服务组件，但保存的会话与业务数据仍按存储路径恢复。

**Q4。** 模型可以理解“200 元内”并生成检索条件，但不能凭自然语言承诺认定某款商品符合预算。商品身份、报价、库存、配送范围，以及按项目规则计算的到手价，需要以商品数据和业务用例的结果为依据。结构化过滤还能区分“没有找到”与“找到了但超预算”。

**Q5。** product_search_tool 是模型可调用的一项明确能力，其内部把参数交给 CatalogSearchUseCase；SearchAgent 是另一个带模型和工具的 Agent，可以围绕一个检索子任务自行循环。MainAgent 已持有商品工具，这条简单检索可以由它直接完成。需要并行任务、上下文隔离或较深的子任务链时，才考虑派发 SearchAgent。

**Q6。** 工具结果回到 Agent，Agent 才能据此继续比较、调整检索或生成有依据的回答。检索事件进入前端链路后，页面才能显示商品卡和执行进度。只有 Agent 回路，页面可能缺少及时的结构化展示；只有页面事件回路，Agent 无法利用观察结果完成后续判断。
