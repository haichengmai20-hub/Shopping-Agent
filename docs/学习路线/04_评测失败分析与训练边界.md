# 第四阶段 评测 失败分析与训练边界

本阶段学习 Globex 怎样判断一次选购任务有没有做好、怎样定位失败，以及怎样判断一次改动是否值得保留。建议用约 45 分钟学习，再用 20～25 分钟做图和答题。正文以此前页面稿及本地源码提交 8cbd4d6b94eb9713952d3bd8f050da176accdca1 为依据；历史结果带日期和版本边界，教学计算不当作真实运行。

## 一、你正在学习项目里的什么

| 项目问题 | 本阶段的方法 |
| --- | --- |
| 推荐的商品是否违反预算、配送要求 | 把需求变成可检查的条目 |
| Agent 说调用过工具，实际上调用了吗 | 核对工具事件 |
| 用户批准前是否已创建订单 | 对照事件顺序、确认接口和持久结果 |
| Prompt 改动是否确实改善表现 | 固定任务、版本和条件做比较 |
| 一批用例有网络错误，成功率怎么算 | 保留错误状态，明确分母 |
| 怎样避免同一坏例重复发生 | 留证据、审核原因、补回归 |
| 日志能否直接拿去 SFT/RL | 核对轨迹、监督目标和算法所需信息 |

~~~text
明确要评的任务
    |
准备固定输入与判断标准
    |
运行 Globex，收集回答、工具事件和业务结果
    |
    +-- 程序能核对的事实 --> 确定性断言
    +-- 需要语义判断的内容 --> Judge
                          |
                          v
                  校验、评分和通过条件
                          |
                          v
                    报告 + manifest
                          |
                          v
                  Bad Case 审核与归因
                          |
                          v
              修工具 / 状态机制 / Prompt / 用例
                          |
                          v
                   固定条件重新评测
~~~

Case（用例）是具体输入、条件和要求；Rubric（评分细则）列出针对任务的检查项；Judge（评委）在这里主要是根据细则评判的模型；Trace（执行记录）记录任务中的调用、结果与相关事件。

## 二、从 agent-001 看检查覆盖什么

打开 [agent_cases.yaml](../../eval/v1/agent_cases.yaml)，第一条 agent-001 的问题是“我需要旅行装备，请推荐一件可寄到 CN 的现货”。下面摘出其评分部分，省略其他元数据：

~~~yaml
queries:
  - 我需要旅行装备，请推荐一件可寄到 CN 的现货。
rubric:
  p0:
    - 不得编造商品、价格、订单或政策事实
  p1:
    - 程序断言：调用该场景所需工具
  p2:
    - 回复清晰并说明边界
deterministic:
  p1:
    - criterion: 程序断言：调用该场景所需工具
      kind: required_tools
      tools:
        - product_search_tool
~~~

required_tools 检查事件中出现了所需工具的调用。它支持“记录到了商品搜索调用”，不能单独证明搜索成功、全部约束成立或推荐正确。[断言实现](../../scripts/eval/evidence.py)

读评测时始终问：这条断言读哪个字段，通过后究竟证明什么？例如以下教学数据均为人民币：

~~~text
商品标价 180 + 运费 50 + 关税 10 = 到手价 240
用户要求：总到手价不超过 200

检查商品标价：180 <= 200       通过
检查加总一致：180+50+10=240    通过
检查到手预算：240 <= 200       不通过
~~~

当前 product_hits 的预算检查读 price_major；landed_price_consistency 检查小计、运费、关税与总价相加是否一致。这些检查不能替代对总到手上限、币种、数量和配送条件的完整核对。

源码进一步显示，应用侧 CatalogSearchUseCase._within_price_cap() 也比较换算后的单件商品金额；_to_card() 随后才计算并附上 landed_price。因此“存在结构化预算过滤”不能被解释为“总到手预算已经硬性过滤”。第五阶段会沿这条实际路径展开。[当前过滤与商品卡实现](../../app/application/usecases/catalog_search.py)

## 三、评测脚本怎样调用后端

真实网页走 AG-UI/SSE；当前回归脚本则调用 /commerce/intents，并订阅 /commerce/events 的 WebSocket 业务事件。两条路径共享核心业务处理，但入口和客户端行为不同。

~~~text
浏览器 React + AG-UI Client            Python 评测客户端
            |                                  |
   /commerce/ag-ui/run                  /commerce/intents
            |                                  |
       AG-UI 运行入口                     业务接口入口
            +----------------+-----------------+
                             |
                             v
                   MainAgentOrchestrator
                             |
                             v
                       Agent 与工具
                  +----------+----------+
                  |                     |
                  v                     v
       AG-UI / SSE → 页面      回答 + WebSocket 业务事件
                                          |
                                          v
                                      断言与 Judge
~~~

HTTP 客户端是发送网络请求的程序；浏览器和 Python 都可以充当客户端。评测脚本不必打开 React 页面，就能测试部分后端行为。[评测执行入口](../../scripts/eval_regression.py)中的 _run_case_with_events() 与 SessionEventCollector 分别负责请求与事件采集。

对应边界也要清楚：后端用例通过不能证明商品卡显示正确；确认接口通过不能证明页面按钮可用；旧接口采集通过不能证明 AG-UI 的刷新恢复通过。一些订单用例通过 HTTP 模拟用户批准，再重读订单，它们没有真实点击浏览器按钮。

## 四、确定性断言与 Judge 的分工

| 检查目标 | 优先看的证据 |
| --- | --- |
| 有没有调用某工具 | tool.invoke 等调用事件 |
| 确认前是否已经创建订单 | 确认、订单快照及事件顺序 |
| 批准后是否创建了对应订单 | 确认响应与重读的持久订单 |
| 数值加总是否一致 | 结构化数值 |
| 推荐理由是否清楚、解释了取舍吗 | Rubric 配合模型或人工评价 |
| 回答是否编造事实 | 商品事实与本轮工具结果；可结构化部分优先程序检查 |

~~~text
用例 Rubric
    |
    +-- 已配置确定性断言的条目 --> 检查 trace 与业务事实
    |
    +-- 剩余条目 --> 回答、事实、细则交给 Judge
                                |
                                v
                          校验 Judge 输出
                                |
                                v
          合并程序和 Judge 判断，计算分数与最终结论
~~~

build_judge_rubric() 会从评委输入中移除已由程序检查的条目；apply_trace_evidence() 合并结果，避免模型再次随机裁决同一项已核对事实。[评分合并代码](../../scripts/eval_regression.py)

Judge 读取买家与 Agent 对话、商品事实表、本轮工具事实及用例声明的前置事实。动态库存、到手价和订单状态应对照本轮工具结果；静态目录或模型常识不能代替它们。

[contracts.py](../../scripts/eval/contracts.py)要求每个评分条目恰好出现一次，pass 必须是布尔值，理由中的明确结论与 pass 一致。漏判、缺字段和重复条目不能默认为通过。

还要区分两种一致性：

~~~text
固定 Judge 输出 + 固定 trace，重复走评分代码
    --> 检查程序评分是否稳定

重新请求 Judge 多次，比较其判断
    --> 检查模型评委的一致性
~~~

verify_fixed_trace_stability() 主要做前一种；它不单独证明新请求的 Judge 判断稳定或与人工一致。

## 五、分数与通过条件

这里的 P0/P1/P2 是用例评分层级。教程以它们表示业务红线、执行规范和质量要求；实际条目以用例为准。当前 score_case() 计算各层通过比例后加权：

~~~text
总分 = 0.50 × P0通过比例
     + 0.35 × P1通过比例
     + 0.15 × P2通过比例

单条 PASS 还要求：
P0 全通过
且配置为确定性检查的 P0/P1 全通过
且总分 >= 0.7
~~~

例如 P0 两条只过一条，P1 两条全过、P2 一条全过，则分数为 0.25+0.35+0.15=0.75，但因 P0 没全过仍 FAIL。[score_case 与门禁实现](../../scripts/eval_regression.py)

分数是汇总，门禁是接受条件。此 runner 的成功退出要求选集非空且全部用例 PASS；代码或数据在运行期间变化时也会影响最终接受结论。单条 PASS 不能代替整批通过。

第 08 章描述了动态生成 Rubric 的方案，而当前 runner 读取 YAML 中预先写好的细则。文档方案不自动等于已经执行的代码路径。

## 六、读成功率、成本与 manifest

分母先于百分比。假设选中四条任务，状态为 PASS、PASS、FAIL、ERROR，则当前任务成功率为 2/4=50%。不能排除 ERROR 后改算 2/3；ERROR 和业务 FAIL 保留不同分类，但都不是成功。[metrics_evidence.py](../../scripts/eval/metrics_evidence.py)

| 字段 | 当前代码的范围 |
| --- | --- |
| task_success_rate | PASS 数 / 全部选中用例数 |
| hard_constraint_pass_rate | 按 P0 全过统计，不表示全部可能业务约束均覆盖 |
| latency_p95_ms | 用例耗时 P95，当前口径排除 Judge |
| input_tokens、output_tokens | 所需业务回合 usage 完整时才给完整汇总 |
| cost_usd | 成本信息完整才汇总，否则未知 |

usage 缺失不能填零。Agent LLM 的计量也不自动包含 embedding、reranker、Judge 等全部外部费用。[指标与 BadCase 口径](../指标与BadCase闭环.md)

一次历史练习：[2026-09-09 Agent 原始 manifest](../../eval/verification/release-20260909/agent/agent-release-report-20260909-132421-803890.manifest.json)中选中 30 条、27 PASS、3 ERROR，整批 gate 为 BLOCK。该次成功率为 27/30=90%；这是那个冻结范围的历史结果，不是今天重跑的成绩。

Manifest 可以理解成“一次评测的运行清单”：哪些 case、哪个 split、哪份代码和数据、哪些 Prompt、模型配置与观察到的降级、用例结果和失败证据。配置的模型名称不单独证明远端实际版本完全相同。[run_manifest.py](../../scripts/eval/run_manifest.py)

~~~text
报告分数
    +-- 选集：哪些 case，dev / release / all？
    +-- 代码：版本、dirty 状态、内容指纹？
    +-- 输入：数据、Prompt、基线？
    +-- 运行：模型配置、实际策略、失败记录？
~~~

dev 用于观察失败并修改；release 对固定方案做发布前检查；--only 缩小到个别用例后属于局部诊断；--dry-run 只检查选集与清单，状态为 NOT_RUN。真实比较需要相应条件可比，局部通过不代表完整发布范围通过。[正式选集规则](../正式评测选集与证据清单.md)

## 七、Bad Case 怎样成为可验证的改进

若模型把“未召回”说成“商品不存在”，先区分：目录真没有、检索漏了、工具已经返回但模型误读，还是 Judge 误判。不同原因需要不同修复。

~~~text
结果及 manifest
    |
Bad Case 候选，保存报告来源 / hash / case ID / 分类
    |
人工核对证据
    +-- rejected：记录原因
    +-- accepted
            |
            v
        导出新的回归提案
            |
       补可判定条件、审核 fixture 与选集归属
            |
            v
       另行纳入合适的回归或评测集
~~~

Fixture 是测试需要的固定输入或环境材料，gold 是经审核的参考答案或标注。accepted 候选不会自动覆盖正式数据；当前导出提案仍要求后续审核，official_dataset_changed 为 false。[feedback.py](../../scripts/eval/feedback.py)

这一部分主要是离线工具，产生报告、manifest、分数发件箱和待审核记录。出现一个分数不会自动改写买家网页回答或训练模型。

## 八、评测 Prompt 优化 SFT 与 RL 分别改什么

在当前 app、scripts 和依赖中找到的直接实现包括评测、Bad Case 管理及离线 Prompt/Skill 优化，未找到对应 SFT/GSPO 权重训练入口及可关联的冻结实跑证据。08 系列在这里用来理解及设计训练扩展。

| 工作 | 改变什么 | 学习目的 |
| --- | --- | --- |
| 评测 | 判断与证据 | 知道系统做得怎样 |
| 工程修复 | 工具、检索、状态或权限代码 | 修具体原因 |
| Prompt/Skill 优化 | 给模型的指令文本 | 改调用方式和行为引导 |
| SFT | 模型参数 | 从审核后的示范学习动作 |
| Agentic RL | 模型参数 | 根据环境交互与奖励改善策略 |

[optimize_prompts.py](../../scripts/optimize_prompts.py)用 GEPA 优化文本；不是 SFT/RL 权重训练。[历史 GEPA 记录](../改动记录/2026-09-18/GEPA离线优化.md)明确保留了未得到优于基线候选的结果。

Trajectory（轨迹）是输入、模型动作和环境观察的顺序记录：

~~~text
用户需求
    |
assistant 工具调用    <-- 要学习的模型行为
    |
tool 商品结果        <-- 环境观察，供后续决策
    |
assistant 继续调用或回答 <-- 要学习的模型行为
~~~

Loss mask（损失掩码）决定哪些 token 参与训练目标。这套 Agent SFT 设计中，已有轨迹的 assistant 输出作为监督目标；system、user、tool observation 提供上下文，通常不作为要求模型生成的答案。只存最终问答会丢掉工具决策，仅有业务事件日志也不保证具备完整训练消息和 token 对齐。

~~~text
可重置任务与环境
    |
当前策略执行，采集 rollout
    |
记录动作、观察、版本、终止原因
    |
计算 reward，保留算法需要的采样信息与 mask
    |
更新策略参数
    |
独立固定任务重新评测
~~~

Rollout 是策略实际执行任务的采样过程，reward 是评价行为结果的训练信号。未来训练还需明确动作 token、mask、采样概率信息、策略版本与终止语义；工具录制回放也需要处理新参数没有对应历史返回的情形。有评分不等于完整训练数据，有日志不等于实现 RL 环境，训练奖励上升不单独证明独立任务质量提高。

### 作业 B 参考答案

缺少按用户币种、数量、配送地和费用范围核对总到手上限。本例加总正确，但 240 大于 200。应检查断言读的实际字段，补“标价合格、到手超预算”的固定样例并保留原始失败。不能用去掉运费、提高预算或删除失败样例的方式获得通过。

### 八题答案

1. 不能。required_tools 只支持调用被记录。还需核对候选、到手总价及币种、数量、配送等条件。
2. FAIL。分数超过阈值，但 P0 没有全部通过。
3. 不能。漏条目或结论冲突违反评分合同，应进入相应错误处理。
4. 不能。只能证明固定输入经本地评分代码稳定；新 Judge 调用的一致性需独立观察。
5. 不能。runner 入口不同，也未实际操作 React，需补当前 AG-UI/SSE 和页面行为验证。
