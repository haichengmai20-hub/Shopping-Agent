# 第四阶段 评测 失败分析与训练边界

<a id="overview-4"></a>
## 总览：04 在整个项目里做什么

**在整个项目里的位置。** 前三篇讲系统怎样跑、怎样不出错。04 换一个角度，站在质量层回答：一次选购做得好不好，一次改动值不值得保留，从现在的评测走到真实训练还差什么。它对应[纵览](README.md#overview-all)七站里的 ⑦ 评测与改进，并且用到前面所有的东西：01 的请求线决定评测从哪个入口进，02 的工具事件是判断「有没有调用」的证据，03 保存的状态和账本是判断「有没有做错」的依据。

**要回答的问题。** **怎样判断一次选购做好了？一次改动值不值得保留？从现有的评测到真实训练还差什么？**

**答案。**

- 把需求变成可检查的条目：程序能核对的事实交给确定性断言，需要语义判断的交给 Judge，Judge 的输出还要通过格式合同检查。
- 分数和门禁分开：加权分只是汇总，单条用例要 P0 全过、确定性条目全过、总分不低于 0.7 才算 PASS；成功率的分母保留出错的用例；manifest 记下这次评测的全部条件，结果才能比较。
- 失败要变成可验证的改进：Bad Case 经人工审核后只导出提案，不自动改正式数据。Prompt 优化（GEPA）改的是文本，SFT 和 RL 才改模型参数，而项目现在没有训练链路。

**放到训练推演里看。** 这一篇是奖励设计的起点。确定性断言是可验证奖励的骨架，但现有断言偏弱（比如 required_tools 只证明调用过），还要补检查；Judge 打分有噪声，要校准后才能用；P0 门禁必须保留成硬约束，不能把加权分直接拿去最大化，否则 P0 只过一部分也能拿到高分。Bad Case 流程是数据飞轮的雏形；现有的日志和学习数据，离真正的训练轨迹还差每一步的模型输入输出、loss mask、策略版本和奖励。

## 文字版导读：先把全篇顺一遍

第一次读，先把这一节读完，再按链接进细节；复习时只读这一节。

**第一节：评测要回答的问题。** 推荐有没有违反预算和配送要求，Agent 说调用了工具是不是真的调用了，买家批准前有没有提前下单，一次 Prompt 改动是不是真的改善了表现，出错的用例怎样算进成功率，同一个坏例怎样不再发生，日志能不能直接拿去训练。评测的流程是：明确任务 → 准备固定输入和判断标准 → 运行 Globex，收集回答、工具事件和业务结果 → 程序能核对的交给确定性断言，要语义判断的交给 Judge → 校验、评分、套门禁 → 出报告和 manifest → 审核 Bad Case、归因 → 修改 → 在固定条件下重新评测。详见[一、你正在学习项目里的什么](#scope-4)。

**第二节：一条用例到底检查了什么。** 以仓库里的真实用例 agent-001（「我需要旅行装备，请推荐一件可寄到 CN 的现货」）为例：它的确定性断言只检查调用了商品检索工具，这只证明「调用被记录了」，不证明搜索成功、约束都满足或推荐正确。读评测时要一直问：这条断言读的是哪个字段，通过后究竟证明了什么。比如寄中国的背包标价 280、运费 25、关税 0，到手价 305：「标价不超过 300」和「加总一致」都通过，「到手价不超过 300」却不通过。详见[二、从 agent-001 看检查覆盖什么](#case-4)。

**第三节：评测从哪个入口进。** 真实网页走 AG-UI 和 SSE；回归评测脚本走旧的业务接口，再订阅 WebSocket 业务事件。两条路共享核心业务处理，但入口和客户端不同。所以后端用例通过，不能证明页面上的商品卡显示正确；用 HTTP 模拟买家批准，也不等于真的点了浏览器按钮。详见[三、评测脚本怎样调用后端](#runner-4)。

**第四节：程序和 Judge 各判什么。** 有没有调用工具、确认前有没有建单、数值加总对不对，这些优先用程序检查工具事件和业务事实；推荐理由清不清楚、有没有说明取舍，才交给 Judge 按评分细则判。已经由程序判过的条目会从 Judge 的输入里去掉，避免模型对同一个事实再随机判一次。Judge 的输出要通过合同检查：每个条目恰好出现一次，pass 必须是布尔值，理由要和结论一致。还要分清两种稳定性：同一份 Judge 输出重放评分代码结论不变，只证明评分代码稳定，不证明重新请求 Judge 也会给出一样的判断。详见[四、确定性断言与 Judge 的分工](#assertions-judge-4)。

**第五节：分数不是门禁。** 总分是三层通过比例的加权：0.5 × P0 + 0.35 × P1 + 0.15 × P2。但单条 PASS 还要求 P0 全过、确定性的 P0 和 P1 全过、总分不低于 0.7。所以 P0 两条只过一条，P1、P2 全过，总分 0.75，结论仍是 FAIL。整批评测要选集非空且全部 PASS 才算成功。教程描述的「动态生成评分细则」只是方案，当前代码读的是预先写好的细则。详见[五、分数与通过条件](#score-gate-4)。

**第六节：先看分母，再看百分比。** PASS、PASS、FAIL、ERROR 四条，成功率是 2/4，不能把 ERROR 排除后算成 2/3；token 用量缺失时不能填零，成本未知就写未知。manifest 是一次评测的运行清单：选了哪些用例、哪份代码和数据、哪些 Prompt、什么模型配置、出现过哪些降级。dev 集用来看失败、改方案，release 集做发布前检查，只跑个别用例属于局部诊断。仓库里有一次历史结果：2026-09-09 选 30 条，27 条 PASS、3 条 ERROR，整批门禁拦下，这是当时冻结范围的结果，不是今天的成绩。详见[六、读成功率、成本与 manifest](#metrics-manifest-4)。

**第七节：坏例怎样变成改进。** 模型把「没召回」说成「商品不存在」，可能是目录真没有、检索漏了、工具返回了但模型误读，也可能是 Judge 判错了，原因不同修法也不同。Bad Case 先作为候选保存来源，人工核对证据后接受或拒绝；接受的也只导出新的回归提案，补上可判定的条件、审核固定输入和选集归属后，再另行纳入评测集，正式数据不会被自动覆盖。详见[七、Bad Case 怎样成为可验证的改进](#bad-case-4)。

**第八节：评测和训练的边界。** 评测改变的是判断；工程修复改代码；Prompt 和 Skill 优化改给模型的文本；SFT 和 Agentic RL 才改模型参数。项目里的 GEPA 优化的是提示词文本，历史实验也没有得到优于基线的候选。要训练，得先有轨迹：输入、模型动作（工具调用）、环境观察（工具结果）的顺序记录。SFT 只让模型学助手的输出，工具结果只作上下文；RL 还要可重置的环境、rollout、奖励、采样信息和策略版本。有评分不等于有训练数据，有日志不等于有 RL 环境，训练奖励上升也不单独证明独立任务变好了。项目里还有一套默认关闭的学习数据回流，失败存成诊断样本，人工补上固定答案后再派生、导出 SFT 和 RL 任务两类样本，但只有单轮摘要，离训练轨迹还差得远。详见[八、评测、Prompt 优化、SFT 与 RL 分别改什么](#training-boundary-4)。

**补充一节：评测分三层。** 合并上游后，评测分成三层，各管一件事，但都不更新模型参数：端到端回归（正文一到七节）管一次选购的业务质量；Harness 评测套件管 Prompt、上下文、缓存、Skill 注入这类改动能不能上线，它不用 Judge，全部检查为真才通过，并把当前配置和候选配置按场景配对比较；Skill 分场景评测管注入的 Skill 会不会覆盖买家最新的约束。Harness 套件离训练最近：每个场景用临时目录和隔离数据库，用户轮次是固定脚本，会记录真实的模型请求和工具结果，只是没有 logprob。详见[补充：正文之外的评测与数据设施](#upstream-4)。

**作业与验收。** 作业 A，从 agent-001 画出一条用例怎样得到结论，并指出 runner 没覆盖的前端体验；作业 B，分析「标价合格、到手超预算」的坏例，画出从证据到复测的改进流程；作业 C，八个问题。验收时打开一个真实用例，逐项指出证据来源，手算分数和成功率，说明一个 PASS 没覆盖什么，并解释从业务日志到训练数据还缺哪几步。详见[十、作业](#assignments-4)和[十一、参考答案与验收](#answers-4)。

读完导读，按顺序读正文一到八节和补充一节，再从[作业](#assignments-4)开始动手；最后用[60 秒口述与面试追问](#oral-4)自测。

## 一、你正在学习项目里的什么

**这一节在项目里管什么。** 前三篇讲系统怎样跑、怎样不出错；这一篇换到质量层，回答两个工程问题：一次选购做得好不好，一次改动值不值得保留。方法是把「好不好」变成可检查的条目，把「值不值得」变成固定条件下的比较。

| 项目问题 | 本阶段的方法 |
| --- | --- |
| 推荐的商品是否违反预算、配送要求 | 把需求变成可检查的条目 |
| Agent 说调用过工具，实际上调用了吗 | 核对工具事件 |
| 用户批准前是否已创建订单 | 对照事件顺序、确认接口和持久结果 |
| Prompt 改动是否确实改善表现 | 固定任务、版本和条件做比较 |
| 一批用例有网络错误，成功率怎么算 | 保留错误状态，明确分母 |
| 怎样避免同一坏例重复发生 | 留证据、审核原因、补回归 |
| 日志能否直接拿去 SFT/RL | 核对轨迹、监督目标和算法所需信息 |

~~~text
明确要评的任务
    |
准备固定输入与判断标准
    |
运行 Globex，收集回答、工具事件和业务结果
    |
    +-- 程序能核对的事实 --> 确定性断言
    +-- 需要语义判断的内容 --> Judge
                          |
                          v
                  校验、评分和通过条件
                          |
                          v
                    报告 + manifest
                          |
                          v
                  Bad Case 审核与归因
                          |
                          v
              修工具 / 状态机制 / Prompt / 用例
                          |
                          v
                   固定条件重新评测
~~~

Case（用例）是具体输入、条件和要求；Rubric（评分细则）列出针对任务的检查项；Judge（评委）在这里主要是根据细则评判的模型；Trace（执行记录）记录任务中的调用、结果与相关事件。

**放到训练里看。** 「固定输入 → 运行 → 收集证据 → 判定」这条流程，就是训练里「任务 → rollout → 轨迹 → 奖励」的骨架。06 的评测协议沿用它：任务集固定，判定独立于策略。[06 第六节](06_训练推演_澄清检索补证.md#attribution-6)

## 二、从 agent-001 看检查覆盖什么

**这一节在项目里管什么。** 评测的一切从用例出发。这一节拿仓库里真实的 agent-001 示范读评测的最重要习惯：每条断言读哪个字段、通过之后究竟证明了什么、没证明什么。后面几节的分数、门禁、报告，全都建立在这条习惯上。

打开 [agent_cases.yaml](../../eval/v1/agent_cases.yaml)，第一条 agent-001 的问题是“我需要旅行装备，请推荐一件可寄到 CN 的现货”。下面摘出其评分部分，省略其他元数据：

~~~yaml
queries:
  - 我需要旅行装备，请推荐一件可寄到 CN 的现货。
rubric:
  p0:
    - 不得编造商品、价格、订单或政策事实
  p1:
    - 程序断言：调用该场景所需工具
  p2:
    - 回复清晰并说明边界
deterministic:
  p1:
    - criterion: 程序断言：调用该场景所需工具
      kind: required_tools
      tools:
        - product_search_tool
~~~

required_tools 检查事件中出现了所需工具的调用。它支持“记录到了商品搜索调用”，不能单独证明搜索成功、全部约束成立或推荐正确。[断言实现](../../scripts/eval/evidence.py)

读评测时始终问：这条断言读哪个字段，通过后究竟证明什么？例如以下教学数据均为人民币：

~~~text
商品标价 280 + 运费 25 + 关税 0 = 到手价 305
用户要求：总到手价不超过 300

检查商品标价：280 <= 300       通过
检查加总一致：280+25+0=305     通过
检查到手预算：305 <= 300       不通过
~~~

当前 product_hits 的预算检查读 price_major；landed_price_consistency 检查小计、运费、关税与总价相加是否一致。这些检查不能替代对总到手上限、币种、数量和配送条件的完整核对。

源码进一步显示，应用侧 CatalogSearchUseCase._within_price_cap() 也比较换算后的单件商品金额；_to_card() 随后才计算并附上 landed_price。因此“存在结构化预算过滤”不能被解释为“总到手预算已经硬性过滤”。第五阶段会沿这条实际路径展开。[当前过滤与商品卡实现](../../app/application/usecases/catalog_search.py)

**放到训练里看。** 「标价合格、到手超预算」这个缺口，就是 06 陷阱商品和补强版奖励的出发点。奖励如果像 required_tools 一样只证明「调用过」，或只核对「参数填了」，策略就会学会把参数填得好看；06 的补强版把这条检查换成按到手价逐件独立核对，堵的正是这里的洞。

## 三、评测脚本怎样调用后端

**这一节在项目里管什么。** 评测从哪个入口进，决定了它能证明什么。真实买家走页面和 AG-UI；评测脚本走旧的业务接口。入口不同、客户端不同，覆盖就不同——这一节把这条边界画清楚，免得拿一层的通过去宣布另一层没问题。

真实网页走 AG-UI/SSE；当前回归脚本则调用 /commerce/intents，并订阅 /commerce/events 的 WebSocket 业务事件。两条路径共享核心业务处理，但入口和客户端行为不同。

~~~text
浏览器 React + AG-UI Client            Python 评测客户端
            |                                  |
   /commerce/ag-ui/run                  /commerce/intents
            |                                  |
       AG-UI 运行入口                     业务接口入口
            +----------------+-----------------+
                             |
                             v
                   MainAgentOrchestrator
                             |
                             v
                       Agent 与工具
                  +----------+----------+
                  |                     |
                  v                     v
       AG-UI / SSE → 页面      回答 + WebSocket 业务事件
                                          |
                                          v
                                      断言与 Judge
~~~

HTTP 客户端是发送网络请求的程序；浏览器和 Python 都可以充当客户端。评测脚本不必打开 React 页面，就能测试部分后端行为。[评测执行入口](../../scripts/eval_regression.py)中的 _run_case_with_events() 与 SessionEventCollector 分别负责请求与事件采集。

对应边界也要清楚：后端用例通过不能证明商品卡显示正确；确认接口通过不能证明页面按钮可用；旧接口采集通过不能证明 AG-UI 的刷新恢复通过。一些订单用例通过 HTTP 模拟用户批准，再重读订单，它们没有真实点击浏览器按钮。

**放到训练里看。** 训练环境（06）选择了第三条入口：从工具层直接进，不经过两条 HTTP 入口中的任何一条。这换来了免费和可重置，代价是页面链路完全没被覆盖——所以 06 的结论只能说「策略决策变好了」，不能说「产品变好了」，后者要靠这一节的评测补。

<a id="assertions-judge-4"></a>
## 四、确定性断言与 Judge 的分工

**这一节在项目里管什么。** 一条用例的检查项分成两堆：程序能核对的和需要语义判断的。这条分工线画在哪里，决定了评测的噪声有多大、成本有多高——它同时也是后面奖励设计最重要的一条线。

| 检查目标 | 优先看的证据 |
| --- | --- |
| 有没有调用某工具 | tool.invoke 等调用事件 |
| 确认前是否已经创建订单 | 确认、订单快照及事件顺序 |
| 批准后是否创建了对应订单 | 确认响应与重读的持久订单 |
| 数值加总是否一致 | 结构化数值 |
| 推荐理由是否清楚、解释了取舍吗 | Rubric 配合模型或人工评价 |
| 回答是否编造事实 | 商品事实与本轮工具结果；可结构化部分优先程序检查 |

~~~text
用例 Rubric
    |
    +-- 已配置确定性断言的条目 --> 检查 trace 与业务事实
    |
    +-- 剩余条目 --> 回答、事实、细则交给 Judge
                                |
                                v
                          校验 Judge 输出
                                |
                                v
          合并程序和 Judge 判断，计算分数与最终结论
~~~

build_judge_rubric() 会从评委输入中移除已由程序检查的条目；apply_trace_evidence() 合并结果，避免模型再次随机裁决同一项已核对事实。[评分合并代码](../../scripts/eval_regression.py)

Judge 读取买家与 Agent 对话、商品事实表、本轮工具事实及用例声明的前置事实。动态库存、到手价和订单状态应对照本轮工具结果；静态目录或模型常识不能代替它们。

[contracts.py](../../scripts/eval/contracts.py)要求每个评分条目恰好出现一次，pass 必须是布尔值，理由中的明确结论与 pass 一致。漏判、缺字段和重复条目不能默认为通过。

还要区分两种一致性：

~~~text
固定 Judge 输出 + 固定 trace，重复走评分代码
    --> 检查程序评分是否稳定

重新请求 Judge 多次，比较其判断
    --> 检查模型评委的一致性
~~~

verify_fixed_trace_stability() 主要做前一种；它不单独证明新请求的 Judge 判断稳定或与人工一致。

**放到训练里看。** 这条分工线直接搬到奖励里：确定性条目做成可验证奖励——零噪声、不能被策略讨好；Judge 类条目要么校准后做稀疏加分，要么不进奖励。06 选的是把全部判定换成商品目录上的独立核对，一条 Judge 都不用：这个任务的对错能完全程序化，是这个窄任务适合做 RL 的原因之一。

<a id="score-gate-4"></a>
## 五、分数与通过条件

**这一节在项目里管什么。** 分数回答「大概多好」，门禁回答「能不能接受」。两者分开，是因为加权分有个天然的漏洞：单项的缺失会被其他项的通过稀释掉。这一节讲这套评分和门禁怎样堵住这个漏洞。

这里的 P0/P1/P2 是用例评分层级。教程以它们表示业务红线、执行规范和质量要求；实际条目以用例为准。当前 score_case() 计算各层通过比例后加权：

~~~text
总分 = 0.50 × P0通过比例
     + 0.35 × P1通过比例
     + 0.15 × P2通过比例

单条 PASS 还要求：
P0 全通过
且配置为确定性检查的 P0/P1 全通过
且总分 >= 0.7
~~~

例如 P0 两条只过一条，P1 两条全过、P2 一条全过，则分数为 0.25+0.35+0.15=0.75，但因 P0 没全过仍 FAIL。[score_case 与门禁实现](../../scripts/eval_regression.py)

分数是汇总，门禁是接受条件。此 runner 的成功退出要求选集非空且全部用例 PASS；代码或数据在运行期间变化时也会影响最终接受结论。单条 PASS 不能代替整批通过。

第 08 章描述了动态生成 Rubric 的方案，而当前 runner 读取 YAML 中预先写好的细则。文档方案不自动等于已经执行的代码路径。

**放到训练里看。** 「加权会稀释硬约束」这个教训直接决定了奖励的形状：06 的补强版奖励把成功和失败做成硬判定（1 和 0），P0 直接 -1，成本项只在成功一侧扣、不与硬判定加权混算——就是把这里的「分数与门禁分开」翻译成了奖励函数。

<a id="metrics-manifest-4"></a>
## 六、读成功率、成本与 manifest

**这一节在项目里管什么。** 两个数字要能比较，前提是口径一样。这一节讲读评测数字的两条纪律：先看分母（ERROR 不能悄悄扔掉），再看条件（manifest 里记录的一切，决定了这份成绩和那份成绩能不能放在一起比）。

分母先于百分比。假设选中四条任务，状态为 PASS、PASS、FAIL、ERROR，则当前任务成功率为 2/4=50%。不能排除 ERROR 后改算 2/3；ERROR 和业务 FAIL 保留不同分类，但都不是成功。[metrics_evidence.py](../../scripts/eval/metrics_evidence.py)

| 字段 | 当前代码的范围 |
| --- | --- |
| task_success_rate | PASS 数 / 全部选中用例数 |
| hard_constraint_pass_rate | 按 P0 全过统计，不表示全部可能业务约束均覆盖 |
| latency_p95_ms | 用例耗时 P95，当前口径排除 Judge |
| input_tokens、output_tokens | 所需业务回合 usage 完整时才给完整汇总 |
| cost_usd | 成本信息完整才汇总，否则未知 |

usage 缺失不能填零。Agent LLM 的计量也不自动包含 embedding、reranker、Judge 等全部外部费用。[指标与 BadCase 口径](../指标与BadCase闭环.md)

一次历史练习：[2026-09-09 Agent 原始 manifest](../../eval/verification/release-20260909/agent/agent-release-report-20260909-132421-803890.manifest.json)中选中 30 条、27 PASS、3 ERROR，整批 gate 为 BLOCK。该次成功率为 27/30=90%；这是那个冻结范围的历史结果，不是今天重跑的成绩。

Manifest 可以理解成“一次评测的运行清单”：哪些 case、哪个 split、哪份代码和数据、哪些 Prompt、模型配置与观察到的降级、用例结果和失败证据。配置的模型名称不单独证明远端实际版本完全相同。[run_manifest.py](../../scripts/eval/run_manifest.py)

~~~text
报告分数
    +-- 选集：哪些 case，dev / release / all？
    +-- 代码：版本、dirty 状态、内容指纹？
    +-- 输入：数据、Prompt、基线？
    +-- 运行：模型配置、实际策略、失败记录？
~~~

dev 用于观察失败并修改；release 对固定方案做发布前检查；--only 缩小到个别用例后属于局部诊断；--dry-run 只检查选集与清单，状态为 NOT_RUN。真实比较需要相应条件可比，局部通过不代表完整发布范围通过。[正式选集规则](../正式评测选集与证据清单.md)

**放到训练里看。** 06 的评测协议照搬了这两条纪律：开发集（dev）用来选 checkpoint，held-out 只在最终 checkpoint 上评一次、绝不参与任何选择；比较两轮用区间不重叠或配对检验，不直接比两个百分比——「先定协议再看数字」正是从这一节学去的。

<a id="bad-case-4"></a>
## 七、Bad Case 怎样成为可验证的改进

**这一节在项目里管什么。** 评测发现失败只是第一步；失败要能变成「不会再发生」才闭环。这一节讲坏例怎样经人工审核变成回归提案——关键在两处：先归因（不同原因不同修法），再固定（补上可判定的条件，而不是让报告变绿）。

若模型把“未召回”说成“商品不存在”，先区分：目录真没有、检索漏了、工具已经返回但模型误读，还是 Judge 误判。不同原因需要不同修复。检索漏了还要再细分：是根本没召回，还是召回了但在排序中丢了。第五阶段讲的检索阶段采集能把两者分开，但它只在离线检索评测里打开，而且只记录混合召回分支；端到端回归的 trace 里没有这些阶段。

~~~text
结果及 manifest
    |
Bad Case 候选，保存报告来源 / hash / case ID / 分类
    |
人工核对证据
    +-- rejected：记录原因
    +-- accepted
            |
            v
        导出新的回归提案
            |
       补可判定条件、审核 fixture 与选集归属
            |
            v
       另行纳入合适的回归或评测集
~~~

Fixture 是测试需要的固定输入或环境材料，gold 是经审核的参考答案或标注。accepted 候选不会自动覆盖正式数据；当前导出提案仍要求后续审核，official_dataset_changed 为 false。[feedback.py](../../scripts/eval/feedback.py)

这一部分主要是离线工具，产生报告、manifest、分数发件箱和待审核记录。出现一个分数不会自动改写买家网页回答或训练模型。

**放到训练里看。** 「现象 → 原因（每条配证据）→ 只改有证据的处 → 固定协议复测」这条 Bad Case 流程，就是 06 里 run-01 到 run-02 的归因方法：run-01 结果一般，三条原因各自有真实运行的证据，run-02 只改这三处再复测。run-02 给 SFT 补 C 风格改写，本质也是把 Bad Case 的思路用在数据分布上——失败样本指出数据缺什么，补什么，而不是凭空加数据。

<a id="training-boundary-4"></a>
## 八、评测 Prompt 优化 SFT 与 RL 分别改什么

**这一节在项目里管什么。** 改进有四类，各改不同的东西：评测改判断，工程修复改代码，Prompt 优化改文本，SFT 和 RL 改参数。分清这四类，才知道手头的问题该用哪把工具、以及项目现在停在哪一级（停在 Prompt 优化，没有训练链路）。这一节同时列出从日志走到训练数据还缺的东西，是全篇通往 06 的桥。

在当前 app、scripts 和依赖中找到的直接实现包括评测、Bad Case 管理、离线 Prompt/Skill 优化，以及默认关闭的学习数据回流（失败存成诊断样本，经人工补固定答案后可派生、导出 SFT 和 RL 任务两类样本，见[补充一节](#upstream-4)）；仍然没有 SFT/GSPO 的权重训练入口，也没有可关联的冻结实跑证据。08 系列在这里用来理解及设计训练扩展。

| 工作 | 改变什么 | 学习目的 |
| --- | --- | --- |
| 评测 | 判断与证据 | 知道系统做得怎样 |
| 工程修复 | 工具、检索、状态或权限代码 | 修具体原因 |
| Prompt/Skill 优化 | 给模型的指令文本 | 改调用方式和行为引导 |
| SFT | 模型参数 | 从审核后的示范学习动作 |
| Agentic RL | 模型参数 | 根据环境交互与奖励改善策略 |

[optimize_prompts.py](../../scripts/optimize_prompts.py)用 GEPA 优化文本；不是 SFT/RL 权重训练。[历史 GEPA 记录](../改动记录/2026-09-18/GEPA离线优化.md)明确保留了未得到优于基线候选的结果。

Trajectory（轨迹）是输入、模型动作和环境观察的顺序记录：

~~~text
用户需求
    |
assistant 工具调用    <-- 要学习的模型行为
    |
tool 商品结果        <-- 环境观察，供后续决策
    |
assistant 继续调用或回答 <-- 要学习的模型行为
~~~

Loss mask（损失掩码）决定哪些 token 参与训练目标。这套 Agent SFT 设计中，已有轨迹的 assistant 输出作为监督目标；system、user、tool observation 提供上下文，通常不作为要求模型生成的答案。只存最终问答会丢掉工具决策，仅有业务事件日志也不保证具备完整训练消息和 token 对齐。

~~~text
可重置任务与环境
    |
当前策略执行，采集 rollout
    |
记录动作、观察、版本、终止原因
    |
计算 reward，保留算法需要的采样信息与 mask
    |
更新策略参数
    |
独立固定任务重新评测
~~~

Rollout 是策略实际执行任务的采样过程，reward 是评价行为结果的训练信号。未来训练还需明确动作 token、mask、采样概率信息、策略版本与终止语义；工具录制回放也需要处理新参数没有对应历史返回的情形。有评分不等于完整训练数据，有日志不等于实现 RL 环境，训练奖励上升不单独证明独立任务质量提高。

**放到训练里看。** 这一节列的清单——轨迹格式、loss mask、可重置环境、rollout、终止语义、策略版本——在 [06](06_训练推演_澄清检索补证.md#overview-6) 里逐项落了地，可以对着看：06 的轨迹就是这里的 Trajectory（每条记录带 `policy_version` 字段），06 的 `max_turns` 就是这里的终止语义，06 两版奖励的对照就是在检验「训练奖励上升不单独证明任务质量提高」这句话。

## 补充：正文之外的评测与数据设施

正文一到八节讲的是端到端回归。2026-10-14 合并上游后，质量层还多了两套评测和一套数据回流。站在整个项目看，评测从此分三层，各管一件事，但都不更新模型参数：

| 设施 | 管什么 | 怎样判 | 离训练有多远 |
| --- | --- | --- | --- |
| 端到端回归（正文一到七节） | 一次选购的业务质量 | 确定性断言加 Judge，P0 门禁 | 有用例和评分，没有可训练的轨迹 |
| Harness 评测套件 | Prompt、上下文治理、缓存、Skill 注入这类改动能不能上线 | 48 个场景，不用 Judge，全部检查为真才通过；当前配置和候选配置按场景配对比较 | 最近：每个场景用临时目录和隔离数据库，用户轮次是固定脚本，会记录真实的模型请求和工具结果；但没有 logprob，商品目录冻结在 v1 |
| Skill 分场景评测 | 注入的 Skill 会不会覆盖买家最新的硬约束、会不会越权 | 600 条合成用例分 6 组；一部分用真实模型比较有无 Skill 时检索参数是否保留约束，一部分是不调模型的审批与版本契约检查 | 参数级检查可以当可验证奖励的原型；但只测单轮检索，不留轨迹 |

Harness 套件有四个档位：contracts 只跑确定性契约测试，不调模型（本机 2026-10-19 跑过，838 个测试全部通过）；smoke、dev、release 依次加大场景数和重复次数，都要调用模型。按仓库约定，修改 Prompt、上下文治理、Skill 注入这类代码，交付前要跑 `make eval-harness`。release 档还要求计费信息经过验证，当前配置里这一项没有验证，所以 release 门禁必然拦下。

学习数据回流默认关闭。开启后，网页运行结束时在同一个事务里登记一项学习任务，评测报告也可以导入。没有正常完成的运行（以及评测里失败的用例）存成诊断样本；正常完成、证据足够的运行交给另一个模型判断是否成功、能否提炼成策略候选（这个判断只用于筛选），人工验证和审核后，才发布为可以撤回的策略记忆。它还能从诊断样本派生并导出带版本的训练样本：SFT 样本的目标输出必须等于固定输入里人工给定的期望答案，RL 任务样本不带目标。但回流的记录最多只有本轮提问、最终回答和 12 个商品事实（网页运行失败时只留引用），没有多轮消息、工具观察、mask 和奖励，导出时也写明还没有开始训练。所以「有回流样本」仍然不等于「能训练」。

## 十、作业

### 作业 A：画一个用例怎样得到结论

## 60 秒口述与面试追问

**60 秒口述。** Globex 的评测把买家需求拆成可检查的条目。程序能核对的事实，比如有没有调用工具、确认前有没有建单、金额加总对不对，交给确定性断言，直接读工具事件和业务数据；推荐理由这类语义判断交给 Judge，Judge 的输出要通过格式合同。分数和门禁是两回事：总分是 P0、P1、P2 通过比例的加权，但单条 PASS 要求 P0 全过、确定性条目全过、总分不低于 0.7，整批要全部 PASS；成功率的分母保留出错的用例，每次评测附一份 manifest，记录代码、数据、Prompt 和模型条件。失败先进 Bad Case，人工审核后只导出回归提案。评测分三层：端到端回归管业务质量，Harness 套件管改动能不能上线，Skill 评测管约束会不会被覆盖。改进有四类：工程修复、Prompt 优化、SFT、RL，只有后两类改参数，而项目目前没有训练链路。放到训练里看，确定性断言就是可验证奖励的雏形，P0 门禁要保留成硬约束。

**面试追问。**

| 追问 | 答题要点 |
| --- | --- |
| 加权分 0.9 为什么还会 FAIL？ | P0 只过了一部分；加权分只是汇总，门禁要求 P0 全过、确定性条目全过、总分不低于 0.7 |
| 为什么不全交给 Judge 判？ | Judge 有噪声、可能翻转、成本高；能程序核对的事实优先程序判，Judge 只判语义，输出还要过合同检查 |
| 成功率能不能把 ERROR 排除掉？ | 不能，ERROR 留在分母里，分类单独保留；用量缺失不能填零 |
| 能不能直接拿评测分数当 RL 奖励？ | 不能直接用：加权分会稀释 P0 硬约束，模型还可能靠「不推荐」「全部追问」投机；要以确定性断言为主，保留硬约束，加防投机检查 |
| 现有日志离 SFT 或 RL 训练数据还差什么？ | 每一步完整的模型输入输出、工具调用与观察的配对、loss mask、策略版本、终止原因和奖励；遥测里的正文已经脱敏，学习数据回流只存单轮摘要 |
