# 第二阶段 AgentLoop 工具调用与子 Agent 派发

<a id="overview-2"></a>
## 总览：02 在整个项目里做什么

**在整个项目里的位置。** 02 打开决策层，也就是[第一阶段](01_项目地图与前后端流程.md#request-flow-1)请求线上 MainAgent 那一格。Globex 在对话里做的事，比如查商品、查品类知识、准备订单确认、记录偏好，都是模型通过工具完成的（整理上下文、批准订单这类操作走独立接口，不经模型）。02 讲的就是这条「模型选工具 → 后端执行 → 结果回到模型」的循环，以及主 Agent 怎样把子任务派给 SearchAgent 和 TradeAgent。它对应[纵览](README.md#overview-all)七站里的 ④ Agent 循环，并补上 ⑥ 里事件怎样到达页面。

**要回答的问题。** **一条用户消息为什么能触发多次模型和工具调用？模型什么时候自己调工具，什么时候派子 Agent？**

**答案。**

- 工具循环：模型生成工具名和参数，后端找到并执行注册的工具，结果按调用 ID 回到上下文，模型再决定下一步。
- 派发：子 Agent 对主 Agent 来说只是一次工具调用，内部新建一个有独立状态的 Agent，所以交给它的任务说明必须自包含。
- 证据要分层：模型说「调用了」不等于后端执行了；参数生成完不等于执行有结果；声明可并发不等于真的并发。

**放到训练推演里看。** 这一篇就是 Agentic RL 里的「动作与观察」：模型每次选工具、填参数是一个动作，工具结果是观察，一串动作和观察就是一条轨迹。训练推演要学的「要不要澄清、怎样检索、要不要补证据」，都发生在这个循环里；调用 ID 配对，以及在模型请求和工具结果两处取到完整的输入输出，决定了将来能不能把轨迹准确地记下来（页面的事件流做不到这一点，第六节讲原因）。

## 文字版导读：先把全篇顺一遍

第一次读，先把这一节读完，再按链接进细节；复习时只读这一节。

**第一节：一个回合里有多次调用。** 买家发一条消息，后端可能多次请求模型、多次执行工具。「我第一次买轻便背包，不知道怎么挑。预算 300 元人民币，寄到中国，先讲讲选购要点，再推荐具体商品」可以这样走：模型先调品类知识工具拿选购要点，再调商品检索工具找候选，最后综合两次观察作答。这是一个对话回合、三次模型调用、两次工具调用。主 Agent 的迭代上限是 15，两个子 Agent 是 6，这是上限，不是固定步数；循环在模型直接作答、需要等买家（审批或表单）、或撞到上限时停下，撞上限的一轮算没有正常完成。循环在 AgentScope 框架里运行，编排器一边接收事件一边处理，所以页面能在回答完成前看到进度。详见[一、先看整个循环](#loop-2)。

**第二节：函数怎样变成工具。** 框架把一个 Python 函数包装成工具：函数名就是工具名，参数签名变成给模型看的参数说明，docstring 说明用途；真正的函数留在后端。模型给出工具名和参数后，后端先过权限检查和工具中间件（顺序检查、超时、熔断），再执行业务代码。由此得出全路线最重要的一个习惯：同时检查「模型传对了吗」和「代码按参数执行了吗」。比如模型漏传预算参数，过滤就不会发生；传了也只比单件价。教程说「做成参数后，模型忘不忘都不影响结果」，前提其实是模型确实传了参数。两个工具声明也别读过头：「只读」不代表重试没有成本，「可并发」不代表真的并发了。详见[二、Python 函数怎样成为模型可调用的工具](#tools-2)。

**第三节：调用和结果靠 ID 配对。** 每次调用带一个 ID，结果带着同一个 ID 回来，框架据此把结果放进上下文，下一次模型请求才能用上这次观察。同一轮查两次背包，一次查日用的、一次查徒步的，后发的那次先回来也不会配错。工具出错也是一种观察，要如实交给模型，不能包装成「搜到空列表」。详见[三、调用和结果怎样配对，并影响下一轮](#call-id-2)。

**第四节：子 Agent 是一次工具调用。** 主 Agent 既能自己调业务工具，也能用 `task_dispatch` 把子任务派给 SearchAgent 或 TradeAgent。对主 Agent 来说，派发只是一次工具调用；内部会新建一个有自己提示词、工具和状态的子 Agent，跑完只交回结论。子 Agent 看不到主对话的历史，但能拿到可信的买家身份，SearchAgent 还会注入相关的长期偏好；所以任务说明要写清商品、预算和收货地。派发的理由有三个：子任务可以并行、中间信息需要隔离、内部调用链较深；有前后依赖的步骤不能并发。子 Agent 交回的结论如果提到本轮检索证据核实不了的商品，会被标成待核验，主 Agent 要复核。详见[四、子 Agent 怎样作为一个工具被派发](#dispatch-2)。

**第五节：并发要分三层看。** 声明可并发是能力；模型在同一轮真的发出了多个调用是行为；两次执行的时间区间确实重叠才是证据。项目用派发的开始和结束时间检查是否重叠。5 秒加 8 秒的两个子任务，串行约 13 秒、并发约 8 秒，这只是教学计算，不是实测。详见[五、async、并发和实际执行证据](#concurrency-2)。

**第六节：页面怎样知道进度。** 后端把框架的原生事件和业务事件转成 AG-UI 事件，写进运行日志，再经 SSE 推给页面。五个原生事件要分清：文字片段（`TEXT_BLOCK_DELTA`）、开始生成调用（`TOOL_CALL_START`）、参数生成完（`TOOL_CALL_END`）、结果开始（`TOOL_RESULT_START`）、结果收口（`TOOL_RESULT_END`）。只有结果收口时才能说成功或失败，「参数生成完」不等于「查询成功」。商品卡来自商品工具发布的结构化结果，不是从回答文字里抠出来的。详见[六、前端看到了什么，后端如何交付事件](#events-2)。

**作业与验收。** 作业 A，画一次工具循环，标出调用 ID、两条回路和两个关键事件；作业 B，画一次派发，主 Agent 同轮派出日用和徒步两个背包子任务，写出自包含的任务说明，再画串行与并发两条时间线；作业 C，八个问题。验收时要能画出「工具结果进入下一次模型输入」的回路，讲清主子 Agent 的边界，并用事件区分参数生成、实际执行和结果收口。详见[八、作业](#assignments-2)和[十、验收与边界](#acceptance-2)。

## 一、先看整个循环

**这一节在项目里管什么。** 01 的请求线走到 MainAgent 那一格就停了。这一格里发生的事，决定了 Globex 是「一问一答的聊天」还是「会查证的 Agent」：模型不是一次就写出最终回答，而是在一个循环里反复「判断 → 调工具 → 看结果 → 再判断」。查商品、查知识、出表单、准备订单，都是这个循环里的一步。

~~~text
当前用户需求与会话信息
          |
          v
    模型生成下一步
          |
     +----+-----------------------+
     |                            |
     v                            v
  可以回答                   需要调用工具
     |                            |
     v                            v
  生成回答              工具名 + 结构化参数
                                  |
                                  v
                        后端查找并执行注册工具
                                  |
                                  v
                         返回结果或明确的错误
                                  |
                                  v
                        结果进入 Agent 上下文
                                  |
                                  +----> 再次请求模型
~~~

整个循环只有一个关键：**工具结果要进入上下文**。下一次模型判断能利用上一步的观察，全靠这一点。循环运行的同时还会产生事件，经 AG-UI 送到页面显示进度，这是 01 讲过的第二条回路，第六节再展开。

例如买家说：“我第一次买轻便背包，不知道怎么挑。预算 300 元人民币，寄到中国，先讲讲选购要点，再推荐具体商品。”一种合理的路径如下：

~~~text
用户提出需求
    |
    v
模型请求 1
    | 判断需要先取得选购知识
    v
category_insight_tool
    | 返回品类选购依据
    v
模型请求 2
    | 根据知识、预算和配送地形成检索参数
    v
product_search_tool
    | 返回具体候选、价格信息和过滤原因
    v
模型请求 3
    | 综合前面的观察结果
    v
选购要点 + 商品建议 + 取舍说明
~~~

先分清三个计数，后面几篇都会用到：

- **用户对话回合**：买家发一条消息，等这一轮处理完。
- **模型调用**：后端向模型服务发一次生成请求。
- **工具调用**：后端真正执行一次工具。

上图是一个回合、三次模型调用、两次工具调用。这只是一种合理路径：先查知识还是直接检索，查一次还是查两次，取决于当轮需求、模型和工具结果。

**循环怎样停下来。** 有三种正常出口：

- 模型给出不再调工具的回答。
- 需要等买家。两种情况不一样：
  - 写长期记忆要买家审批，框架把本轮暂停在这次调用上；买家确认后，从暂停处接着跑，还是同一轮。
  - 澄清表单展示后，工具结果提示模型结束本轮（这一步靠模型遵守提示，框架不强制）；买家提交的表单作为一条新消息，开始新的一轮。
- 撞到迭代上限。主 Agent 的上限是 15 次，两个子 Agent 各是 6 次。到上限时框架会再请求一次模型，并禁止调工具，要求它总结作答；这一轮记为「超出步数上限」，页面提示没有正常完成。

15 是上限，不是固定步数。它也不等于 HTTP 请求总数：上游出错时编排器会整轮重试，一次模型决策也可能同时发出多个工具调用。

**谁在跑这个循环。** 循环本体在锁定版本的 AgentScope 2.0.8 框架里，Globex 自己不写循环。编排器只做一件事：调用 Agent 的 `reply_stream()`，一边接收事件一边处理。

后端知识补充：普通函数完成时才交回一个返回值；`reply_stream()` 则连续交出事件。`async for` 每收到一个事件就处理一个，所以页面能在最终回答完成之前，先看到文字片段、工具进度和商品卡。

~~~text
时间向后推进 →
Agent：文本片段 → 工具调用 → 工具结果 → 新文本片段 → 结束
后端：逐个接收 → 逐个处理 → 逐个处理 → 逐个处理 → 收尾
~~~

教程里的 Think → Act → Observe → Reflect 是一种教学视角。项目每轮并不会额外调用一个独立的「反思模型」，Reflect 就是下一次模型调用。

**放到训练里看。** 这个循环正是 Agentic RL 要优化的对象：每次模型调用产生一个动作（作答、追问还是检索，参数怎么填），每次工具结果是一次观察，循环停下就是一个回合结束。迭代上限对应训练里「单条轨迹最多几步」，撞上限的轨迹要单独标记终止原因，不能当成正常完成。

终止原因有现成字段可用。一轮结束时，框架发出的结束事件带 `finished_reason`，取值只有四个：`completed`（正常作答）、`exceed_max_iters`（撞上限）、`interrupted`（被中断）、`error`（出错）。编排器把 `exceed_max_iters` 和 `error` 当失败，把 `interrupted` 当取消。有三点要注意：

- **等审批不是一种结束。** 这时框架只是暂停，不发结束事件，轨迹要接上买家确认后的部分才算完整；表单等待在框架看来就是 `completed`。
- **撞上限的轨迹最后多一步。** 一次迭代是「一次模型调用，加上它发出的全部工具执行」。第 15 次迭代做完还没作答，框架会追加一条系统提示，再以「禁止调工具」请求一次模型，所以主 Agent 一轮最多做 16 次决策（整轮重试另算）。这最后一步的上下文多了框架提示，动作也只剩写文字，不能当普通作答来学。
- **整轮重试会把一轮拆成几段。** 上游瞬时出错时，编排器用同一个 Agent 最多再跑两次，不重发买家消息；出错前已写进上下文的步骤留着，迭代计数从零重新算。单次模型调用重试用尽，还会换成备用模型（默认 qwen-plus）。所以一条轨迹里可能有几步不是同一个模型生成的。

<a id="tools-2"></a>
## 二、Python 函数怎样成为模型可调用的工具

**这一节在项目里管什么。** 循环里模型能做的每件事，都要先有人把它做成工具。Globex 的工具分三类：

- **只读的业务工具**：商品检索、品类知识、对话事实回查、订单查询、Skill 与策略记忆读取；配了密钥时还有联网搜索。
- **有副作用、但受控的工具**：准备订单确认单和取消单，只写一张待确认单，买家点确认才真正执行；写长期记忆要经买家审批；澄清表单展示后，提示模型结束本轮、等买家提交。
- **编排类工具**：计划（`TaskCreate` 等）和派发（`task_dispatch`）。

主 Agent 持有全部业务工具，所以它可以不派发、自己干。这一节以 `product_search_tool` 为例，看一个 Python 函数怎样变成模型能调用的工具。

打开 [SearchAgentFactory.build_tools()](../../app/application/agents/search_agent.py)，先看 product_search_tool 的注册。FunctionTool 将一个 Python 函数包装成 Agent 可用的工具：函数名与文档描述帮助模型判断用途，参数签名生成输入字段说明，真正的函数留在后端等待执行。

~~~text
Python 工具函数
    |
    +-- 函数名 ----------------> 工具名称
    +-- 参数与类型 ------------> 输入字段说明
    +-- docstring 文档字符串 --> 用途、参数含义和使用时机
    |
    v
FunctionTool 包装
    |
    +-- 工具定义交给模型
    +-- 真实 Python 函数留在后端，等待调用
~~~

JSON Schema 是描述数据结构的格式。第一遍可以把它理解成“工具参数填写说明”：有哪些字段、字段是什么类型。下面是生成工具参数的教学示意，并非完整 HTTP 报文：

~~~json
{
  "normalized_query": "轻便 背包",
  "ship_to": "CN",
  "price_max_major": 300,
  "target_currency": "CNY",
  "top_k": 5
}
~~~

CN 是中国的二位国家码，CNY 是人民币币种代码，top_k 指最多返回多少个候选。模型生成工具名和这些参数后，AgentScope 找到注册工具；后端会进行权限与工具中间件处理，再执行 [product_search_tool.py](../../app/application/tools/product_search_tool.py) 中的函数。工具将参数整理为 ProductSearchSpec，调用 [CatalogSearchUseCase.execute()](../../app/application/usecases/catalog_search.py)，最后以 ToolChunk 返回内容和状态。

~~~text
模型生成工具名和参数
    |
    v
框架定位已注册工具
    |
    v
权限判断及工具中间件
    |
    v
product_search_tool(...)
    +-- 将可接受的数字字符串转成数字
    +-- 构造 ProductSearchSpec
    +-- 调用 CatalogSearchUseCase.execute(...)
    |
    v
业务结果封装为 ToolChunk
~~~

中间件是包在工具调用前后的代码，像洋葱一样一层套一层：外层是 Harness 的顺序检查和重复检测（03 细讲），内层是超时和熔断。被拦下或超时的调用，会以明确的错误结果交回模型，不会悄悄消失。ToolChunk 是工具的返回容器；查询、过滤和做商品卡由业务用例负责（05 细讲）。

**全路线最重要的一个习惯：同时检查「模型传对了」和「代码按参数执行了」。** 预算就是现成的例子：

- **模型可能漏传。** `price_max_major` 默认为空，模型没填这个字段，用例就跳过价格上限检查。所以教程第 02 章说「做成参数后，模型忘不忘都不影响结果」，前提是模型确实传了参数。[工具参数默认值](../../app/application/tools/product_search_tool.py)
- **传了也只管单件价。** 即使正确传入，当前的价格检查也只比较换算后的单件商品价，不含运费和关税。买家要的「总到手价不超过 300」，回答前要对照商品卡里的到手价另外核对。[用例价格检查](../../app/application/usecases/catalog_search.py)

参数名只是接口，不是保证。这个口径在 05 有完整讲解。

工具还有两个常见声明，都别读过头：

| 声明 | 当前用途 | 需要注意的边界 |
| --- | --- | --- |
| is_read_only=True | 标明这次调用没有业务副作用；权限引擎见到只读工具直接放行，不用审批（非只读工具要靠项目的放行名单） | 不等于重试零成本，也不保证库存快照永不变化；真正挡住副作用的是待确认单和审批 |
| is_concurrency_safe=True | 允许调用进入框架的并发批次（FunctionTool 的默认值就是 True） | 不证明任务之间独立，更不证明一次运行已经并发或一定提速 |

**放到训练里看。** 动作空间由三块组成：注册了哪些工具、每个工具的参数说明、直接写文字作答。模型能调哪些工具、能填哪些字段、每个字段什么类型，决定了它能做出哪些动作。一次模型调用的整份输出算一个动作，里面可以同时有多个工具调用。工具清单也不是固定的：联网搜索、澄清表单、Skill 工具都看配置注册，撞上限那一步只能写文字；所以记轨迹时要连同当次的工具清单一起存。「漏传预算参数」这类错误正是训练要纠正的行为。奖励不能只看参数填得对不对，还要核对结果是否真的满足约束，否则策略会学会「参数好看、推荐超预算」。

<a id="call-id-2"></a>
## 三、调用和结果怎样配对，并影响下一轮

**这一节在项目里管什么。** 循环能不能正确地「看结果、再决定」，取决于结果有没有配回对应的调用。这件事同时影响三处：模型的上下文、页面上的工具进度，以及将来记录训练轨迹。

一次工具调用包含工具名、参数和调用 ID。工具结果带同一个调用 ID，框架据此把调用和结果联系起来，再把结果加入 Agent 上下文，模型之后才能利用这次观察。

~~~text
用户消息
    |
    v
assistant：调用 category_insight_tool，ID=call_A
    |
    v
tool：返回选购知识，关联 call_A
    |
    v
assistant：调用 product_search_tool，ID=call_B
    |
    v
tool：返回商品结果，关联 call_B
    |
    v
assistant：综合已有结果，生成回答
~~~

调用 ID 不能省略。假设同一轮两次调用 product_search_tool，第一次查日用小背包，第二次查徒步背包，而徒步那次先返回；只看工具名或返回顺序，就可能把两份结果配错。后端的[编排器](../../app/application/agents/orchestrator.py)和页面的事件适配，也都按 tool_call_id 把「开始调用」和「结果收口」连起来。

「Observe → 再次决策」用大白话说：上一步的工具结果放进了下一次模型能读到的上下文，模型才能据此改写检索词、换工具、承认没找到，或者收尾作答。

**模型看到的观察是一段文字。** 工具结果回到上下文时，发给模型的是一条带调用 ID 的文字消息；商品检索给的是一段 JSON 文本，只保留决策要用的字段，太长时框架还会截断并附上提示。页面商品卡用的是另一份数据：商品工具单独发布的业务事件，字段更全。同一次检索，模型和页面看到的内容并不一样。

**工具出错也是一种观察。** 超时、熔断、参数非法时，工具会返回一个明确标成错误的结果，同样配着调用 ID 回到上下文。错误状态不会发给模型；项目的工具和中间件出错时，都在结果文字开头写 `[error]`，模型靠这段文字认出出错。不能把它包装成「成功检索到空列表」：「没有符合条件的商品」和「检索没跑成」，买家听到的回答应该完全不同。

**放到训练里看。** 调用 ID 配对就是轨迹的骨架。训练数据要按「助手发出调用 → 同 ID 的工具结果 → 下一次助手输出」的顺序存，SFT 只让模型学助手那几段，工具结果只作上下文（04 讲 loss mask）。配错一次，模型学到的就是「看着 A 的结果做 B 的决定」。

还有三点影响数据构造：

- **观察要取模型看到的那份。** 训练用的观察是发给模型的工具结果文字，包括 `[error]` 前缀、护栏追加的 `[harness]` 提示和截断提示，不能拿页面商品卡或业务事件代替。评测接缝里的工具结果记录在护栏加提示之前，所以要以下一次模型请求里的消息为准。
- **同轮多个调用，结果按完成先后排。** 每个调用一收口，结果就追加进上下文；同一批并发的调用，谁先完成谁排在前面，与发出顺序无关。ID 保证不配错，但不保证顺序能复现：同样的动作，网络快慢不同，下一步看到的观察顺序就可能不同。
- **上一步的思考不回传。** 模型公开返回的思考内容只做显示，格式化时会被跳过，不进下一次模型输入。记轨迹时，下一步的输入里也不该带上一步的思考，否则和线上看到的不一致。

<a id="dispatch-2"></a>
## 四、子 Agent 怎样作为一个工具被派发

**这一节在项目里管什么。** Globex 是「一个主 Agent 加两个专家」的结构（Supervisor-Workers）：MainAgent 面对买家，SearchAgent 专做检索，TradeAgent 专做下单与查单。架构上的关键选择是：**专家不是独立服务，而是主 Agent 的一个工具。**

主 Agent 在[工具集装配](../../app/application/agents/main_agent.py)时既持有业务工具，也持有 task_dispatch。task_dispatch 对主 Agent 来说是一次工具调用，内部却会新建并运行另一个 Agent，这叫 SubAgent as Tool。

~~~text
MainAgent 的模型
    | 生成 task_dispatch 调用
    v
task_dispatch(subagent_type, demands)
    +-- 选择 SearchAgentFactory 或 TradeAgentFactory
    +-- 新建子 Agent
    +-- 把 demands 作为子任务输入
    +-- 等待 worker.reply(inputs)
    +-- 整理结论、证据引用和核验状态
    |
    v
以工具结果形式回到 MainAgent
~~~

在 [task_dispatch_tool.py](../../app/application/tools/task_dispatch_tool.py) 里按顺序找三处：`worker = ...build()`、`UserMsg(..., demands)`、`await worker.reply(inputs)`。子 Agent 是当前后端进程里新建的 Python 对象，有自己的模型循环、提示词、工具集和 AgentState；每次派发都新建一个，用完即弃，不会另起 Docker 容器或操作系统进程。

子 Agent 状态独立，但护栏是共用的：主 Agent 把自己的顺序检查和重复检测交给两个子 Agent 共用，所以把任务派出去不会让计数重新开始（03 细讲）。

~~~text
主 Agent
    +-- 自己的对话历史与 AgentState
    +-- 生成 demands
             |
             v
       新建的子 Agent
          +-- 子任务描述 demands
          +-- 自己的提示词与业务工具
          +-- 独立 AgentState
          +-- 服务端按配置注入的相关信息
~~~

**子 Agent 看得见什么。** 状态独立不等于没有可信身份：子 Agent 能读到服务端传下来的买家和会话上下文，派发工具还会按配置给 SearchAgent 注入相关的长期偏好（TradeAgent 不注入，偏好影响不了下单）。但它不会自动复制主 Agent 的对话历史。本轮的商品目标、预算、收货地、商品 ID，都要写进自包含的 demands；「按刚才那个要求查一下」撑不起可靠的派发。

**什么时候派。** 主 Agent 的[当前提示词](../../app/application/prompts/globex.yml)给出三类考虑派发的条件：独立的子任务可以并行；子任务的中间信息需要隔离，免得塞满主上下文；子任务内部的调用链较深。一次简单查询或查单，直接调业务工具更省。后端只提供派发能力和护栏，派不派由模型决定。这是一项策略，不是能完全判断业务依赖的确定性分类器。

~~~text
MainAgent 收到目标
    |
    +-- 单步业务工具足够完成？
    |       +-- 是：MainAgent 直接调用
    |
    +-- 有独立可并行的子任务、上下文隔离或较深内部链路？
            +-- 是：考虑 task_dispatch
            +-- 否：继续由主 Agent 处理
~~~

例如“查这件商品现在能否寄中国”可由主 Agent 直接查询；“分别找日用和徒步两种轻便背包，各自比较候选”可考虑拆分；“先找商品，再对选中的 SKU 准备订单确认”有前后依赖，不能忽略前一步结果直接并发。

**子 Agent 交回什么。** 只交结论，不交过程：`summary`、`evidence_refs`、`verified_product_ids`、`unverified_product_ids` 和 `status`。派发工具会对子 Agent 的回复做一道核对：回复里提到的商品或规格 ID，如果在本轮检索结果里找不到，`status` 就标成 `unverified`，`summary` 换成「请用业务工具复核」。主 Agent 这时应查看证据，必要时自己再查。

即使 `status` 是 `completed`，也只说明回复里的 ID 都在本轮证据里出现过，不证明推荐理由都对。「派发工具成功返回」和「子任务的结论可信」是两个层次。

子 Agent 是怎么结束的，也不会传上来。派发工具只取子 Agent 最后一条回复的文字，不看它的结束原因：子 Agent 跑满 6 次后被迫写的总结，同样当成 `summary` 交回，`status` 照样可能是 `completed`。

**放到训练里看。** 派发对训练有两面：

- **好处**：子 Agent 的中间步骤不进主上下文，主轨迹更短。
- **代价**：子 Agent 内部的决策不在主轨迹里，主策略只看到一个结论。但这只是说主 Agent 的上下文里没有：在模型请求和工具结果两处取记录时，子 Agent 的那几步会和主 Agent 的混在一起，记录本身不标是哪个 Agent，要靠提示词和工具清单分开。

所以训练推演先只训主 Agent 自己调工具的那条路径；「派不派、怎么写 demands」是更后面的决策。

<a id="concurrency-2"></a>
## 五、async、并发和实际执行证据

**这一节在项目里管什么。** 派发的一大理由是「可以并行」，但「能并行」「模型想并行」「真的并行了」是三件事。这一节讲清它们各自需要什么证据，免得把一句声明当成提速。

Python 的 `await` 表示等待当前的异步操作，同时让事件循环去处理别的工作。连着写 `await A()` 再 `await B()`，通常要等 A 结束才开始 B。要让两个独立任务重叠，得先把两者都调度起来，再一起等结果。

~~~text
串行：
启动 A → 等 A 完成 → 启动 B → 等 B 完成

并发：
启动 A ───────────────→ A 完成
启动 B ──────────────────────→ B 完成
                    等待两者收齐
~~~

主 Agent 把 task_dispatch 注册为 `is_concurrency_safe=True`。模型在同一轮发出多个调用后，AgentScope 2.0.8 按顺序把它们分批：相邻的可并发调用合成一批，用 `asyncio.gather` 同时执行；不可并发的调用单独成批，按顺序执行。声明只是必要条件，还需要两样：模型确实在同一轮发出了多个适合同时执行的调用；外部模型网关没有因为配额或限流把它们排成队。

~~~text
主模型同轮生成两个 task_dispatch
         |
         v
框架建立可并发批次
    +----+--------------------+
    |                         |
    v                         v
子 Agent A                 子 Agent B
研究日用背包               研究徒步背包
    |                         |
    +------------+------------+
                 |
                 v
          两份结果回到主 Agent
                 |
                 v
              汇总回答
~~~

假设 A、B 单独耗时分别是 5 秒和 8 秒，耗时固定、忽略额外开销，那么串行约 13 秒，并发约 8 秒。这只是学习用的计算，不是项目实测。真实耗时还要算上主模型的决策、子 Agent 的初始化、限流、重试和汇总。

项目的 [verify_parallel.py](../../scripts/verify_parallel.py) 从派发事件里取每次的开始和完成时间，检查执行区间是否重叠，并比较墙钟时间。它要先启动后端、调用真实模型，所以本机没跑过。

三层证据对应三件事：

| 层次 | 证据 | 说明 |
| --- | --- | --- |
| 能力 | 声明可并发 | 工具允许被放进并发批次 |
| 行为 | 模型同一轮发出多个派发 | 模型确实选择了并行 |
| 执行 | 时间区间确实重叠 | 两个任务真的同时在跑 |

并发是否提高了质量、降低了成本，还要另外评测。

<a id="events-2"></a>
## 六、前端看到了什么，后端如何交付事件

**这一节在项目里管什么。** 这是 01 那两条回路里「回到页面」的一条。买家看到的进度、商品卡、确认单和表单，都来自结构化事件，而不是从模型的回答文字里猜出来的。也正因为事件先写进持久的运行日志再推送，页面刷新后才能恢复（03 细讲）。

后端的 [AGUIRunAdapter](../../app/application/agents/ag_ui_adapter.py) 接收两类事件：AgentScope 原生的文本和工具事件，以及商品、派发、确认、表单等业务事件。它把两类事件都转成 AG-UI 事件或状态，写进持久的运行日志，再经 SSE 推回浏览器。整个运行和写日志的过程由 [AGUIRuntime](../../app/presentation/ag_ui_runtime.py) 承载。

~~~text
AgentScope 原生事件                 业务工具事件
文本、工具参数、工具结果             商品、派发、确认等
            |                              |
            v                              v
AGUIRunAdapter.on_agent_event()  AGUIRunAdapter.on_trade_event()
            |                              |
            +---------------+--------------+
                            |
                            v
                   AG-UI 事件或状态
                            |
                            v
                  持久运行日志 → SSE
                            |
                            v
                  浏览器 CommerceClient
                   +--------+--------+
                   |                 |
                   v                 v
               消息与进度         商品等结构化状态
                   +--------+--------+
                            |
                            v
                       React 重新渲染
~~~

前端知识补充：浏览器里的 CommerceClient 维护消息、商品、工具进度、确认单、表单和运行状态这些数据。[onMessagesChanged](../../frontend/src/lib/commerceClient.ts) 更新消息；onStateChanged 更新商品、进度和确认单；onEvent 只保存适量的诊断事件，高频的文字片段和工具参数片段不逐条记录。数据一变，React 就按新数据重画页面。

框架的原生事件有十几种（还包括思考片段、参数片段等），对理解循环最关键的是下面五个时刻，要分清：

| 原生事件 | 当前含义 | 前端大致怎样表现 |
| --- | --- | --- |
| TEXT_BLOCK_DELTA | 模型新生成文本片段 | 逐步更新文本 |
| TOOL_CALL_START | 开始生成某次工具调用 | 记录工具名与调用 ID |
| TOOL_CALL_END | 这次工具调用的参数流结束 | 可以说“参数已就绪” |
| TOOL_RESULT_START | 工具结果开始到来或进入执行阶段 | 进度标为运行中 |
| TOOL_RESULT_END | 工具结果收口，并带状态 | 标为完成或错误 |

~~~text
TOOL_CALL_END：参数已生成完
          |
          v
权限判断和真正的工具执行
          |
          v
TOOL_RESULT_END：结果与状态已返回
~~~

TOOL_CALL_END 不能显示成「查询成功」。商品卡也不是用正则从回答里抠价格：商品工具发布结构化的 `tool.result` 业务事件，适配器据此更新 `state.products`，前端通过 onStateChanged 和 `readProducts()` 拿到结构化商品再渲染。所以页面上的价格以工具结果为准，模型回答里写错了价格，商品卡也不会跟着错。[商品状态适配](../../app/application/agents/ag_ui_adapter.py)、[前端状态订阅](../../frontend/src/lib/commerceClient.ts)

子 Agent 内部调用的是 `worker.reply()`，不是流式接口。它的业务工具事件仍会经 EventBus 上报，页面能看到子任务里的商品和进度；但这不等于页面收到了子 Agent 完整的模型文字和内部历史。

**放到训练里看。** 事件流是页面的数据源，不是训练轨迹：

- 高频片段只做显示，不完整保存。
- 遥测里的正文已经脱敏。

要记录训练轨迹，得在模型请求和工具结果这两处直接取完整的输入输出（04 和训练推演细讲）。「参数已就绪」和「结果收口」的区分，在训练里同样重要：只有收口的结果才算环境给出的观察。

## 60 秒口述与面试追问

**60 秒口述。** Globex 在对话里的能力，查商品、查知识、准备订单确认，都是模型通过工具完成的。MainAgent 在一个循环里工作：模型根据当前上下文生成工具名和参数，后端校验并执行，结果带着调用 ID 回到上下文，模型再决定继续还是作答；所以一条用户消息可以触发多次模型和工具调用，主 Agent 的迭代上限是 15。遇到可以并行、需要隔离或调用链很深的子任务，主 Agent 用 `task_dispatch` 派给 SearchAgent 或 TradeAgent。对主 Agent 来说这只是一次工具调用；子 Agent 有独立状态、看不到主对话，所以任务说明必须自包含。证据要分层：模型说调用了不算，要看执行事件；参数生成完不算成功，要看结果收口；声明可并发不算并发，要看时间区间是否重叠。放到训练里看，这个循环就是动作与观察的序列，也就是将来要记录、要训练的轨迹。

**面试追问。**

| 追问 | 答题要点 |
| --- | --- |
| 怎么证明工具真的被调用了？ | 看结构化的调用事件和同一 ID 的结果事件，不看模型文字；再核对相应的业务状态 |
| 子 Agent 能看到主对话吗？派发时最容易犯什么错？ | 看不到完整历史，只拿到任务说明和可信身份；最常见的错是写「按刚才的要求查一下」这种不自包含的说明 |
| 预算做成工具参数，就能保证不超预算吗？ | 不能。模型可能漏传；即使传了，当前也只比较单件价，不含运费和关税 |
| 什么时候不该派子 Agent？ | 单步查询由主 Agent 直接调工具更省；派发多一层模型调用、上下文和汇总的成本；有前后依赖的步骤不能并发 |
| 这个循环和 Agentic RL 有什么关系？ | 每次选工具是动作，工具结果是观察，整串就是轨迹；训练需要准确记录每一步的输入、输出和配对关系。调用 ID 是配对的基础；记录要在模型请求和工具结果两处直接取，事件流只给页面用，片段不全、正文脱敏；终止原因看结束事件的 `finished_reason` |
