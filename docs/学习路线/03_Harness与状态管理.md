# 第三阶段 Harness 与状态管理

本阶段学习 Globex 怎样维持一段持续多轮的选购，并在整理上下文、用户确认、刷新页面和执行失败时保持状态正确。第一阶段解决系统由什么组成，第二阶段解决 Agent 怎样调用工具；第三阶段对应的是项目里的“继续比较、整理上下文、保存偏好、确认订单、恢复页面和停止执行”。

建议用约 60 分钟学习，另用约 25 分钟画图与答题。以本地源码提交 8cbd4d6b94eb9713952d3bd8f050da176accdca1 为参照；工作区还有此前的本机环境准备改动。本章是源码学习，场景与示意图不是本次真实模型运行。

| 你在 Globex 中做的事 | 本阶段学它背后的什么 |
| --- | --- |
| 预算改成 150 元，再比较前两个商品 | 当前需求、历史候选和会话状态怎样关联 |
| 点击“整理上下文” | 什么保留、什么归档，整理后怎样安全保存 |
| 记住以后偏好轻便设计 | 长期记忆怎样审批、写入和再次召回 |
| 生成确认单，再点击批准 | 模型建议怎样成为用户授权的业务操作 |
| 刷新、断线重连、点击停止 | 页面与后端执行怎样恢复、取消和收尾 |
| 工具报错或反复搜索 | 超时、熔断和循环提示各控制什么 |

## 一、用一段选购过程串起本阶段

~~~text
第 1 轮：找 200 元内、可寄中国的保温杯
    |
第 2 轮：这次预算改为 150 元，比较前两个候选
    |
第 3 轮：记住以后偏好轻便设计
    |
继续搜索几轮，历史和商品结果越来越多
    |
点击“整理上下文”
    |
为选中商品生成订单确认单
    |
批准后断网，再刷新页面
~~~

你要能解释五个问题：新预算怎样替代当前任务里的旧预算；移出模型上下文的旧商品结果能否回查；一次性预算为什么不自动变成长期偏好；待批准确认单和已创建订单有什么区别；批准后重试为什么不应重复扣库存。

Harness 指支撑 Agent 工作的工程机制。本项目的状态管理、权限、恢复、预算和工具可靠性代码分别处理上述问题。机制存在只证明有相应实现，具体效果仍需场景验证。

## 二、分清项目保存的六类信息

| 信息 | 通俗解释 | Globex 例子 |
| --- | --- | --- |
| Context，上下文 | 本次模型请求实际能看到的材料 | 消息、工具结果、摘要及注入的相关偏好 |
| AgentState，会话运行状态 | Agent 当前工作的记录 | 上下文、摘要、任务及待审批工具状态 |
| 原始证据 | 当时真正查到了什么 | 某次商品顺序、报价、SKU、查询条件 |
| 长期记忆 | 跨会话保留的买家偏好 | 偏好轻便设计 |
| 运行日志与页面投影 | 用来恢复页面的已保存消息、事件和状态 | 文本、商品卡、运行终态 |
| 业务账本 | 订单、库存与确认单的业务事实 | 待批准确认、已建订单、剩余库存 |

Checkpoint（检查点）在本章指会话恢复所需的保存记录。上下文治理会保存摘要、工作状态及相关版本信息；这与模型权重训练的 checkpoint 不是同一个对象。

~~~text
原始对话 / 商品证据 / 长期偏好 / 当前交易事实
                      |
                      | 按本轮任务组织
                      v
              本次模型读取的 Context
                      |
                      v
                 Agent 继续工作
                      |
           +----------+----------+
           |                     |
           v                     v
    更新 AgentState        产生运行事件
           |                     |
           v                     v
    保存状态与检查点       日志 → 前端展示

订单、库存与确认单由业务账本维护。
~~~

数据库保存了某段内容，不意味着下一次模型会自动读取它；后端需要选择和组织输入。Context 的工作集、页面显示状态和持久业务记录因此各有职责。

先按问题找入口：[SessionRegistry](../../app/application/agents/main_agent.py)取得与保存会话；[ContextEvidenceStore](../../app/infrastructure/persistence/context_evidence.py)保存历史证据；[AGUIJournal](../../app/infrastructure/ag_ui_journal.py)保存运行事件；[交易存储](../../app/infrastructure/persistence/sql/trade_store.py)维护订单、库存及确认。

## 三、整理上下文怎样保留重要信息

本节学习页面中的“本次选购摘要”和“整理上下文”。长对话把许多候选反复送给模型，输入会持续增长。分层治理会保护当前相关信息，把适合归档的旧商品结果移出工作集，并留下回查引用。

~~~text
商品工具返回结果
    |
    +-- 完整结果保存到证据存储 → 获得 result_ref
    |
    +-- 决策所需内容进入模型上下文
            |
            v
      后续对话继续增长
            |
            v
      检查哪些内容可以整理
            +-- 当前轮、近期轮次、未完成工具配对：保护
            +-- 选中或比较中的重要信息：按规则保护
            +-- 已使用且可以归档的旧结果：考虑替换
                            |
                            v
                用引用替换旧结果正文
                            |
                            v
             需要细节时调用 conversation_fact_lookup
~~~

result_ref 可以理解成“原始证据的取件编号”。当前模型输入只保留引用时，原始列表仍能按批次、位置或商品标识回查。

分层代码记录某结果是否随一次成功模型调用进入输入，作为“已读取”的运行信号。这只证明模型获得过这次读取机会，不证明它理解正确。直接删掉尚未进入模型输入的新结果，会失去第一次利用该结果的机会。

历史价格和当前库存必须分开判断：历史证据可以说明第一轮第三个商品当时多少钱；现在是否有货仍需要新业务查询。

项目支持 legacy 与 layered 两种策略，配置读取缺省值是 legacy，而 .env.example 配置为 layered。本节学习 LayeredContextMiddleware 分支；运行是否走它，需要核对实际配置和[中间件装配](../../app/infrastructure/tracing.py)。先看 [prune()](../../app/infrastructure/context_governance.py) 和 [conversation_fact_lookup](../../app/application/tools/conversation_fact_lookup.py)，分别理解保护、归档与回查。

归档后仍需要压缩历史时，再尝试摘要：

~~~text
保留整理前状态
    |
    v
归档原始材料 → 生成摘要候选
    |
    v
检查格式和部分来源约束
    |
    +-- 通过：接受候选，准备保存新状态
    +-- 失败：保留诊断，恢复整理前状态
~~~

[摘要流程 run()](../../app/infrastructure/context_governance.py)检查商品标识、证据引用及部分金额库存来源。这种检查不能证明完整语义正确。旧预算和新预算都出现在历史里时，“这个数字曾出现过”并不足以证明它仍适用于当前任务；当前工作状态、最新查询与交易校验仍须发挥作用。

补充三个概念：上下文整理改变下一次交给模型的信息；持久化把信息存到数据库或文件；缓存复用已得到的结果或计算。整理上下文并不等于删除原始证据，缓存命中也不等于模型学会了长期偏好。

## 四、一个“整理”按钮怎样成为可追踪的维护任务

本节学习前端按钮与后端异步操作的配合。手动整理使用独立维护接口，不生成新的买家聊天消息，也不调用交易工具。

~~~text
前端读取当前上下文与 revision
    |
    v
买家点击“整理上下文”
    |
    v
POST /commerce/context/compact
携带 session_id、request_id、expected_revision
    |
    v
后端校验会话、版本、忙碌和待审批情况
    |
    v
创建或返回整理操作，给出 operation_id；HTTP 202
    |
    v
前端按 operation_id 查询状态
    |
    +-- running：继续等
    +-- completed / noop / failed / interrupted：更新页面并重读状态
~~~

| 名称 | 人话解释 |
| --- | --- |
| request_id | 识别这一次整理请求，用于处理重复提交 |
| operation_id | 后端维护任务编号，用于查进度 |
| revision | 当前会话数据版本 |
| HTTP 202 | 已接受处理，单凭状态码不能认定整理完成 |
| noop | 检查后无需修改，不表示失败 |

前端在忙碌、待审批或整理过程中禁用按钮；后端独立检查同类条件。按钮禁用是交互限制，数据库保护不能只依赖它。[ContextWorkspace.tsx](../../frontend/src/components/ContextWorkspace.tsx)管理读取、提交和轮询；[context_workspace.py](../../app/presentation/context_workspace.py)声明接口；[ContextService](../../app/application/agents/context_service.py)执行维护操作。

旧执行者可能在停顿后恢复，尝试保存过时状态：

~~~text
旧执行者读取预算 200，revision=7
                    |
                    | 中途停顿
                    v
另一有效执行保存预算 150，revision=8
                    |
                    v
旧执行者恢复，试图按 revision=7 保存
                    |
                    v
数据库发现版本或票据不匹配 → 拒绝旧写入
~~~

revision 说明数据版本，fence 是递增执行票据，CAS（比较后写入）要求持有版本与数据库当前版本相符。[save_claim()](../../app/infrastructure/persistence/sql/session_store.py)在 SQLite 事务内核对 owner、revision 和 fence，保存 AgentState 与相应 checkpoint。这个边界避免旧执行者覆盖新状态，不应扩大成跨任意存储的全局事务保证。

## 五、长期偏好和订单分别怎样确认

本节学习长期记忆维护与订单确认卡。“这次预算 150 元”属于任务约束；“以后偏好轻便设计”才表达稳定偏好。助手说过什么不自动成为买家事实。

~~~text
对话中明确要求长期记忆变更
    |
    v
模型调用记忆工具
    |
    v
MemoryPermissionMiddleware 要求本次审批
    |
    v
前端展示待批准 / 拒绝的操作
    |
    v
买家提交决定 → 后端核对当前待处理调用
    |
    +-- 批准：恢复该工具执行，保存记忆
    +-- 拒绝：不执行这次变更
~~~

[tool_confirmation.py](../../app/application/agents/tool_confirmation.py)把批准/拒绝关联到当前挂起调用。前端不能借审批换工具或追加永久放行规则。页面上买家直接编辑偏好是显式操作，与模型请求修改记忆的入口不同。

之后的会话按当前问题召回偏好，再注入模型输入。语义召回可以先理解为“找出含义上与当前任务相关的偏好”；项目还保留负向约束，并核对记忆的当前版本。[记忆中间件](../../app/application/memory/middleware.py)、[语义偏好存储](../../app/infrastructure/semantic_memory.py)分别对应读路径与存储。

订单走持久业务确认：

~~~text
create_order_tool / cancel_order_tool
    |
    v
准备持久确认单，此时尚未完成实际创建 / 取消交易
    |
    v
前端展示确认卡 → 买家批准或拒绝
    |
    v
POST /commerce/confirmations/{id}/resolve
    |
    v
校验买家、会话、确认内容、有效期和业务条件
    |
    +-- 批准：事务内处理订单、库存和确认结果
    +-- 拒绝：保存拒绝决定
~~~

[ConfirmationService.resolve()](../../app/application/usecases/confirmation_service.py)没有注册为模型工具。聊天文字“同意”或模型转述不能直接替代真实确认请求。

后端知识补充：事务把相关数据库操作作为一个整体处理，例如订单、扣库存与确认结果保持一致；幂等保证同一次业务决定重复到达时不重复产生相同副作用。

~~~text
第一次批准：
提交订单 + 扣库存 + 保存确认结果 → 响应途中断网

同一确认的批准重试：
找到已提交结果 → 返回原结果 → 不重复创建订单或扣库存
~~~

[交易存储 resolve_confirmation()](../../app/infrastructure/persistence/sql/trade_store.py)对同一确认的相同决定返回原结果，对相反决定拒绝修改。当前本地订单确认金额只含商品，不含运费和关税；它与商品搜索卡到手价的口径需要分别看字段，不能自动视为同一金额。[交易确认与库存说明](../交易确认与库存验证-2026-09-09.md)

## 六、刷新、断网、停止、重启各恢复什么

本节学习当前网页的恢复合同。一次后端运行与一个浏览器订阅连接具有不同生命周期：

~~~text
后端执行任务 → 事件追加到持久日志
                        |
                        v
浏览器收到序号 1、2、3……
                        |
                        X 网络中断
                        |
                        v
重新请求最后已收序号之后的日志
                        |
                        v
收到 4、5、6……
~~~

Cursor（游标）表示已经读到的位置。[recoveringFetch.ts](../../frontend/src/lib/recoveringFetch.ts)会核对序号、忽略重复事件并用 GET 重读已有运行的日志；不会为断线恢复反复 POST 新的模型运行。

| 情况 | 当前项目的处理边界 |
| --- | --- |
| 刷新、订阅断线 | 恢复已有消息和事件，活跃后端任务可以继续 |
| 点击停止 | 提交明确取消请求，并确认服务端状态 |
| 停止请求网络失败 | 保留“尚未确认停止”的不确定状态 |
| 后端关闭或执行租约失效 | 未完成运行标中断，已保存内容可恢复查看 |
| 下一轮继续提问 | 从保存的会话状态进入新一轮处理 |
| 订单已提交后停止 Agent | 不自动撤销交易，取消订单走自己的确认流程 |

恢复页面和会话内容，不等于恢复模型进程内部执行位置。未完成模型调用不能仅凭日志存在就声称自动续跑。[AGUIRuntime](../../app/presentation/ag_ui_runtime.py)控制运行，前端 [commerceClient.ts](../../frontend/src/lib/commerceClient.ts)中的 stop()/detach() 区分停止运行与离开订阅。

第 14 章仍保留快照损坏后“按新会话继续”的旧示例；当前 [SessionRegistry](../../app/application/agents/main_agent.py)会在快照损坏时抛错，避免空状态覆盖历史。恢复行为以当前代码为准。

## 七、工具报错和反复调用时的护栏

本节学习买家看到的等待、错误提示与执行收尾背后的代码。

| 机制 | 控制的问题 | 边界 |
| --- | --- | --- |
| max_iters | 循环次数过多 | 不能保证每一步都有价值 |
| 工具超时 | 单次调用迟迟不返回 | 应回传明确错误，不能伪装成没有商品 |
| 熔断 | 同一工具持续失败还被反复调用 | 冷却后允许探测，失败可再熔断 |
| LoopDetector | 连续调用同名工具 | 注入收敛提示，不是语义无进展判定或强制停止 |
| Token 预算 | 控制消耗与收尾行为 | 是否生效须看配置 |

~~~text
Agent 请求工具
    |
    v
执行适用的权限与调用检查
    |
    v
工具中间件
    +-- 判断熔断
    +-- 限制等待时间
    +-- 处理成功结果或错误
            |
            v
结果 / 明确错误回到 Agent
            |
            v
重试、换策略、说明失败或收尾
~~~

[resilience.py](../../app/infrastructure/resilience.py)把超时或熔断表现为错误结果；[LoopDetector](../../app/application/harness/loop_detector.py)按连续工具名称检查，即使参数不同仍可能提示。触发次数不能直接当作成功阻止死循环的次数。排查时要区分模型未回答、工具超时、运行取消与浏览器断线。

### 作业 B 参考主干

浏览器                确认接口                  数据库
  |---- 批准 C --------->|---- 开启事务 ---------->|
  |                      |    校验、创建订单       |
  |                      |    扣库存、存确认结果   |
  |                      |<--- 提交成功 -----------|
  X 响应途中断网         |

同一确认改成相反决定时，后端拒绝修改已作出的决定。浏览器未收到响应不证明首次失败，应查询或接收服务端的持久结果。

### 八题参考答案

1. 本次预算属于当前约束，稳定偏好经用户明确保存后可成为长期记忆；历史报价属于证据，待批准订单属于业务确认状态。它们生命周期不同，不能都自动写成长期偏好。
2. 过早归档会让模型还没获得读取完整新结果的机会就只剩引用；代码记录“进入成功模型调用”也不能证明理解正确。历史库存仅说明当时观察，当前库存需重新查询。
3. HTTP 202 不能证明完成，前端应检查操作状态并按 operation_id 查询。摘要检查只覆盖已实现的格式和来源约束，无法自动证明新旧需求、时间与语义全部正确。
4. 直接覆盖可能丢失新需求和进度。revision 检查数据版本，fence 检查执行票据；数据库保存时共同校验，拒绝旧执行者并要求重读。
5. 记忆工具通过原生审批挂起并恢复；订单工具先准备持久确认资源，实际交易由用户动作接口提交。历史摘要不构成授权，不能代替待审批调用和确认单的真实决定。
6. 后端根据同一确认及已提交结果做幂等处理，并把订单、库存和确认结果放进一致事务。禁用按钮挡不住网络重试、多标签页和直接请求。
7. 断线影响订阅，停止是明确取消，重启会中断旧进程的未完成执行。任何一种都不能仅凭保存了日志就宣称恢复模型内部执行栈；页面和会话各有恢复路径。
8. 超时限制一次等待，熔断暂时阻止持续失败调用，LoopDetector 提示减少重复行为；循环提示本身不会强制停止，迭代上限和预算另有职责。

验收：合上资料解释“整理为什么不等于删历史”“刷新为什么不等于重新执行”“批准重试为什么不应再扣库存”，然后定位 ContextService.start()、save_claim()、ConfirmationService.resolve() 和 recoveringFetch.ts，指出它们各保护哪种项目状态。
