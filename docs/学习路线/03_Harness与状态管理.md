# 第三阶段 Harness 与状态管理

<a id="overview-3"></a>
## 总览：03 在整个项目里做什么

**在整个项目里的位置。** 01 讲一次请求怎样穿过各层，02 讲模型在一次请求里怎样循环。真实的选购却是连续多轮：改预算、比较候选、记住偏好、整理上下文、确认订单、刷新页面。03 讲支撑层（Harness）里和状态有关的那一半：系统靠什么在这些情况下不丢信息、不乱写、不重复扣库存。它对应[纵览](README.md#overview-all)七站里 ③ 的状态部分，和 ⑥ 的保存与恢复。

你在页面上做的事，和 03 学的机制一一对应：

| 你在 Globex 中做的事 | 本篇学它背后的什么 |
| --- | --- |
| 预算改成 250 元，再比较前两个商品 | 当前需求、历史候选和会话状态怎样关联 |
| 点击「整理上下文」 | 什么保留、什么归档，整理后怎样安全保存 |
| 记住以后偏好轻便设计 | 长期记忆怎样审批、写入和再次召回 |
| 生成确认单，再点击批准 | 模型建议怎样成为用户授权的业务操作 |
| 刷新、断线重连、点击停止 | 页面与后端执行怎样恢复、取消和收尾 |
| 工具报错或反复搜索 | 超时、熔断和循环提示各控制什么 |

**要回答的问题。** **一段多轮选购里，Globex 保存了哪些信息？在整理上下文、审批、刷新和出错时，它怎样做到不丢、不乱、不重复？**

**答案。**

- 六类信息各管各的：模型这次看到的上下文、会话运行状态、原始证据、长期记忆、运行日志、业务账本。数据库里存了，不等于下一次模型就会读到，后端要挑选和组织。
- 改变状态的动作都要有版本或授权：整理上下文是一个带数据版本和执行票据的维护任务，过时的执行者写不进来；长期记忆的变更要买家审批当前这一次调用；订单走持久确认单，同一个决定重复到达也只扣一次库存。
- 恢复的是已经保存的内容，不是模型的执行位置；超时、熔断和迭代上限把失败变成明确的结果，而不是悄悄卡住或编造，重复检测只给模型一条换办法的提示。

**放到训练推演里看。** 强化学习要求环境能重置、轨迹能复现。Globex 的库存和会话都持久保存，不能一键重置，所以训练时每条轨迹都要用隔离的数据目录；审批要买家亲手点，训练时要用规则化的模拟用户代替；上下文整理会改变模型看到的观察，训练和评测时这套策略要固定下来，否则效果变化说不清来自哪里。

## 文字版导读：先把全篇顺一遍

第一次读，先把这一节读完，再按链接进细节；复习时只读这一节。

**第一节：一段多轮选购。** 本篇用一条连续的选购串起所有机制：先找 300 元内、可寄中国的轻便背包；再把预算改成 250 元，比较前两个候选；然后让系统记住「以后偏好轻便设计」；继续搜几轮后点击「整理上下文」；为选中的商品生成确认单；批准后断网，再刷新页面。要回答五个问题：新预算怎样替代旧预算；移出上下文的旧结果还能不能回查；一次性的预算为什么不会变成长期偏好；待批准的确认单和已创建的订单有什么区别；批准后重试为什么不会重复扣库存。详见[一、用一段选购过程串起本阶段](#story-3)。

**第二节：六类信息各管各的。**

- 上下文：这次模型请求实际看到的材料。
- 会话运行状态（AgentState）：Agent 当前工作的记录。
- 原始证据：当时真正查到的商品顺序、报价和规格。
- 长期记忆：跨会话保留的买家偏好。
- 运行日志：用来恢复页面的消息、事件和状态。
- 业务账本：订单、库存和确认单。

它们生命周期不同，存放的地方也不同。最重要的一句话是：存了不等于模型会读到，下一次给模型看什么，要由后端挑选和组织。详见[二、分清项目保存的六类信息](#state-kinds-3)。

**第三节：整理上下文，不等于删历史。** 长对话会把候选反复送给模型，输入越来越长。分层治理会保护当前轮、最近几轮、未配对完的工具调用，以及正在比较的重要信息；把已经用过的旧商品结果移出工作集，只留一个「取件编号」（result_ref），需要时再用回查工具按批次、位置或商品标识找回原文。仍然太长时再生成摘要，摘要要过格式和来源检查，不通过就恢复整理前的状态。两个判断：历史证据能说明当时多少钱，现在有没有货要重新查；摘要检查只覆盖格式和部分来源，不能证明语义全对。代码默认用 legacy 策略，`.env.example` 配的是 layered，本篇学的是 layered 分支，实际走哪条要看配置。详见[三、整理上下文怎样保留重要信息](#context-3)。

**第四节：一个按钮背后的维护任务。** 「整理上下文」不是一条聊天消息，而是一个独立的维护任务：前端带着请求编号和期望的数据版本提交，后端检查会话是否忙碌、有没有待审批，返回 HTTP 202 和操作编号，前端按编号查进度。202 只表示「已接受」，不表示完成；noop 表示无需修改，不是失败。并发保护靠数据版本加递增的执行票据：数据库在事务里核对两者，过时的执行者恢复后再写，会被拒绝。前端禁用按钮只是交互限制，真正的保护在后端。详见[四、一个「整理」按钮怎样成为可追踪的维护任务](#compaction-op-3)。

**第五节：长期偏好和订单，两套授权。** 「这次预算 250 元」是任务约束，「以后偏好轻便设计」才是稳定偏好；助手说过的话也不会自动变成买家事实。记忆变更走工具审批：模型调用记忆工具时挂起，买家批准或拒绝的只是当前这一次调用，不能借机换工具或加永久放行。订单走持久确认单：模型只能准备确认单，真正的创建或取消要买家通过确认接口提交；后端在一个事务里处理订单、库存和确认结果，同一个决定重复到达返回原结果，不重复扣库存，相反的决定会被拒绝。另外，确认单金额只含商品，不含运费和关税，和商品卡上的到手价不是一个口径。详见[五、长期偏好和订单分别怎样确认](#approval-3)。

**第六节：恢复了什么，没恢复什么。** 后端运行和浏览器订阅是两条生命周期：断线时后端可以继续跑，事件追加进日志，浏览器重连后按游标接着读，不会为了恢复重新发起模型运行。停止是明确的取消请求；后端关闭或执行租约失效时，未完成的运行标为中断，已保存的内容仍能查看；已经提交的订单不会因为停止 Agent 而撤销。一句话：恢复的是页面和会话内容，不是模型进程内部的执行位置。会话快照损坏时，系统会报错，而不是用空状态覆盖历史。详见[六、刷新、断网、停止、重启各恢复什么](#recovery-3)。

**第七节：护栏把失败变成明确结果。** 迭代上限防止循环无限进行；工具超时防止一次调用迟迟不返回；熔断防止对持续失败的工具反复调用；重复检测在模型拿同样参数反复得到同样结果时，提示它换办法或直接作答；Token 预算控制消耗，是否生效看配置。它们共同的原则是：超时、熔断要表现成明确的错误交给模型，不能伪装成「没有商品」；重复检测只提示、不强制停止。排查问题时，要分清模型没回答、工具超时、运行被取消和浏览器断线。详见[七、工具报错和反复调用时的护栏](#guards-3)。

**补充一节：正文之外的机制。** 合并上游后，支撑层多了几样默认生效的东西：会话第一次运行时固定一个 Prompt 版本，模型也按轮冻结，买家中途换模型只影响下一轮；执行记录把每一步写进运行日志，重启或停止时如实标成中断或取消；下单前要在本会话的检索证据里找到商品；子 Agent 和主 Agent 共用护栏。还有几项默认关闭、要通过收益验收才开：显式 Prompt Cache 标记与稳定前缀、回答被截断时的有限续写。另有一条在 layered 策略下生效的规则：买家明确要求重新核验时强制先查，问的历史商品整批都在上下文里时直接作答。这条规则替模型做了「要不要补证据」的决定，训练推演时要特别注意。详见[补充：正文之外的状态与支撑机制](#upstream-3)。

**作业与验收。** 作业 A，画「整理后继续选购」：预算从 300 改成 250，整理上下文后再问第一轮第三个背包当时多少钱、现在还有没有货。作业 B，画「批准后断网」的时间线：浏览器、接口、数据库三条线。作业 C，八个问题。验收时合上资料，解释「整理为什么不等于删历史」「刷新为什么不等于重新执行」「批准重试为什么不会再扣库存」，并指出几处关键代码各保护哪种状态。详见[九、作业](#assignments-3)和[十、参考答案与验收](#answers-3)。

## 一、用一段选购过程串起本阶段

**这一节在项目里管什么。** 01 讲一次请求怎样穿过各层，02 讲一个回合里模型怎样循环。但真实的买家不会只发一条消息：改预算、记偏好、整理上下文、下确认单、刷新页面，全都发生在同一段会话里。03 用下面这条选购线，把支撑层里和状态有关的机制全部串起来。

~~~text
第 1 轮：找 300 元内、可寄中国的轻便背包
    |
第 2 轮：这次预算改为 250 元，比较前两个候选
    |
第 3 轮：记住以后偏好轻便设计
    |
继续搜索几轮，历史和商品结果越来越多
    |
点击“整理上下文”
    |
为选中商品生成订单确认单
    |
批准后断网，再刷新页面
~~~

你要能解释五个问题：新预算怎样替代当前任务里的旧预算；移出模型上下文的旧商品结果能否回查；一次性预算为什么不自动变成长期偏好；待批准确认单和已创建订单有什么区别；批准后重试为什么不应重复扣库存。

Harness 指支撑 Agent 工作的工程机制。本项目的状态管理、权限、恢复、预算和工具可靠性代码分别处理上述问题。机制存在只证明有相应实现，具体效果仍需场景验证。

**放到训练里看。** 这条线上的每一步都会改变状态或依赖状态：改预算改变当前约束，审批改变记忆，整理改变模型看到的观察。训练环境（[06](06_训练推演_澄清检索补证.md#overview-6)）要在每条轨迹里重建或绕开它们——这正是 03 的机制直接决定训练环境设计的地方。

## 二、分清项目保存的六类信息

**这一节在项目里管什么。** 这是全篇的底图。后面每一节讲的整理、审批、恢复、护栏，都是这六类信息里某一类的写入或读出路径；不知道信息分几类、各存在哪，就说不清每种保护在保护什么。

| 信息 | 通俗解释 | Globex 例子 |
| --- | --- | --- |
| Context，上下文 | 本次模型请求实际能看到的材料 | 消息、工具结果、摘要及注入的相关偏好 |
| AgentState，会话运行状态 | Agent 当前工作的记录 | 上下文、摘要、任务及待审批工具状态 |
| 原始证据 | 当时真正查到了什么 | 某次商品顺序、报价、SKU、查询条件 |
| 长期记忆 | 跨会话保留的买家偏好 | 偏好轻便设计 |
| 运行日志与页面投影 | 用来恢复页面的已保存消息、事件和状态 | 文本、商品卡、运行终态 |
| 业务账本 | 订单、库存与确认单的业务事实 | 待批准确认、已建订单、剩余库存 |

Checkpoint（检查点）在本章指会话恢复所需的保存记录。上下文治理会保存摘要、工作状态及相关版本信息；这与模型权重训练的 checkpoint 不是同一个对象。

~~~text
原始对话 / 商品证据 / 长期偏好 / 当前交易事实
                      |
                      | 按本轮任务组织
                      v
              本次模型读取的 Context
                      |
                      v
                 Agent 继续工作
                      |
           +----------+----------+
           |                     |
           v                     v
    更新 AgentState        产生运行事件
           |                     |
           v                     v
    保存状态与检查点       日志 → 前端展示

订单、库存与确认单由业务账本维护。
~~~

数据库保存了某段内容，不意味着下一次模型会自动读取它；后端需要选择和组织输入。Context 的工作集、页面显示状态和持久业务记录因此各有职责。

先按问题找入口：[SessionRegistry](../../app/application/agents/main_agent.py)取得与保存会话；[ContextEvidenceStore](../../app/infrastructure/persistence/context_evidence.py)保存历史证据；[AGUIJournal](../../app/infrastructure/ag_ui_journal.py)保存运行事件；[交易存储](../../app/infrastructure/persistence/sql/trade_store.py)维护订单、库存及确认。

**放到训练里看。** 训练轨迹用的消息序列（06 第二节），就是第一类「上下文」逐轮的快照；奖励核对「本轮查到过什么」用第三类「原始证据」的口径，但商品事实不读证据：独立判定回到商品目录按到手价重算，不复用工具存下的结果（[05 第七节](05_商品检索与前后端闭环.md#outlets-5)）；而记录接缝（模型请求和工具结果两处，见 [02 第三节](02_AgentLoop与子Agent派发.md#call-id-2)）拿到的正是这两类信息的原始形态。六类分清了，才知道训练时要记录哪几类、可以不记录哪几类。

## 三、整理上下文怎样保留重要信息

**这一节在项目里管什么。** 02 的循环每走一步，工具结果就往上下文里塞一批商品。多轮之后输入越来越长：贵、慢，还可能撞上模型的长度上限。这一节讲的「整理」，就是控制输入增长的机制——它不删历史，只改变下一次模型看到什么。

本节学习页面中的“本次选购摘要”和“整理上下文”。长对话把许多候选反复送给模型，输入会持续增长。分层治理会保护当前相关信息，把适合归档的旧商品结果移出工作集，并留下回查引用。

~~~text
商品工具返回结果
    |
    +-- 完整结果保存到证据存储 → 获得 result_ref
    |
    +-- 决策所需内容进入模型上下文
            |
            v
      后续对话继续增长
            |
            v
      检查哪些内容可以整理
            +-- 当前轮、近期轮次、未完成工具配对：保护
            +-- 选中或比较中的重要信息：按规则保护
            +-- 已使用且可以归档的旧结果：考虑替换
                            |
                            v
                用引用替换旧结果正文
                            |
                            v
             需要细节时调用 conversation_fact_lookup
~~~

result_ref 可以理解成“原始证据的取件编号”。当前模型输入只保留引用时，原始列表仍能按批次、位置或商品标识回查。

分层代码记录某结果是否随一次成功模型调用进入输入，作为“已读取”的运行信号。这只证明模型获得过这次读取机会，不证明它理解正确。直接删掉尚未进入模型输入的新结果，会失去第一次利用该结果的机会。

历史价格和当前库存必须分开判断：历史证据可以说明第一轮第三个商品当时多少钱；现在是否有货仍需要新业务查询。

项目支持 legacy 与 layered 两种策略，配置读取缺省值是 legacy，而 .env.example 配置为 layered。本节学习 LayeredContextMiddleware 分支；运行是否走它，需要核对实际配置和[中间件装配](../../app/infrastructure/tracing.py)。先看 [prune()](../../app/infrastructure/context_governance.py) 和 [conversation_fact_lookup](../../app/application/tools/conversation_fact_lookup.py)，分别理解保护、归档与回查。

归档后仍需要压缩历史时，再尝试摘要：

~~~text
保留整理前状态
    |
    v
归档原始材料 → 生成摘要候选
    |
    v
检查格式和部分来源约束
    |
    +-- 通过：接受候选，准备保存新状态
    +-- 失败：保留诊断，恢复整理前状态
~~~

[摘要流程 run()](../../app/infrastructure/context_governance.py)检查商品标识、证据引用及部分金额库存来源。这种检查不能证明完整语义正确。旧预算和新预算都出现在历史里时，“这个数字曾出现过”并不足以证明它仍适用于当前任务；当前工作状态、最新查询与交易校验仍须发挥作用。

补充三个概念：上下文整理改变下一次交给模型的信息；持久化把信息存到数据库或文件；缓存复用已得到的结果或计算。整理上下文并不等于删除原始证据，缓存命中也不等于模型学会了长期偏好。

**放到训练里看。** 整理会改变模型看到的观察：同样一段对话，整理前后模型下一步的输入不一样。所以训练和评测必须用同一套整理策略，否则同一个策略、同一个任务，观察分布也会漂移，效果变化说不清来自哪里。06 的训练环境不挂这套中间件，等于「无整理版本」，是和线上的差距之一；真要在线上录轨迹，归档后留下的 result_ref 引用也是模型实际看到的观察，要原样记进轨迹。

<a id="compaction-op-3"></a>
## 四、一个“整理”按钮怎样成为可追踪的维护任务

**这一节在项目里管什么。** 整理上下文不是买家说的一句话，也不是模型发起的工具调用——它是绕过对话流、直接改写会话状态的维护操作。正因为绕过了常规路径，它需要自己的追踪和保护：编号、版本、票据、独立接口。

本节学习前端按钮与后端异步操作的配合。手动整理使用独立维护接口，不生成新的买家聊天消息，也不调用交易工具。

~~~text
前端读取当前上下文与 revision
    |
    v
买家点击“整理上下文”
    |
    v
POST /commerce/context/compact
携带 session_id、request_id、expected_revision
    |
    v
后端校验会话、版本、忙碌和待审批情况
    |
    v
创建或返回整理操作，给出 operation_id；HTTP 202
    |
    v
前端按 operation_id 查询状态
    |
    +-- running：继续等
    +-- completed / noop / failed / interrupted：更新页面并重读状态
~~~

| 名称 | 人话解释 |
| --- | --- |
| request_id | 识别这一次整理请求，用于处理重复提交 |
| operation_id | 后端维护任务编号，用于查进度 |
| revision | 当前会话数据版本 |
| HTTP 202 | 已接受处理，单凭状态码不能认定整理完成 |
| noop | 检查后无需修改，不表示失败 |

前端在忙碌、待审批或整理过程中禁用按钮；后端独立检查同类条件。按钮禁用是交互限制，数据库保护不能只依赖它。[ContextWorkspace.tsx](../../frontend/src/components/ContextWorkspace.tsx)管理读取、提交和轮询；[context_workspace.py](../../app/presentation/context_workspace.py)声明接口；[ContextService](../../app/application/agents/context_service.py)执行维护操作。

旧执行者可能在停顿后恢复，尝试保存过时状态：

~~~text
旧执行者读取预算 300，revision=7
                    |
                    | 中途停顿
                    v
另一有效执行保存预算 250，revision=8
                    |
                    v
旧执行者恢复，试图按 revision=7 保存
                    |
                    v
数据库发现版本或票据不匹配 → 拒绝旧写入
~~~

revision 说明数据版本，fence 是递增执行票据，CAS（比较后写入）要求持有版本与数据库当前版本相符。[save_claim()](../../app/infrastructure/persistence/sql/session_store.py)在 SQLite 事务内核对 owner、revision 和 fence，保存 AgentState 与相应 checkpoint。这个边界避免旧执行者覆盖新状态，不应扩大成跨任意存储的全局事务保证。

**放到训练里看。** 数据版本加执行票据，保证的是会话状态有一条确定的线性历史。04 的评测协议里「固定 Judge 输出和 trace 重放五次结论不能翻转」，重放的是评分代码、不碰会话状态，但用的也是这种确定性：输入一样，结论就一样。训练环境不需要这套并发保护——每条轨迹独立，没有第二个执行者——但它提示了一件真跑时的事：同一条轨迹回放评测时，环境里不能有任何未记录的随机性。

<a id="approval-3"></a>
## 五、长期偏好和订单分别怎样确认

**这一节在项目里管什么。** 六类信息里有两个最危险的写操作：往长期记忆里写（影响以后所有会话），和动库存（真金白银）。这一节讲它们各自的授权方式——一个是工具调用级的审批，一个是业务确认单。两者都遵循同一条原则：模型只能建议，授权必须来自买家的一次明确动作。

本节学习长期记忆维护与订单确认卡。“这次预算 250 元”属于任务约束；“以后偏好轻便设计”才表达稳定偏好。助手说过什么不自动成为买家事实。

~~~text
对话中明确要求长期记忆变更
    |
    v
模型调用记忆工具
    |
    v
MemoryPermissionMiddleware 要求本次审批
    |
    v
前端展示待批准 / 拒绝的操作
    |
    v
买家提交决定 → 后端核对当前待处理调用
    |
    +-- 批准：恢复该工具执行，保存记忆
    +-- 拒绝：不执行这次变更
~~~

[tool_confirmation.py](../../app/application/agents/tool_confirmation.py)把批准/拒绝关联到当前挂起调用。前端不能借审批换工具或追加永久放行规则。页面上买家直接编辑偏好是显式操作，与模型请求修改记忆的入口不同。

之后的会话按当前问题召回偏好，再注入模型输入。语义召回可以先理解为“找出含义上与当前任务相关的偏好”；项目还保留负向约束，并核对记忆的当前版本。[记忆中间件](../../app/application/memory/middleware.py)、[语义偏好存储](../../app/infrastructure/semantic_memory.py)分别对应读路径与存储。

订单走持久业务确认：

~~~text
create_order_tool / cancel_order_tool
    |
    v
准备持久确认单，此时尚未完成实际创建 / 取消交易
    |
    v
前端展示确认卡 → 买家批准或拒绝
    |
    v
POST /commerce/confirmations/{id}/resolve
    |
    v
校验买家、会话、确认内容、有效期和业务条件
    |
    +-- 批准：事务内处理订单、库存和确认结果
    +-- 拒绝：保存拒绝决定
~~~

[ConfirmationService.resolve()](../../app/application/usecases/confirmation_service.py)没有注册为模型工具。聊天文字“同意”或模型转述不能直接替代真实确认请求。

后端知识补充：事务把相关数据库操作作为一个整体处理，例如订单、扣库存与确认结果保持一致；幂等保证同一次业务决定重复到达时不重复产生相同副作用。

~~~text
第一次批准：
提交订单 + 扣库存 + 保存确认结果 → 响应途中断网

同一确认的批准重试：
找到已提交结果 → 返回原结果 → 不重复创建订单或扣库存
~~~

[交易存储 resolve_confirmation()](../../app/infrastructure/persistence/sql/trade_store.py)对同一确认的相同决定返回原结果，对相反决定拒绝修改。当前本地订单确认金额只含商品，不含运费和关税；它与商品搜索卡到手价的口径需要分别看字段，不能自动视为同一金额。[交易确认与库存说明](../交易确认与库存验证-2026-09-09.md)

**放到训练里看。** 这两套授权正是训练环境最难线上化的部分：审批要真人点，06 干脆把记忆写工具挡在动作空间外，审批链路在训练里整个不存在，规则化的模拟用户只替买家回答澄清表单和追问（06 第二节）；库存扣减有副作用，所以 06 的任务干脆只检索、不下单，用收窄换可重置。将来要训下单决策，就得有这一节「同一个决定只生效一次」的幂等保护，否则一条轨迹里的重试就能把库存打穿。

<a id="recovery-3"></a>
## 六、刷新、断网、停止、重启各恢复什么

**这一节在项目里管什么。** 页面断线和后端运行是两条命：浏览器随时可能刷新、断网、关掉，后端的一段运行却可能还在跑。这一节讲两条生命周期各自的边界——什么能恢复、什么不能，靠的是运行日志而不是「冻结进程」。

本节学习当前网页的恢复合同。一次后端运行与一个浏览器订阅连接具有不同生命周期：

~~~text
后端执行任务 → 事件追加到持久日志
                        |
                        v
浏览器收到序号 1、2、3……
                        |
                        X 网络中断
                        |
                        v
重新请求最后已收序号之后的日志
                        |
                        v
收到 4、5、6……
~~~

Cursor（游标）表示已经读到的位置。[recoveringFetch.ts](../../frontend/src/lib/recoveringFetch.ts)会核对序号、忽略重复事件并用 GET 重读已有运行的日志；不会为断线恢复反复 POST 新的模型运行。

| 情况 | 当前项目的处理边界 |
| --- | --- |
| 刷新、订阅断线 | 恢复已有消息和事件，活跃后端任务可以继续 |
| 点击停止 | 提交明确取消请求，并确认服务端状态 |
| 停止请求网络失败 | 保留“尚未确认停止”的不确定状态 |
| 后端关闭或执行租约失效 | 未完成运行标中断，已保存内容可恢复查看 |
| 下一轮继续提问 | 从保存的会话状态进入新一轮处理 |
| 订单已提交后停止 Agent | 不自动撤销交易，取消订单走自己的确认流程 |

恢复页面和会话内容，不等于恢复模型进程内部执行位置。未完成模型调用不能仅凭日志存在就声称自动续跑。[AGUIRuntime](../../app/presentation/ag_ui_runtime.py)控制运行，前端 [commerceClient.ts](../../frontend/src/lib/commerceClient.ts)中的 stop()/detach() 区分停止运行与离开订阅。

第 14 章仍保留快照损坏后“按新会话继续”的旧示例；当前 [SessionRegistry](../../app/application/agents/main_agent.py)会在快照损坏时抛错，避免空状态覆盖历史。恢复行为以当前代码为准。

**放到训练里看。** 运行日志能把页面恢复到任意进度，但它不是轨迹：[02 第六节](02_AgentLoop与子Agent派发.md#events-2)讲过，高频片段不逐条保存、遥测正文脱敏。训练轨迹要的是完整、未脱敏的消息序列，只能在模型请求和工具结果两处直接取，不能指望事后从日志拼回来。

<a id="guards-3"></a>
## 七、工具报错和反复调用时的护栏

**这一节在项目里管什么。** 02 讲循环怎样前进，这一节讲循环怎样不出事故：调用的次数要有上限，等待要有期限，失败要有冷却，原地打转要有提示。它们的共同原则和 02 第三节一致——失败要变成明确的错误结果交给模型，不能伪装成「没有商品」。

本节学习买家看到的等待、错误提示与执行收尾背后的代码。

| 机制 | 控制的问题 | 边界 |
| --- | --- | --- |
| max_iters | 循环次数过多 | 不能保证每一步都有价值 |
| 工具超时 | 单次调用迟迟不返回 | 应回传明确错误，不能伪装成没有商品 |
| 熔断 | 同一工具持续失败还被反复调用 | 冷却后允许探测，失败可再熔断 |
| LoopDetector | 同一工具用同样参数反复得到同样结果 | 只注入提示，不跳过工具、不强制停止；翻页、换字段或结果变化都不算 |
| Token 预算 | 控制消耗与收尾行为 | 是否生效须看配置 |

~~~text
Agent 请求工具
    |
    v
执行适用的权限与调用检查
    |
    v
工具中间件
    +-- 判断熔断
    +-- 限制等待时间
    +-- 处理成功结果或错误
            |
            v
结果 / 明确错误回到 Agent
            |
            v
重试、换策略、说明失败或收尾
~~~

[resilience.py](../../app/infrastructure/resilience.py)把超时或熔断表现为错误结果；[LoopDetector](../../app/application/harness/loop_detector.py)在工具返回后判断：最近 6 次已完成的调用里，同一工具、同样参数得到同样结果累计 3 次，才追加一条提示；中间穿插别的调用也能识别，参数不同或结果变了就不提示（2026-10-19 按当前代码核对；旧版本按连续工具名判断）。触发次数不能直接当作成功阻止死循环的次数。排查时要区分模型未回答、工具超时、运行取消与浏览器断线。

**放到训练里看。** 护栏追加的 `[harness]` 提示会出现在工具结果文字里，是模型实际看到的观察的一部分——训练时应当作环境反馈保留，不要剔除（理由和处理见 [06 第九节](06_训练推演_澄清检索补证.md#reproduce-6)）。06 的环境不挂这些中间件，属于和线上的差距；真要在线上环境训练，护栏的参数（超时、阈值）也要固定，否则不同轨迹的观察口径不一致。

## 补充：正文之外的状态与支撑机制

正文按 `8cbd4d6` 写成。2026-10-19 对照当前代码，支撑层还有几样正文没讲的机制，多数来自 2026-10-14 合并的上游提交。站在整个系统看，它们回答的是同一个问题：怎样让一段会话的行为可复现、可追踪，出了错能如实说明。

默认生效的四项：

| 机制 | 做什么 | 为什么需要 |
| --- | --- | --- |
| 会话固定 Prompt 版本和模型 | 会话第一次运行时分到一个 Prompt 版本，之后固定；工具契约变了会报错而不是悄悄换版本。买家切换模型只对下一轮生效，每轮开始时冻结模型快照，等待审批的会话沿用发起审批的那个模型 | 同一段会话的行为可复现；中途换模型不会打乱进行中的回合和审批 |
| 执行记录 | 工具步骤和模型公开的思考写进运行日志，页面的「执行记录」标签显示白名单摘要；重启或停止时，进行中的步骤标为中断或取消 | 刷新、重启后能如实显示每一步的状态；审批卡上的「已批准」不等于已经执行 |
| 下单前核对检索证据 | 订单工具只接受本会话检索返回过的商品和规格 | 防止模型凭编造的 ID 准备订单 |
| 子 Agent 共用护栏 | 主 Agent 把顺序检查和重复检测交给子 Agent 共用 | 派发给子 Agent 后，护栏不会失效，也不会重新计数 |

默认关闭、要通过 Harness 收益门禁（见第四阶段）才开启的两项：

- 显式 Prompt Cache 标记与稳定前缀：让每轮请求的开头逐字不变，并主动标出可缓存的部分，目的是让供应商缓存命中、省钱、降低延迟，收益还没有验证。为此要把每轮都变化的选购状态移出系统提示。默认的 passthrough 只是不主动标记，并不等于关掉供应商自己的隐式缓存。
- 有限续写与容量恢复：回答被截断或断流时有限次续写；输入超出模型容量时只归档已读结果再试一次。开启后跳过外层整轮重试，避免重放交易。

还有一条在 layered 策略下生效的规则：买家问的历史商品整批都还在上下文里时，直接用已有证据作答；买家明确要求重新核验某个规格的当前价格或库存时，强制先调用检索工具。它减少了无谓的回查，也避免把历史当成当前，但这是规则在替模型做「要不要补证据」的决定。训练推演要学的恰好是这个决定，到时候要先关掉或绕开这条规则。

另有一项默认关闭的学习数据回流，属于质量层，见第四阶段的补充一节。

### 作业 B 参考主干

~~~text
浏览器                确认接口                  数据库
  |---- 批准 C --------->|---- 开启事务 ---------->|
  |                      |    校验、创建订单       |
  |                      |    扣库存、存确认结果   |
  |                      |<--- 提交成功 -----------|
  X 响应途中断网         |
~~~

同一确认改成相反决定时，后端拒绝修改已作出的决定。浏览器未收到响应不证明首次失败，应查询或接收服务端的持久结果。

### 八题参考答案

1. 本次预算属于当前约束，稳定偏好经用户明确保存后可成为长期记忆；历史报价属于证据，待批准订单属于业务确认状态。它们生命周期不同，不能都自动写成长期偏好。
2. 过早归档会让模型还没获得读取完整新结果的机会就只剩引用；代码记录“进入成功模型调用”也不能证明理解正确。历史库存仅说明当时观察，当前库存需重新查询。
3. HTTP 202 不能证明完成，前端应检查操作状态并按 operation_id 查询。摘要检查只覆盖已实现的格式和来源约束，无法自动证明新旧需求、时间与语义全部正确。
4. 直接覆盖可能丢失新需求和进度。revision 检查数据版本，fence 检查执行票据；数据库保存时共同校验，拒绝旧执行者并要求重读。
5. 记忆工具通过原生审批挂起并恢复；订单工具先准备持久确认资源，实际交易由用户动作接口提交。历史摘要不构成授权，不能代替待审批调用和确认单的真实决定。
6. 后端根据同一确认及已提交结果做幂等处理，并把订单、库存和确认结果放进一致事务。禁用按钮挡不住网络重试、多标签页和直接请求。
7. 断线影响订阅，停止是明确取消，重启会中断旧进程的未完成执行。任何一种都不能仅凭保存了日志就宣称恢复模型内部执行栈；页面和会话各有恢复路径。
8. 超时限制一次等待，熔断暂时阻止持续失败调用，LoopDetector 提示减少重复行为；循环提示本身不会强制停止，迭代上限和预算另有职责。

验收：合上资料解释“整理为什么不等于删历史”“刷新为什么不等于重新执行”“批准重试为什么不应再扣库存”，然后定位 ContextService.start()、save_claim()、ConfirmationService.resolve() 和 recoveringFetch.ts，指出它们各保护哪种项目状态。

## 60 秒口述与面试追问

**60 秒口述。** 真实的选购是连续多轮的。Globex 把一段对话里的信息分成六类：模型这次看到的上下文、会话运行状态、原始证据、长期记忆、运行日志、业务账本，各自保存、各自恢复，存了不等于模型会读到。长对话靠分层治理控制输入：保护当前和正在比较的内容，把用过的旧结果换成可回查的编号，必要时再做带检查的摘要。所有改变状态的动作都有保护：整理上下文是带数据版本和执行票据的维护任务，过时的执行者写不进来；记忆变更要买家批准这一次调用；订单走持久确认单，在一个事务里处理订单、库存和确认结果，重复提交不会重复扣库存。恢复的是已保存的内容，不是模型的执行位置；超时、熔断和迭代上限把失败变成明确的结果，重复检测只给模型提示。放到训练里看，这些持久状态正是环境难以重置的原因，训练时要用隔离的数据和模拟用户。

**面试追问。**

| 追问 | 答题要点 |
| --- | --- |
| 整理上下文会不会丢信息？ | 不删原始证据，只把旧结果换成取件编号，需要时用回查工具找回；摘要检查只保证格式和部分来源，失败就回滚 |
| 两个执行者同时保存会话怎么办？ | 数据库在事务里核对数据版本和执行票据，过时的写入被拒绝；前端禁用按钮只是交互限制 |
| 为什么记忆和订单走两套授权？ | 记忆是工具调用级的审批，批准的只是当前挂起的这次调用；订单是业务确认单，真正的交易由买家通过确认接口提交，在事务里处理并且幂等 |
| 批准时断网，重试会不会重复下单？ | 不会。同一确认的相同决定返回原结果，相反决定被拒绝；浏览器没收到响应不代表第一次失败了 |
| 这些状态对 RL 训练环境意味着什么？ | 库存和会话持久、不能一键重置，每条轨迹要隔离数据；审批要用模拟用户；上下文策略和 Prompt 版本要固定，否则观察分布会漂移，效果变化说不清来源 |
