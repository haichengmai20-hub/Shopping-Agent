# Globex 时间紧张版学习路线

这套材料以当前 Globex 项目为学习对象，以 [时间紧张版教程导读](../../docxs/Globex_教程导读_时间紧张版.docx) 的阶段顺序为主线。先读项目的实际调用链和源码，再按需查阅 docxs 中的概念解释。教程中的设计、历史示例和当前运行代码需要分别核对。

<a id="project-map"></a>
## 项目全景：Globex 是一个什么样的系统

Globex 是一个跨境电商选购 Agent。买家在网页上用一句话描述需求，系统会澄清缺少的条件、检索商品、查品类知识、比较报价，准备订单确认单，买家点击确认后才真正下单；它还能记住买家的长期偏好，加载买家自己写的选购 Skill。商品来自版本化的样例目录（运行时用 v3，共 3700 个商品、7105 个 SKU），订单记在本地账本，没有接入真实的供给、支付和物流。

整个系统分四块：

| 块 | 做什么 | 主要部件 | 在哪篇讲 |
| --- | --- | --- | --- |
| 交互层 | 接收请求、推送进度、刷新后恢复 | React 页面、AG-UI 协议、SSE、运行日志 | 01、02、03 |
| 决策层 | 模型在循环里决定调哪个工具、要不要派子任务 | MainAgent、SearchAgent、TradeAgent | 02 |
| 能力层 | 提供可核查的事实和受控的动作 | 商品检索、品类知识、订单确认、长期偏好、澄清表单、个人 Skill | 05 讲商品检索，03 讲订单确认和长期偏好；澄清表单和个人 Skill 只在本页提到 |
| 支撑与质量层 | 让循环可控、可恢复，并判断做得好不好 | 上下文治理、审批、护栏、模型管理；评测、Bad Case、GEPA、Harness 评测套件 | 03、04 |

页面上能看到的其他功能也都挂在这四块上：偏好和个人 Skill 管理、上下文整理、确认单、订单列表、收藏、模型切换。

项目现在**没有参数训练**：评测和 GEPA 改进的是判断方法和提示词，不改模型权重。学完五个阶段后的训练推演，就是在这套系统上设想「把哪一部分交给训练、用什么当奖励」，见下文的[五个阶段在训练推演里对应什么](#training-map)。

## 纵览：一次选购请求做什么，分在哪几篇

Globex 处理一次选购请求，要做这些事：

- 页面把本轮文本，连同买家、会话、运行三个 ID 发给后端；后端校验后登记这一次运行。
- 编排器恢复这段会话的 Agent，把记忆提示、交易状态、上一轮候选和本轮问题组织成输入。
- MainAgent 进入循环：模型决定调哪个工具、填什么参数，后端执行，结果回到上下文，模型再决定下一步；需要时把子任务派给 SearchAgent 或 TradeAgent。
- 商品工具把参数变成结构化检索条件，查出商品、过滤、报价，做成带到手价的商品卡。
- 结果分两路回来：观察结果回到 Agent，事件经运行日志和 SSE 回到页面。本轮结束时，会话、对话和证据各自保存。
- 离线再用固定用例评测这一切：失败进 Bad Case，改进要在固定条件下复测。

用贯穿例子「帮我找一件轻便背包，寄到中国，总到手价不超过 300 元人民币」走一遍，共七站。每站进来什么、出去什么、在哪篇细学：

| 站 | 进来 | 出去 | 在哪篇细学 |
| --- | --- | --- | --- |
| ① 启动装配 | Uvicorn 加载 `server.py` | `build_container()` 装好的 Agent 工厂、会话注册表、编排器和 AGUIRuntime；`startup()` 初始化数据库、库存、商品向量索引和品类知识库 | 01 |
| ② 请求进入 | 页面发来的本轮文本，以及买家、会话、运行三个 ID | `POST /commerce/ag-ui/run` 解析、校验后的本轮输入；AGUIRuntime 登记这一次运行 | 01 |
| ③ 组织本轮 | 本轮输入 | 恢复的会话 Agent（已绑定 Prompt 版本和模型），加上记忆提示、交易状态、上一轮候选和本轮问题 | 01 讲入口，03 讲状态 |
| ④ Agent 循环 | 组织好的输入 | 模型多次「选工具 → 后端执行 → 结果回上下文」，必要时派发子 Agent，最后作答 | 02 |
| ⑤ 商品检索 | `product_search_tool` 的参数：轻便 背包、CN、CNY、300 | `ProductSearchSpec` → 召回与过滤（单件价不超过 300）→ 带到手价的商品卡 | 05 |
| ⑥ 回到页面与保存 | 工具结果和各类事件 | 观察结果回到 Agent；事件写进运行日志，经 SSE 变成页面上的文字和商品卡；会话状态按版本保存，对话和证据各自落库，刷新后能恢复 | 01、02 讲两条回路；03 讲保存与恢复；05 讲商品卡 |
| ⑦ 评测与改进 | 固定用例、评分细则、运行记录 | 确定性断言加 Judge → 分数与门禁 → 报告和 manifest；失败进 Bad Case；GEPA 离线改 Prompt | 04 |

### 五个阶段在训练推演里对应什么

学完五个阶段之后是**训练推演**（[06 训练推演](06_训练推演_澄清检索补证.md#overview-6)，2026-10-20 写成，代码在仓库根目录 `agentic_rl/`）：参照 Code-R1 的实跑推演，把第 ④ 站里「要不要澄清、怎样检索、要不要补证据」这组决策交给一个可训练的策略，用第 ⑦ 站的确定性断言做奖励的骨架。任务按[项目定位与其他AI须知](../项目定位与其他AI须知.md)的推荐：约束缺失或变化时，怎样澄清、检索和补取证据。每个阶段都为它打一块底：

| 阶段 | 讲的是 | 放到训练推演里看 |
| --- | --- | --- |
| 01 | 系统分层和一次请求的路径 | 分清策略和环境：要训练的是 MainAgent 里做决策的模型，工具、业务用例、数据和会话状态都属于环境 |
| 02 | 工具循环与派发 | 动作和观察：每次选工具是一个动作，工具结果是观察，一串动作和观察就是一条轨迹 |
| 03 | 状态、审批与恢复 | 环境能否重置、轨迹能否复现：库存和会话是持久的，审批要有人点；训练时要给每条轨迹隔离的数据，用模拟用户代替真人 |
| 04 | 评测与质量闭环 | 奖励从哪来：确定性断言是可验证奖励的骨架，但现有断言偏弱，要补检查、防投机；Judge 有噪声，P0 门禁要保留成硬约束；现有的学习数据回流离训练轨迹还差很多 |
| 05 | 一个核心工具的全链路 | 奖励按什么口径算：检索只按单件价过滤、到手价另算，奖励要自己核对总价；被过滤掉的候选也是策略能利用的观察 |
| 06 | 训练推演本身 | 把上面五块拼成一个可重置的环境、两版奖励、规则基线和两轮训练；真实运行证明原版奖励看不见陷阱商品、规则在换说法的 held-out 上只有 10% |

现在的代码离可训练环境至少还差三样：环境不能重置、拿不到 logprob、layered 策略下有规则替模型决定要不要补证据。详见仓库根目录 `CLAUDE.md` 第 6、7 节。

合并上游（2026-10-14）后新增的内容，2026-10-19 已补进对应阶段：会话固定 Prompt 版本和模型、执行记录、下单前核对检索证据，见 03 的[补充一节](03_Harness与状态管理.md#upstream-3)；Harness 评测套件、Skill 分场景评测、学习数据回流，见 04 的[补充一节](04_评测失败分析与训练边界.md#upstream-4)；增量建库、按 ID 精确查询、选购工作台与执行记录，分别见 05 正文的第三节、第四和五节、第七节。

### 一张图记住全程

~~~text
① 启动  Uvicorn 加载 server.py → build_container() 装配 → startup() 初始化数据库、库存、索引、知识库
          |  （每个进程只做一次）
          v
② 请求  React 页面 -- POST /commerce/ag-ui/run --> 解析并校验买家与会话 --> AGUIRuntime 登记 run
          |
          v
③ 本轮  MainAgentOrchestrator：get_or_create 恢复会话 Agent，
        组织记忆提示 + 交易状态 + 上一轮候选 + 本轮问题
          |
          v
④ 循环  MainAgent 与模型往返，最多 15 次迭代；
        按需 task_dispatch --> SearchAgent / TradeAgent（各最多 6 次）
          |
          v
⑤ 检索  product_search_tool --> ProductSearchSpec --> CatalogSearchUseCase：
        召回 → 过滤（单件价 ≤ 300）→ 商品卡（到手价按 1 件报价）
          |
          v
⑥ 回路  观察结果 --> 回到 Agent，继续判断或作答
        业务事件 --> AG-UI 适配 --> 运行日志 --> SSE --> 页面商品卡
        本轮收尾 --> AgentState 按版本保存；对话、证据各自落库
          :
          :  （离线）
          v
⑦ 评测  固定用例 --> 运行 --> 确定性断言 + Judge --> 分数与门禁 --> 报告 + manifest
        --> Bad Case --> 修改 --> 固定条件复测
~~~

一句话版本：**页面把一句话交给后端，编排器恢复会话、组织输入；模型在循环里选工具、看结果、再决定；商品工具负责查证、过滤和报价；结果一路回到 Agent，一路回到页面，本轮记录各自保存；离线再用固定用例和断言判断做得好不好。**

## 讲解约定

带学一个阶段时，先在对话里讲三段：纵览（本页上面那一节，按最新状态更新）、本阶段总览（它在全流程里做什么、长什么样）、本阶段文字版导读。三段都要按当前源码和资料逐条核对，再写进资料：纵览写进本页；总览和导读写进该阶段文档开头的 `overview-N`、`guide-N` 两节，原有的开头说明并进总览。

每篇都从完整项目的全局视角来写（用户 2026-10-19 要求）：总览先讲这一篇在整个系统里的位置、要回答的问题和答案，再讲「放到训练推演里看」，最后是全篇结构、用时与边界、源码依据和前后衔接；导读讲机制、取舍和边界，不纠缠代码细节，行号只留在仓库根目录的 `CLAUDE.md`；每篇末尾有「60 秒口述与面试追问」，口述从整个项目讲到这一层，追问里至少有一条和训练有关。

每份材料开头明确本阶段正在学习 Globex 的什么功能，并对应到买家操作或项目工程任务。每份材料都包含该阶段的前端、后端及相关工程概念的直观解释：概念是什么、在 Globex 的哪个文件里、它解决了什么问题、数据怎样跨越前后端边界。作业包含手写 plain text 流程图、几个需要用自己语言回答的问题，以及完整参考答案与自查标准。答案放在题目之后，便于先独立完成。

学习资料默认只解释和引用项目源码，不修改 docxs 原件。模型 API、商品样例和运行状态以当次项目证据为准；阅读代码不等于真实服务或效果已经验收。
