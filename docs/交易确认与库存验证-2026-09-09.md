# 交易确认、库存事务与前端闭环

实施日期：2026-09-09。当前工程已实现独立的持久确认资源、原子交易账本、前端确认卡和 AG-UI 状态投影。下单指创建项目内的订单意向，没有支付或物流调用。

## 执行路径

1. `create_order_tool` / `cancel_order_tool` 仅准备确认；商品详情表单也可直接准备。
2. 服务端按当前目录与持久库存生成 `confirmation_id`、`operation_id`、`snapshot_hash`、有效期及商品/数量/原币价格/地址快照。金额只含商品，不含运费和关税。
3. `confirmation.required` 事件投影到 AG-UI `state.confirmations`，React 渲染真实确认卡。聊天中的“同意”和模型转述不能执行批准。
4. 用户点击卡片调用 `/resolve`，SQLite `BEGIN IMMEDIATE` 中校验归属、会话、hash、有效期与当前价格/币种；订单、条件扣库存、操作记录和确认决议同事务提交。
5. 同一确认的重复决议返回原结果；相反决定拒绝。不同购买操作有不同操作 ID，允许再次购买相同商品。取消同样原子回补且只执行一次。
6. GET/list 从持久化账本恢复确认状态；刷新后的迟到 pending 不能覆盖已确认结果。已结束的卡片默认收起商品与地址明细。
7. 每轮模型输入补充当前会话的精简交易事实，包含真实订单状态与待确认商品引用；不再次注入收货地址或确认 hash。存在交易事实时不使用仅含最终文本的语义缓存。

这不是 AgentScope 原生 `resume`：标准 AG-UI 消息与工具事件仍保留原生边界，交易决议由独立 HTTP 资源承载。当前 SSE 断连仍取消本轮，尚未实现事件游标重放或后台继续运行恢复。

## API

| 接口 | 用途 |
|---|---|
| `POST /commerce/confirmations/orders` | `buyer_id/session_id/items/shipping_address`，准备订单意向 |
| `GET /commerce/confirmations?buyer_id=...&session_id=...` | 最近 20 条确认记录 |
| `GET /commerce/confirmations/{id}?buyer_id=...&session_id=...` | 恢复单张确认状态 |
| `POST /commerce/confirmations/{id}/resolve` | `buyer_id/session_id/snapshot_hash/approved`，明确批准或拒绝 |
| `GET /commerce/orders/{id}?buyer_id=...` | 核验归属后查当前订单状态 |
| `POST /commerce/orders/{id}/cancel` | `buyer_id/session_id/reason`，仅准备取消确认 |

HTTP 层拒绝布尔/小数/字符串数量、字符串 approved、额外字段及空身份。业务层再次校验数量、配送国家、SKU、价格和库存。用户身份仍是本机 demo 的客户端声明；这些归属检查不等于生产登录鉴权。真实多用户部署还需可信登录身份及会话/WS 权限绑定。

## 库存与迁移

- 订单继续使用已有 `orders/order_items`，新增 `trade_sku_inventory/trade_confirmations/trade_operations`。
- 首次初始化以目录库存为初始库存，扣除已有 SQL CONFIRMED 订单占用；超过种子库存时拒绝启动，要求核对迁移。
- 重启只更新目录价格/币种/规格标题，不重置库存；商品查询从 SQL 账本投影库存。
- `DATABASE_URL=file` 时会话/偏好仍用文件，交易使用 `DATA_DIR/trade.db`。检测到非空旧 `orders.json` 时拒绝静默忽略，要求迁移。原版内存订单在旧进程退出后已经丢失的内容无法凭空恢复。
- SQLite 同机多连接/多进程已验证；未声称支持 PostgreSQL/MySQL 事务语义。首次并发初始化也在写锁内建表。
- 提交前异常或取消会回滚。提交后连接丢失时使用同一确认查询/重试，不把网络中断误判为已撤销。
