## 后续记录规则

1. 每次工程交付前，在 `docs/改动记录/YYYY-MM-DD/功能点.md` 创建或更新记录，并维护当日 `README.md` 与本页日期索引。
2. 同一天同一功能的补充、修复和复测写回同一文件，保留阶段顺序与原始失败；同一天不同功能分文件。跨天继续做该功能时新建当天记录，链接此前记录，不覆盖之前的验证结论。
3. 每份记录写清需求或问题、具体变化、关键源码、验证方式和证据、遗留问题、关联版本。涉及配置和数据时补充启用条件、迁移或回滚方式。
4. 区分“代码已实现”“测试通过”“真实外部链路通过”“效果验收通过”；计划和外部阻塞明确标记，不用单测通过替代效果结论。未经测量的数据写未知。
5. 按可核实的日期归档。前序修复随当天发布时标明“本次合并发布，开发日期未独立核实”，不凭文件修改时间虚构开发日期。
6. 链接原始日志、失败样本、截图和冻结数据，不复制完整报告；历史证据及其指纹保持原样。使用仓库相对链接，凭据、真实数据库和买家原文不进入记录。
7. 当日总览统一记录共享回归、代码提交与发布边界。提交哈希在产生后补充；提交前写待提交，不编造版本。这套归档规则本身不新增自动推送或定时任务。

## 功能记录格式

每份文件按下面顺序组织，内容短时可合并段落，不强行填空：

- 标题：日期 + 功能点；开头写当前状态与关联代码版本。
- 问题或需求：这次为什么修改。
- 本次变更：行为前后差异、关键实现、源码入口。
- 验证与证据：执行了什么、结果是什么、数据与服务是否隔离。
- 遗留问题与后续：尚未通过的场景、下一步、配置和回滚边界。

现有设计文档继续讲机制，`docs/设计演进记录.md` 保留历史与总入口，不再把每天所有功能的明细堆在一个章节里。协作约定同时写入工程根目录 [AGENTS.md](../../AGENTS.md)。
