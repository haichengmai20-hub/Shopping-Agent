本仓库当前是 **Agent 应用 + 评测 + 离线文本优化（GEPA）** 工程，具备改造成 Agentic RL 环境的业务底座，但**尚未完成任何参数训练**；对「中国大陆大厂后训练岗」的求职目标而言，推荐路线是：**把 Globex 当业务环境与工程底座，针对一个窄的多轮决策问题做真实参数训练，并把 GEPA／Skill 优化留作对照组**。

## 这个仓库现在有什么、没有什么

| 当前能力 | 实际做的事情 | 能证明什么 |
|---|---|---|
| MainAgent、SearchAgent、TradeAgent | 调用模型 API，选择工具、处理观察、继续推理 | 有 Agent 执行与业务编排能力 |
| 评测、Rubric、Bad Case 管理 | 检查工具调用、回答和业务状态，保存失败证据 | 有质量评估与改进基础 |
| GEPA 优化 | 根据运行反馈生成、评估新的 Prompt 或公共 Skill 正文 | 有非参数的文本优化能力 |
| 模型参数训练 | 当前可执行链路中未找到相应训练入口、参数更新与权重产物 | **目前不能宣称已完成 SFT／Agentic RL 训练** |

**分类要按「优化对象」理解，不能按名字理解：**

- 改 Prompt、Skill、记忆 → 改变模型运行时看到的内容（本仓库目前只做到这里）。
- 做 SFT → 用示范更新模型参数。
- 做 Agentic RL 后训练 → 让策略与环境交互，根据奖励更新模型参数，包括可训练的 LoRA 参数。
- 「自进化」是更宽泛的说法，可以包含上述不同方法，**不能单凭这个名称判断有没有训练**。

**Globex 的优势在于业务环境较完整，短板在于尚未形成适合学习的任务。**

它已经有商品、SKU、配送、价格、库存、工具结果和证据回查；也有澄清、需求变化、会话状态和人工审批。这些可以支撑「观察结果以后再决定下一步」的任务，电商场景本身并不排斥 RL。WebShop 就是将选购过程构造成交互环境并开展训练的先例，但它的结果不能替代 Globex 的验证。参考 [WebShop 论文](https://arxiv.org/abs/2207.01206)。

问题是：**系统流程长，不代表需要学习的决策链也长。**

如果任务总是：

```text
用户给齐条件 → 模型提取参数 → 搜索工具过滤 → 返回商品
```

那么主要问题可能是结构化抽取、检索质量和业务规则。先做好 Prompt、SFT 或工具实现，通常更容易判断收益。为了把它叫作 Agentic RL，强行增加思考轮次、工具调用或子 Agent，没有明确价值。

当前 GEPA 恰好就很窄：它主要检查每次搜索参数有没有保留预算、配送地、材质等条件，**不检查最终推荐是否正确，也不检查完整选购是否成功**。评分口径就是「工具调用参数是否保留买家约束」，见 [现有评分逻辑](../scripts/optimize_prompts.py) 的 `tool_argument_constraint_preservation`。

另一个具体例子是预算：`price_max_major` 只约束单件商品价，而展示的到手价在另一处计算，数量固定为 1。因此，「含税运买两件，总预算 300 元」不能直接靠这个字段保证。这个缺口需要先明确业务合同和计算方式，不能指望 RL 补救。参见 [价格过滤与报价代码](../app/application/usecases/catalog_search.py) 中 `price_max_major` 的比较与 `landed_price` 报价处（`quantity=1`）。

**最推荐的训练题目是：约束不完整或发生变化时，如何通过澄清、检索和证据补取，完成可靠的选购决策。**

这是建议新增的实验任务，尚不是仓库已有的训练能力。第一版只训练一个策略，动作限制为：

```text
读取当前需求与已知事实
        ↓
选择：澄清缺失条件 / 搜索 / 复核候选 / 回查证据
        ↓
收到用户或工具的观察
        ↓
更新判断，选择下一步
        ↓
给出有证据的推荐，或说明限制，或等待必要信息
```

例如，任务可以区分：

- 条件已经完整：继续追问只增加成本。
- 缺少一个会改变候选集合的条件：应先问清。
- 第一次搜索没有结果：需要改写检索词或补证据，不能擅自放宽用户的硬约束。
- 用户改变了材质或预算要求：需要淘汰旧候选，不能沿用过期条件。
- 已获得足够证据：应停止搜索，避免无效循环。

这里模型要学的是**信息获取与决策策略**。训练价值来自「不同动作影响后续观察和最终结果」，而不是回答写得更长。

第一版建议采用结构化、规则式的模拟用户：隐藏条件由任务生成器保存，只有被问到时才按规则回答。这样更容易核验真值，也能减少让另一个 LLM 随意模拟用户带来的噪声。之后再测试自然语言变化和更开放的交互。

不过必须有一个停止条件：**如果固定规则「问完几个槽位，再搜一次」已经稳定解决任务，就不要继续强上 RL。** 这说明任务没有体现需要学习的多步决策，应该调整研究问题，或者接受规则方案已经足够。

**要做成真实训练，最少补齐下面五项；这也是面试时能深入讲的内容。**

1. **可重置、相互隔离的环境。**
   每个 episode，也就是一次完整任务尝试，都有固定任务、初始状态和终止条件。新建会话不等于重置库存和订单；需要隔离状态，区分成功结束、等待用户、出错和达到步数上限。

2. **可以更新的策略模型。**
   将明确的一份策略接到可训练模型，冻结其他模块。仅更换模型 API 地址，只完成推理接入；还要有训练器、参数更新、权重保存和新权重评测。

3. **训练所需的真实轨迹。**
   保存每次策略实际看到的输入、生成 token、工具观察、策略版本，以及所选算法需要的 logprob 和 mask。不能把网页聊天记录重新编码后，就默认它与原始采样完全一致。verl 的官方文档也特别指出工具解析、重新编码造成的不一致会影响 RL 训练。参考 [verl Agent Loop 文档](https://verl.readthedocs.io/en/latest/advance/agent_loop.html)。
   Globex 的遥测导出会将部分消息正文替换为长度，因此「Langfuse 有 trace」也不等于已经具备训练轨迹，见 [遥测脱敏代码](../app/infrastructure/tracing.py) 中把正文字段替换为 `len(...)` 并标记 `globex.content.redacted` 的分支。

4. **能抵抗投机的奖励。**
   主要奖励应来自最终推荐是否满足任务条件、证据是否支持结论；成本可以作为次要项。要防止模型靠「永远不推荐」「永远追问全部条件」「删掉约束后返回商品」得到高分。确定性的业务条件优先由代码验证，主观表达再考虑经过校准的 Judge。
   现有评测的加权分数与硬门禁是分开的。按当前公式 `0.5*P0 + 0.35*P1 + 0.15*P2`，P0 通过 4/5、P1／P2 全过仍可得 0.9 分，但整体应判失败（P0 必须全过）。直接把这个原始分数拿去最大化，会丢失关键限制。见 [评分与门禁代码](../scripts/eval_regression.py) 的 `score_case`。

5. **能区分「训练收益」与其他变化的对照实验。**
   固定模型基础版本、工具合同、目录、任务划分和推理预算。模型回退、语义缓存、摘要器等机制，要固定或明确记录，否则收益来源容易混杂。先训练单一角色，也更容易解释是哪部分行为改变了。

不建议第一轮同时训练 Main／Search／Trade，也不建议把库存扣减、税运计算或用户授权交给策略学习。这些应继续由业务代码保证。

**实验路线可以分阶段投入，先确认值得训练，再增加成本。**

| 阶段 | 应交付的证据 | 进入下一阶段的条件 |
|---|---|---|
| 规则与人工 Prompt 基线 | 任务集、成功判定、失败分类、工具与 token 成本 | 错误确实来自策略决策，而非工具或标签错误 |
| GEPA 对照 | 相同模型上的候选、独立评测、重复运行波动 | 能判断文本优化解决了哪些问题、还剩哪些问题 |
| SFT 基线 | 审核后的轨迹、训练配置、checkpoint、独立评测 | 基本工具行为可靠，并存在需要进一步优化的决策 |
| RL 实验 | rollout、奖励分项、训练日志、checkpoint、留出结果 | 相比 SFT 有可复核收益，或能解释明确的失败原因 |

这里 SFT 是否需要冷启动，要看所选基础模型的工具能力，不能机械地每次都从零做一遍。但**如果要宣称 RL 有贡献，就需要一个足够强的非 RL 基线**。

测试集也不能只是训练句子的同义改写。应留出新的需求组合、商品组合、澄清分支和无匹配场景，并同时报告成功率、硬约束违反率、交互次数、工具成本和随机波动。模型训练过与模型有效提升，是两项不同结论。

**求职展示时，你最需要形成的是一段能被追问、也有证据回答的个人贡献。**

例如，完成以后可以围绕这样的事实组织项目：

> 基于 Globex 的业务工具构建隔离的多轮选购环境，设计可核验任务与奖励；比较规则、Prompt／GEPA、SFT 和 RL，分析策略在澄清、约束变化及检索失败场景中的表现，并定位奖励投机和泛化失败。

这段描述中的每一步，都应有你实际新增的代码、实验或报告。已有仓库里的多 Agent、审批、持久化和页面，应清楚标为复用的基础；你的区分度来自任务建模、训练实现和实验判断。

如果你**已经有完整的 SFT／RL 实跑经历**，Globex 很适合用来补「环境交互、多轮工具决策、奖励设计」这部分特色。如果你**还缺第一份完整训练证据**，先跑通一个范围小的参数训练闭环，再接 Globex；直接改造整个全栈项目，容易让大量时间消耗在应用联调上。

就目前掌握的信息，下一步最值得投入的是：**先为一个窄任务做出可信基线和失败分类，确认存在规则与提示词无法充分解决的策略错误，再决定是否进入参数 RL。GEPA 保留为对照，前端与多 Agent 扩建暂时不应占据主要精力。**
